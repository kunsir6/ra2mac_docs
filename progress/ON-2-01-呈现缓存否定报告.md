# ON-2-01 否定报告：呈现层不能缓存 CGImage

**日期**：2026-11-11 05:5x
**任务**：ON-2-01「呈现管线：去掉每帧 CGImageCreate，按 surface 指针+尺寸缓存」
**结论**：**按任务描述实现会冻结屏幕**（DIB 每帧都在变，屏幕永远停在第 1 帧）。任务前提不成立，
已标 `superseded`。代码零改动（已回退到 HEAD），复现值与基准数字见下。

---

## 1. 做了什么

按任务 detail 实现了一版缓存：`compat/win32/src/RuntimeAppleWindowSurface.mm` 里按
`(pixels, width, height, bytesPerRow)` 四元组缓存 CGImage（no-copy provider，容量 2，LRU 淘汰），
每帧只做 `layer.contents = image`。为规避"CoreAnimation 因为 contents 还是同一个对象而跳过上传"
这个风险，还特意准备了**两个**图像对象轮流挂（相邻两帧的 contents 指针必然不同）。

然后做了隔离实验（`/tmp/pc/probe3.mm`，仓库外），三种模式各跑一遍，每阶段抓自己窗口的图：

| 模式 | 每阶段屏幕颜色（BGR 均值） | 判定 |
|---|---|---|
| `fresh`（每帧新建 CGImage） | 红(5,7,226) → 绿(5,227,4) → 蓝(227,5,23) → 黄(5,227,226) | **四帧四色，屏幕在更新** |
| `alt`（两个缓存对象轮流挂） | 红 → 红 → 红 → 红 | **冻在第一帧** |
| `same`（一直挂同一个对象） | 红 → 红 → 红 → 红 | **冻在第一帧** |

`alt` 与 `same` 抓出来的 PNG 四个文件**字节数完全相同（12174）**，即逐像素相同。
`fresh` 的四个文件是 12174 / 12160 / 12063 / 12036。

**所以交替挂两个对象救不了**：CA 的去重不是按"contents 指针变没变"，而是按图像对象本身
（或它背后的 provider）。一旦某个图像对象被上传过，再挂它就不会重新读内存。

## 2. 为什么必须在自己窗口里自抓

前两版用外部 `screencapture` 得到过互相矛盾的结果，原因是**遮挡**：被 WorkBuddy 窗口挡住的
游戏窗口抓回来是上一次的合成快照，"冻住"和"被挡住"看起来一样。

v3 改成：每次抓图前自己 `activateIgnoringOtherApps` + `makeKeyAndOrderFront`，再用
`screencapture -l <NSWindow.windowNumber>` 抓自己那个窗口。这样"谁在最前面"这个变量被消掉，
三组结果的差异只可能来自代码。

**副产品（对 ON-3-01 有用）**：`screencapture -l <windowNumber>` 在本机能抓到窗口级图像（18 KB 的
512×… PNG，内容正确）。此前 ON-1-03 因为"沙箱没有屏幕录制权限"而放弃窗口级取证，只用了整屏抓图。
注意：本轮对**产品窗口**（windowNumber=1836）试过一次 `-l`，返回
`could not create image from window`；对自建探针窗口全部成功。差异未查清（可能是抓图瞬间窗口正在
resize / 正在被销毁），ON-3-01 开工时先复测这一点。

## 3. 代价到底有多大（基准）

`/tmp/pc/bench.mm`，1024×640（2,621,440 字节）缓冲，20000 次迭代：

| 变体 | 每帧耗时 |
|---|---|
| A provider + image 每帧新建（当前实现） | **0.0013 ms**（1.3 µs） |
| B provider 缓存、image 每帧新建 | 0.0007 ms |
| C provider + image 全缓存（会冻结） | 0.0000 ms |

关键事实：`CGDataProviderCreateWithData` 是 **no-copy**，`CGImageCreate` **不分配像素缓冲**，
只分配一个描述对象。所以任务里"游戏内 60fps × 1.92MB 就是每秒上百 MB 的分配"这个前提是错的：
那 1.92 MB 的 DIB 只分配一次，每帧真正分配的是几百字节。
缓存能省下的上限是 **0.7 µs/帧 = 60fps 下 0.04 ms/s**，而代价是整屏冻结。

## 4. 更根本的问题：现在根本没有 60fps 的提交

用带计数器的构建实测（`CONCORD_PRESENT_STATS=1`，计数器随后一并回退）：

- 主菜单挂机 20 s：`shows < 10`（一次都没到 10 帧的打印阈值）——菜单只在交互时重绘。
- `--skip-main-menu --skip-skirmish-menu` 进游戏世界 45 s：**`shows = 2`**（首帧 + resize 后那一帧）。
  世界画完一帧就不再提交了，因为游戏内帧循环还没做（ON-4-03 pending）。

也就是说："每帧重建图像对象"这件事当前**每秒发生 0～0.1 次**，优化它没有任何可测收益。
真正该优化的对象是**提交次数**（ON-2-02 脏帧合并），而它现在的分母同样接近 0——
先把帧循环做出来（ON-4-03），"每秒提交多少次"才有意义。

## 6. 对后续任务的影响

- **ON-2-01** → `superseded`。不要再尝试缓存 CGImage（无论单对象还是双对象交替）。
- **ON-2-02（脏帧合并）** 仍是真需求，但它的价值不在省 CPU，而在**避免陈旧的重复提交**与撕裂。
  它需要先有帧循环，被 ON-4-03 前置。
- **ON-3-01（上屏自证）** 可以直接复用本轮的 `screencapture -l <windowNumber>` 路线：
  这是唯一能自动化的"屏幕上真的是这一帧"的证据，而且不依赖屏幕录制授权。
- 呈现层若要真正减少上传量，方向不是"缓存对象"，而是"只提交变化区域"
  （`layer.contentsRect` + 局部图像，或 IOSurface + 局部脏区），那是 ON-2-03/ON-4-03 之后的事。

## 7. 复现方式

源码与 12 张抓图已归档在 `progress/on-2-01-probe/`（`probe3.mm` / `bench.mm` / `probe-*.png`）。

```bash
# 隔离实验（仓库外，需签名后才能跑：未签名二进制会卡在 U 状态）
cd /tmp/pc
clang++ -fobjc-arc -std=c++17 -O1 probe3.mm -o probe3 \
  -framework Cocoa -framework QuartzCore -framework CoreGraphics
codesign -s - --force probe3
for m in fresh alt same; do MODE=$m ./probe3; done
# 每个模式产出 probe-<mode>-0..3.png，按"哪个通道占优"判别颜色

# 基准
clang++ -fobjc-arc -std=c++17 -O2 bench.mm -o bench -framework Cocoa -framework CoreGraphics
codesign -s - --force bench && ./bench
```
