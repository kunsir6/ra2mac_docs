**2026-11-10 P4-01b 复核（里程碑）**：`ninja -C build-product-mac -k 0 concord_runtime`
**BUILD_EXIT=0**，产出 `concord_runtime` 49,640,608 字节、Mach-O x86_64。
`nm -u` 里 grep `XAudio2Create|create.*DeviceWin32|makeUnsupported` 为空。
8 个符号的消失**零新增**——唯一新增的依赖是 6 个 `makeUnsupportedXxx` 桩
（工厂在 null 编码器 / null 诊断钩子 / 通道越界时的诚实回退），它们是产品源文件，
过去只在 Windows 的 `#else` 分支里被间接使用，Apple 侧第一次成为真实链接依赖。

口径提醒（下一轮别被 0 骗到）：缺口是 0 只说明"ld 不再抱怨"。仍然未知的有三件——
① 产品从未运行过，`菜单音效可播` 无第一手证据（P4-01c）；② `XAudio2Create` 返回
`E_NOTIMPL`，多路语音在 mac 上不出声（P4-02）；③ 没有 Windows 听感基线。
"缺口 0 + 编译干净"仍是**编译面**的完成，不是功能面的完成。

**2026-11-10 P4-01a 复核**：缺口仍是 8（C 1 / C++ 7），本轮**预期不动**——音频底座
（`src/audio/apple/RuntimeAppleAudioOutput.cpp`）是"给 P4-01b 的工厂用的零件"，自己不兑现任何
工厂符号。产品级 `ninja -k 0 concord_runtime` 130 步编译 0 FAILED，唯一 FAILED 是链接步，
8 个符号逐名与上表一致（XAudio2Create + 7 个 createXxxWin32）。**从这一轮起的判据**：
音频这一族盯的不是"缺口降了没有"，而是"解码与设备是否真的对"（自测 88 checks + 与 afconvert
逐样本一致 8,095,320 个样本），以及 b 轮的"缺口真正归零"。

**2026-11-10 S4-2 复核**：缺口 **仍是 109（C 83 / C++ 26），零新增、零消失**——这是预期的。
S4-2 不补链接符号：文本族 11 个 C-linkage 与 7 个字体 TU 的 29 个 C++ 符号在 S4-1 就已全部
兑现，缺的一直不是"符号存在"，而是"字形画不出来"（TextOutW 只画豆腐块）。这一轮把字形光栅
从占位换成 CoreText，链接面自然不动。**所以从本轮起，"缺口单调下降"不再是唯一进度指标**：
S4/S7 这类"符号已在、行为不对"的轮次不会让数字下降，验收要看各自的语义断言。

**2026-11-10 S4-1 复核（重要）**：上一行的 C-linkage / 项目 C++ 分段口径有误。按 ld 原始清单
逐条判定（符号名含 `concord::` 即项目 C++），P5-06 之后的 138 实际是 **C 83 / C++ 55**，
不是 75/63。总数一直是对的，只有分段列错。S4-1 之后 109 = C 83 / C++ 26，即本轮
**C 段一个都没动、C++ 段 −29**，与"放回 7 个字体 TU"完全对得上（逐名 diff：消失 29、新增 0）。
本表 P5-06 及更早的 C/C++ 两列只可看趋势，不可用于对账。

读法: 这一份不是 todo 列表，是**分区图**。
  A 段（C-linkage）是兼容层该兑现的 Win32/CRT 接口，机械工作，按族逐个实现。
  B 段（项目 C++）是 macOS 上**根本没有对应实现**的 Windows 专属层
  （字体/文字、GDI 覆盖绘制、D3D11 presenter、音频设备、BMP 读取），不能靠 shim
  兑现，要么把原 TU 放回构建图（纯逻辑），要么写 macOS 原生对位（D3D11）。

注意：**编译干净 ≠ 能跑**。编译只证明头层对上了，ld 才告诉你实现还差多少。
每轮收尾都要重跑本清单，链接缺口必须单调下降。

三件必须在下一轮之前记住的事（是"判据"，不是"待办"）：

1. **CreateFileW 的失败码不是装饰**。RuntimeAtomicFile 的临时文件重试用
   `GetLastError() == ERROR_FILE_EXISTS || == ERROR_ALREADY_EXISTS` 分流，并在
   ACCESS_DENIED 时再查一次属性决定要不要重试。若一律给 0 或 GEN_FAILURE，
   重试循环会空转 8 次后报"临时文件重试耗尽"——症状与"磁盘满了"一模一样。
   本轮的映射表就是按调用点真正会比较的那几个值写的，不是按 MSDN 顺序抄的。

2. **WriteFile 不 fsync**。Windows 的 WriteFile 也不保证落盘，落盘是
   FlushFileBuffers。为"稳妥"在这里加 fsync 会让存档路径慢一个数量级，
   而崩溃安全性一点没提高——原子性来自 rename，不来自把临时文件刷盘。

3. **wchar_t 宽度差异不在这层修**。本平台 wchar_t 是 32 位，U+1F600 是**一个**
   wchar_t；Windows 上是两个。本层保证的是**码点序列一致**。凡是拿 size() 当
   判据的地方（截断阈值、缓冲长度），两平台数字本来就不同——将来若要跨平台
   逐字节对拍，得先把这些判据改成按码点数，不能指望"这层做得更仔细"。

**一处刻意的偏离**（记在这里，免得下次被当成 bug）：
  GetCurrentProcess() 返回独立令牌指针，**不是** (HANDLE)-1。Windows 的伪句柄
  恰好等于 INVALID_HANDLE_VALUE，而本项目多处拿这个值判"打开失败"；照抄会让
  "当前进程句柄"被自己的失败判据命中。CloseHandle(伪句柄) 仍返回 FALSE。

  GetImageEncodersSize / GetImageEncoders  报告唯一一个 PNG 编解码器
  Gdiplus::Bitmap 构造                   持有像素缓冲 + 几何信息

实现落在 `compat/win32/src/RuntimeWin32CompatGdiplus.cpp`（新建，7 符号全在这一个 TU），
新建 `CompatGdiplusSemantics.cpp`（23 checks）。PNG 编码走 ImageIO，cmake 的
CONCORD_APPLE_WIN32_COMPAT_FRAMEWORKS 新增 ImageIO。

**范围判据**：全仓库只有 3 处用 GDI+，且全部只为「把像素缓冲写成 PNG 诊断图」
（RuntimeMapRenderer 启动器 / muzzles-N.png / 调色板审计图）。渲染结果不经过 GDI+，
所以本层不实现任何绘制语义——Gdiplus.h 头注释早写清了这一点。

**关键决策**：
- GetImageEncoders 报的 PNG Clsid 必须与 muzzle smoke 里硬编码的
  0x557cf406-1a04-11d3-... 完全一致，否则「查表取 Clsid」与「硬编码 Clsid」两条
  路径会对不齐。
- 像素布局 PixelFormat32bppRGB 在小端机上是 B,G,R,X，对应
  kCGBitmapByteOrder32Little | kCGImageAlphaNoneSkipFirst。selftest 用 ImageIO 把
  写出的 PNG 解回、画进默认 RGBA 上下文，断言红/绿像素的 R/G/B 通道次序正确
  ——这是「诚实判据」，防止 BGR 被静默当 RGB（编译不报错、图像难查）。
- Bitmap::Save(WCHAR*) 用 concord_compat::utf8FromWideText 转 UTF-8（wchar_t 在
  macOS 是 32 位 UTF-32，不能用 wcstombs 直接压 UTF-8）。
- 只兑现真正用到的 PixelFormat32bppRGB；ARGB/PARGB 全仓库无调用点，诚实返回
  InvalidParameter，不伪造实现。
