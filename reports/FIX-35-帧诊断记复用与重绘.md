判定依据：queue 无 brake、无腐烂预算（近三轮净增 +29 / +17 / −638，删除量 645）、无 attempts≥3

**但本轮受一条额外约束**：§八.3 比例闸仍在（近 5 轮 test: 3 / fix: 1 = 3.0× ≥ 2×），所以

## 一、主目标 S-08：这个量早就算出来了，只是没人累加

S-08 在计划里挂了三轮（第 14 轮定位到行：`if (tickAdvanced) state.repaintRequested = true;`）。
按纪律先找「读数该挂在哪」，结果发现比预想的浅：

- `WM_PAINT` 里 `reuseCachedFrame` 早就算好了（`RuntimeShell.cpp:29021`），条件是
  `!repaintRequested && 后备缓冲尺寸相符 && 记分动画不在跑`；
- 它已经被当成参数传进 `recordRuntimeCompletedFrameDiagnostics(state, w, h, reused, submitted)`；
- 而它在那里面只被用来把 map/overlay/sidebar/fog/terrain 的耗时记成 `0`，**从来没有人把它累加**。

所以「这一帧到底改没改画面」在过去只能靠帧间隔反推——而世界加载后 `continuousRuntimeFrame`
（`RuntimeShell.cpp:90274`）让**每个帧截止时间都 Invalidate 一次**，帧间隔恰恰不反映这件事。
这就是 M-03「静止也全量重绘」在数据上一直说不清的原因：不是缺计数器，是缺「复用/重绘」这对数。

改法（`cf1903b`，2 文件 +30 行，不动任何绘制或复用判定）：

| 位置 | 改动 |
|---|---|
| `RuntimeFrameSample` | 加 `bool reusedScene`（注释写明：帧间隔短**不能**证明复用） |
| `RuntimeFrameDiagnostics::observe` | 每帧按 `reusedScene` 累加复用/重绘两数，并维护「当前连续复用数 → 历史最长」 |
| `writeReport` | 落三行：`复用缓存帧 / 重绘帧：A / B`、`最长连续复用帧：N` |
| `RuntimeFrameDiagnosticsRuntime.inl` | `sample.reusedScene = reused;`（一处，参数本来就在手上） |

数字的出口是既有的 `local_data/performance/latest.txt`（会话退出时写），不新增文件、不新增开关。

## 二、诚实标注：仪器接好了，实机读数还没取到（但输出文本已离线验过）

三个数只在**真实会话跑完退出**时落盘。而真实开局通道（M-13 / S-17）仍被
`skirmish-build-smoke-test` 的 `unholy` 段挡着（第 32 轮已把阻塞点后移到 MCV 发放）。
所以本轮**没有实机读数**——但「输出到底长什么样、三个数算得对不对」不用等真实会话，可以离线验：
用同一份头文件编一个 11 帧样本（3 重绘 → 5 连复用 → 1 重绘 → 2 复用），一次跑出

```
采样帧数 / 无效间隔：11 / 0
复用缓存帧 / 重绘帧：7 / 4
最长连续复用帧：5
```

`reused=7 / redrawn=4 / longestStreak=5` 与构造的序列一致，报告三行落在
「全会话绘制更新率」之后、「最长帧间隔」之前。探针是 `/tmp` 下的一次性文件，未进仓库、未进构建。

因此 S-08 的状态写 **measuring**，不是「已完成」——按 §八.4，只加 trace/只把问题收窄都不算完成。
M-03 继续不启动：它的验收是「静止 3 秒内提交帧数下降 ≥80% 且不冻帧」，而那必须先有这三个数做基线，
否则改的就是没量过的判定（漏字段的后果是冻屏，比多画几帧贵得多）。

## 三、清单治理：11 条缺估值条目的真相是 16 条

第 30 轮审计登记「12 条 queue-only 条目缺根因与成本」，第 33 轮只处置 1 条并把窗口顺延到本轮，
计划里写着「不许再顺延第三次」。本轮实测：**实际是 16 条**，其中 5 条是并发会话新登记的
`M-25~M-28` + `EVO-06`，另外 8 条是 fix-plan 条目的**队列侧镜像**（`ON-2-06≈S-08`、
`ON-2-02b≈M-04`、`EVO-03≈M-07`、`EVO-04≈M-06`、`EVO-05≈C-03`、`EVO-13≈M-05`、
`EVO-14≈C-04`、`EVO-15≈C-01`）。审计那 11 条从一开始就没数镜像，所以每次「处置完」都还剩一批。

处置分三类，全部落进 queue（`entry-fields` 门禁现在把这条钉死）：

1. **补估值，留 pending**（7 条）：`ON-5-01` B/中、`ON-5-02b` **A**/中（S-18 的 37GB 就漏在菜单动画
   路径上，30 分钟台架是它唯一的回归门）、`ON-4-02d` B/中、`ON-3-01b` C/中、`ON-2-04b` C/高/复杂、
   `ARM-03` C/中、`EVO-07` **S/A**（双击 `.app` 是用户第一触点，数据根缺失现在是静默失败）。
2. **降 blocked 并写清死因**（4 条）：`U-19 / U-20 / U-21 / U-23`。它们的缺根因是同一个：
   **取证前置未满足**——真实开局取证通道未绿，而离屏路径的空白已被 U-20 自己实测证明不能当证据
   （`decodeMapPreviewImage` 在离屏路径根本不执行）。继续挂 pending 会让它们在第 35 轮第四次顺延。
3. **镜像条目不另立估值**（8 条）：`root_cause/value/cost` 指向 fix-plan 对应 ID，
   避免同一个问题两本账两份估值（这正是上一轮 S-19 估值失真的同类风险）。

## 四、上一轮给 S-19 的成本估错了，本轮推翻

第 33 轮写「低：抽 1 个 pal + 编 1 份旧二进制 + 跑 2 次导出，约 30 分钟（A 级）」。本轮实地探查：

- 本机无 loose `isotem.pal`；它在 `mix_exports/ra2md/isotemmd.mix` 里，而仓库**没有按名抽取 MIX 的
  CLI**（`build-product-arm` 里只有 `concord_tmp_codec_contract` / `concord_terrain_tmp_query_contract`，
  没有 mix 工具），要自己实现 Westwood CRC 才能定位成员；
- 「编一份旧二进制」= 检出 `b2ebc4c^` 的 `MapPreviewExporter.cpp` 与当前树混合，或另建一个构建树整编
  （`CMAKE_OSX_DEPLOYMENT_TARGET` 只活在 CMakeCache，新目录会退回 SDK 版本）。

结论：这不是「30 分钟的简单项」，前置是「MIX 按名抽取 + 第二构建树」。S-19 的 `cost` 改为
**高**、`roi` 由 A 降 B、`complexity` 改**中等**。这条不改状态（仍待修），但改估值——
**估值只写形容词（低/中/高）而不写依据，下一轮就会照着它排错序**，这是 C-02 螺旋的同款病灶。

## 五、第 7 道门禁：字段完整性（可以失败的那种）

`scripts/ledger-check.sh` 从 6 项变 7 项，新增 `entry-fields`：非 done 条目缺
`root_cause / value / cost / roi / complexity / verify` 任一（或写成「待估/未估」）即 `LEDGER-BREACH`、退出码 1。

**它确实会失败**（不是装饰）：把 `M-25.cost` 改回「未估」喂给同一段检测逻辑，输出 `1 M-25`。
这是 S-14 那句「写进规则但没人量的指标一定会失真」的第二次验证——上一轮 `dup-ids` 也是这么加上去的。
