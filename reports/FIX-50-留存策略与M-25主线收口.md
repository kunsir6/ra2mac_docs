## 一、为什么这轮不是修复轮（先把话说清）

计划里 R50 的起手写的是「S-28 挤压原语，单 TU，不动 World.cpp」。本轮没有做，理由三条，都可核对：

1. **子项额度已满**：unit-behavior 4/4（M-25 / M-26 / M-28 / S-28），§六.3 禁止开第 5 个；而
   §附四已写死「M-25 若第 50 轮仍拿不到产品行为变化，整线按 §六.3 三选一收口」。R50 就是那个判定点。
2. **S-28 的调用点不在单 TU**：`advanceRuntimeMoveBehavior` 定义在
   `src/runtime/session/RuntimeSessionWorld.cpp:27776`，`setRuntimeObjectCell` 在 `:13057`——**两个都在
   World.cpp**，而该文件带着并发会话 678 行 WIP（`git status` 11 项，mtime 09:13）。落地要 hunk 级拆补丁 +
   至少两次构建迭代，一旦改出问题回退成本高于本轮的收益。
3. **构建不是增量**：开工时 `ninja -C build-product-arm -n` 要求 **1642 目标全量**（`.ninja_deps` 尾部截断，
   老问题，见项目 MEMORY）。单次全量 4~5 分钟，两次迭代就把本轮 50 分钟吃掉 20%。

这不是「简单区为空就啃深水区」的反面——清偿对象本轮**确实存在**，见第二节的 6.1GB。

## 二、主目标：S-27 回归产物与旧交付包没有保留策略

### 现象（第 46 轮登记，本轮实测）

| 目录 | 轮次登记 | 本轮实测 | 单份体积 | 在门禁里？ |
|---|---|---|---|---|
| `progress/regress/` | 148 个目录 / 3.4GB | **157 个 / 3.5GB** | ~23MB | 否 |
| `dist/.archive/` | 34 个包 / 3.2GB | **42 个 / 3.6GB** | 96MB | 否 |

两个目录都只写不删：`regress.sh` 每次新建时间戳目录、`pack-dist.sh` 每次把旧包 `mv` 进 `.archive`；
`ledger-check.sh` 只管文本账（9 项），不管磁盘账。5 天涨了 0.5GB，按此速率一个月 20GB。

### 改法（两个脚本，+61 行，全在删除侧）

**`regress.sh` → `prune_regress_outputs()`**（跑在打印头部之后、执行用例之前）

- 保留 = **每天首跑**（目录名前 8 位 `YYYYMMDD` 分组取第一条）+ **最近 20 次**；
- 删除只对**严格匹配 `YYYYMMDD-HHMMSS`** 的目录生效——同目录下的 `known-red.tsv` 等文件一律不碰；
- 本次运行的 `$STAMP` 显式跳过（即使它还没落盘）；
- 打印一行 `pruned N 次历史产物`，删了多少当轮可见。

**`pack-dist.sh` → `prune_archive()`**（跑在归档旧包之后、组装新包之前）

- `.archive` 只留 `ls -1t` 最近的 **5** 个；
- 只删已注销 LaunchServices 的归档副本，保留 5 个是为了回退时还拿得回上一版。

两处都是纯 bash（无 grep/sed，避开本机 shim；`set -u` 下空数组不展开），`pack-dist.sh` 是
`set -euo pipefail`，所以判断用 `if` 而不是 `[ ] && echo`。

### 判据（怎么验的，不是「看起来对」）

1. `bash -n` 两个脚本语法通过；
2. 跑一次真回归 → `pruned 129 次历史产物`；目录数 **157 → 25**（20 次 + 5 天各一个每天首跑），
   `du` **3.5GB → 516MB**；`known-red.tsv` 仍在（1921 字节）；
3. 跑一次真打包 → `pruned 37 个旧归档（保留最近 5 个）`；包数 **42 → 5**，`du` **3.6GB → 481MB**；
   新包 `--smoke-test rc=0`、`arch -x86_64 … --smoke-test rc=0`；
4. **合计释放 6.1GB**。

### 为什么可以删（§五.5 要求的「靠什么兜住」）

- 每轮回归的**结论**已经落在两处长期资产里：`report.md` 的关键行进 `progress/RUNLOG.md`，定性进
  `reports/FIX-NN-*.md`。被删的是同一结论的原始日志副本，重跑一次 40 秒即可再生。
- 旧包已从 LaunchServices 注销（`pack-dist.sh` ①步做），删掉不影响图标/名字解析——
  这条是本项目踩过的坑（同 bundle id 的多份拷贝会参与解析）。
- 保留窗口取「每天首跑 + 最近 20 次」而不是「最近 N 次」，是为了跨天回看时每天至少有一份可比对的基线。

## 四、M-25 主线整体收口（§六.3② → 判 blocked）

**账目**：unit-behavior 子项 **4/4 已满**（M-25 / M-26 / M-28 / S-28），已用 **3 轮**
（R48 重排、R49 方案，加上 R50 判定）；产品行为变化 **0 次**。

**三次尝试的实测（全部是负结果，这才是判 blocked 的依据）**

| 轮 | 改法 | 结果 |
|---|---|---|
| R44 | 解除寻路层对友军步兵格的否决 | `12E1_2MTNK_tank_first` 打红 `arrival_timeout` |
| R48 | 只放行「停着的」友军步兵 | 同一处仍红——**在规划时刻问了落位时刻的性质** |
| R49 | 把挤压原语挂在寻路结果侧 `applyRuntimeMovePathResult` | 三条冒烟 **零触发**，接缝错，整文件回退 |

**死因（已排除什么 / 还缺什么）**

- 已排除「判别式不够窄」：R48 收窄到「只放行停着的步兵」仍打红，问题不在判别式的精度。
- 已排除「接缝在寻路结果侧」：R49 用 `CONCORD_SQUEEZE_TRACE=1` 在 compactgroups / command / skirmishbuild
  三条冒烟里**一次都没命中**，说明载具 commit 进格不经过那个分支。
- **还缺的是**：`advanceRuntimeMoveBehavior` 里「载具即将 commit 进格」那一步的**读数**——
  目前不知道 `runtimeGroundBodyTransitionAdmission` / `runtimeCanEnterAndCrushCell` 在这条路径上谁是终局否决。
  一条读数（把两个判据各自打一个布尔 + 目标格上的步兵 id）就能定，但它要在 World.cpp 里改。

**结论（按 §六.3②）**：整线判 **blocked**，理由=「前置工作全都压在并发会话仍有 WIP 的那个 TU 上，
且已有三次判别式/接缝被实测否定」。**S-28 随线移出**到 `progress/deferred.md`，重开条件写在那里。

**代价（写清）**：载具被友军步兵堵在终点前这个**用户实测确认**的缺陷继续存在，且不在任何门禁里
（S-24 也因此继续 blocked——判据存在但是未跟踪文件）。这是真实的产品差距，不假装已修。
