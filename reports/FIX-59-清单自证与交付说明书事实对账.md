## 二、S-32：为什么「引用存在」这件事要分两侧查

R51 加 `refs-head` 的动机写得很好：「R50 把那条未跟踪引用记成悬空引用但没法治，
因为旧检查判的是工作区」。但它只补了一半：

| 侧 | 旧门禁 | 量什么 |
|---|---|---|
| `fix-plan.md` | `refs-head`（第十一项，R51） | 表里 `reports/*.md` 引用必须在 docs HEAD 内 |
| `queue.json` | **无** | — |

本轮我就是在这个缺口上踩的：把三条本轮尚未入库的报告写进 queue 的 `reports` 字段，
`ledger-check.sh` 十一项全绿——因为它根本不看 queue 的引用。

**改法**（`scripts/ledger-check.sh`，+22 行）：新增第十二项 `refs-in-queue`，遍历
`tasks[].reports` / `tasks[].report`，剥掉反引号与锚点后逐个 `git cat-file -e HEAD:<path>`，
不存在即 `LEDGER-BREACH`。与 `refs-head` 同一判据（判 HEAD 而非工作区），否则本地有、干净树没有
的那一类还是查不出来。

**为什么不在同一轮把两条合成一条**：`refs-head` 是 grep fix-plan 的裸字符串匹配（含
`reports/…png`），`refs-in-queue` 是 JSON 字段遍历，判据相同、取数不同；合成一条会让报错定位
从「哪一行」退化成「某一侧」。合并是后续可选的重构，不进本轮。

## 三、S-33：交付物的说明书是「事实」，事实过时就是 bug

`dist/README.txt` 的源是 `ConcordRTS/packaging/README-dist.txt`（R55 入库，pack-dist ⑩ 每次覆盖写）。
它被三处推翻过：

| 位置 | 原文 | 事实（判据） | 后果 |
|---|---|---|---|
| 回归现状 | 「共 14 条：13 绿 / 1 known-red / 0 新红」 | R58 起 **15 条**（`13/2/0`）：`20261115-204728/report.md` | 用户手数条数对不上，会以为是包不对 |
| 已知缺口 | 「M-25 的判据 `.inl` 还没进 HEAD，所以这条缺陷不在日常门禁里」 | `782e194` 已入库、`vehiclepass` 已进门禁，**现在是 known-red 第 2 条** | 把「已经有门禁」说成「没有」，反向误导 |
| 数据根搜索顺序 | 「`CONCORD_DATA_ROOT` → 自身/当前目录 → 兄弟目录」 | 包内指针**最优先**（`RuntimeConfigPaths.cpp:188`，R55 只改了代码注释没改说明书） | 用户按说明书设环境变量却无效 |

后两处都不是文字润色，是**会让人按错误步骤操作的**事实错误。三条都在本轮改对，
并把「最后核对：轮次 + hash」写进文件头，下次漂开至少能看出它停在哪。

**根因不是忘了改，而是没有任何东西量它**：`pack-dist.sh` 每次覆盖写它，但从不断言内容；
README 里写的事实分散在 scripts/queue/regress 三处，谁改都不会想到去改它。
这与 S-29（regress 报告不记源码版本）是同一类：**交付物记录了它自己的内容，但没人核对内容与现实**。

但会把一个只改了文档的轮次包装成「新 dmg 版本」）。重出条件：下一轮真有产品代码改动时，
