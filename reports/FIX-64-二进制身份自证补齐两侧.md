# 第 64 轮（修复轮）：二进制身份自证补齐两侧

**轮型：修复轮**（无 brake / 无 attempts≥3 在办 / 腐烂预算未触发 / 距 AUDIT-61 三轮）。
**主目标：S-37** —— 「二进制自证」只查了 WIP 一侧，且用的是错的字段。
伴生小项（同一主目标）：`build-health.sh` 的待办比例分母取错，导致每次增量构建都报 WARN。

---

## 一、根因：判据读错了字段

第 63 轮收口时发现包内自报 `compiled=Nov 15 19:25:24`，而二进制是 00:18 刚链接的，
`regress.sh` 的报告头对这 3.7 小时的落后一声没吭。当时的定性是「只查一侧」——
这一轮落实到代码后，真正的根因比「只查一侧」更前一步：**它查的那个字段本身不是构建时刻**。

```
kRuntimeBuildTimestamp = __DATE__ " " __TIME__
```
`__DATE__/__TIME__` 是 `RuntimeMain.cpp` 这**一个 TU** 的编译时刻。增量构建只改别的文件时，
这个 TU 根本不重编，于是它能比二进制旧几个小时；反过来，只要它恰好被重编，
它又会等于链接时刻（本轮 `--version` 就是 `built=01:27:20 / compiled=01:27:19`，两者只差 1 秒）。
**两种状态都在正常范围内，所以这个字段既不能证明「是这版」，也不能证明「不是这版」。**

WIP 判据当时的写法是 `compiled - HEAD_CT > 5s → +WIP`。它之所以在 R56 抓到过一次
（678 行 WIP 烘进 dist），是因为那次 `RuntimeMain.cpp` 恰好在未提交改动里被重编了——
**是靠巧合工作的**。改成「用任何字段都能稳定工作」的判据，才是这条的实质。

## 二、改法

### 产品侧（`73be404`，+59/−2）
`--version` 多印一行 `built:`，取**本文件的落盘时刻**（`realpath(argv[0])` + `stat` 的 `st_mtime`）。
链接、ad-hoc 重签、打包拷贝三者都会刷新 mtime，而它们正是「产出这份二进制」的动作。

```
built: 2026-11-16T01:28:59
compiled: Nov 16 2026 01:27:19 (版本 TU 编译时刻，增量构建不刷新，仅作下界)
```
两个都印。只印 `compiled` 时，增量构建的二进制会报出一个几小时前的时刻，看着像构建失败——
这就是本轮之前 `--version` 对用户说的那句假话（EVO-07 ① 的全部意义是「这算哪一版」）。
取不到时打印 `unknown`，**不许静默回退成 TU 时刻冒充构建时刻**。

### 脚本侧（`regress.sh`）
判据换成两向，且都只用能稳定工作的信号：

| 方向 | 判据 | 输出 |
|---|---|---|
| 树脏 | `DIRTY_N > 0` | `source <hash>+WIP` + 一行警告 |
| 二进制旧 | `built < HEAD 提交时刻 − 60s` | 一行警告「它不含 \<hash\>，先重建再谈结论」 |

`+WIP` 不再由时刻反推，直接由 `git status --porcelain` 的条数决定——
树脏才是「含未提交改动」的**定义**，时刻只是它的一个（不可靠的）代理。
报告头与 `report.md` 同步改成 `built=… compiled(下界)=…`。

## 三、负向验证（先证它会红）

道具：把二进制 mtime 改到 2026-11-15T12:00（早于 HEAD 提交时刻），再放一个未跟踪文件让树变脏。

```
source  25b6c53+WIP   提交 2026-11-16T00:19:37+08:00   dirty=1   built=2026-11-15T12:00:00   arch=arm64
警告    工作区 dirty=1 个文件，被测二进制含未提交改动 —— 本报告的结论不能直接归给 25b6c53
警告    被测二进制 built=2026-11-15T12:00:00 早于 HEAD 提交时刻 2026-11-16T00:19:37+08:00 约 44377s —— 它不含 25b6c53，先重建再谈结论
```
恢复干净后再跑：`source 73be404 … dirty=0 built=2026-11-16T01:27:20`，零警告。
**两条都先红后绿，不是「加上去就绿了」。**

## 四、伴生小项：`build-health.sh` 的分母取错了

负向验证时顺手照出：`build-product-arm WARN 待办 1/1 超过 30%`。
分母来自 ninja 进度行的 `[3/3]` 右半边——那是**本次剩余**，不是图里目标总数。
只改一个 TU 时它也是 `[2/2]`，于是「待办 100%」每次增量都成立：
**这个告警在正常增量下恒真，等于噪声**，而它的用途恰恰是「看见就说明该怀疑整图脏了」。
分母改为 `ninja -t targets all | wc -l`（实测 3268）：

```
build-product-arm      clean    增量 1/3268
build-product-x86_64   clean    增量 2/3268
```
同时把「待办看起来是全量」从 WARN 升成 CORRUPT（`todo ≥ total 且 total > 200`）——
全量重编（1858 目标）本来就该按「先查 `.ninja_deps`」处理，挂在 WARN 一档会被当成可忽略。

## 五、断言纠正（不计入「已修复」的部分）

原 DoD 写着「**正常构建时 `compiled` 与二进制 mtime 差 <60s**」。这半句是把机制写进了验收：
`compiled` 只要没被重编就必然不等于 mtime，且**这是正常的**。本轮按「让 `built` 成为权威、
把 `compiled` 降为下界」交付，等价于承认原 DoD 的这半句错在「拿 TU 时刻当构建时刻」。
生效的验收条件改为：

- 二进制 mtime 早于 HEAD 提交时刻 >60s → 报告头必须打 WARN（已负向测过）；
- 树 dirty>0 → 必须 `+WIP`（已负向测过）；
- `built:` 与 `stat` 出来的 mtime 逐字一致（实测 `built=2026-11-16T01:27:20` =
  `ls -l` 的 `Nov 16 01:27`，精确到秒）。

## 七、本轮没做什么 / 遗留什么债 / 放弃了什么

- **没做**：`pack-dist.sh` 的 ⑨ 没加「`built` 与 BUILD-INFO 打包时刻 ±10min」这条断言。
  理由：本轮打包时 `built=01:28:59` 正是 pack 时刻，加上去是恒真断言；要让它有意义，
  得先让 pack-dist 不重签（ad-hoc 重签必然刷新 mtime），那是打包链结构改动，单独成轮。
- **遗留**：`compiled` 这个字段仍然印在 `--version` 里，只是加了「仅作下界」的括注。
  彻底的做法是链接时注入构建戳（`-DVERSION_BUILD_STAMP`），但那会让 `RuntimeMain`
  每轮重编——本轮实测这个 TU 只要 1.5s（1164 行），**代价其实很低**，是下一轮可选项。
- **放弃**：M-03（空转重绘）本轮不动。按 §六.5，它已用 2 轮，第 3 轮若无产品行为变化必须换赛道；
  本轮换到「身份自证」正好把它留给「先补逐帧对账」那一轮。
- **放弃**：U-20/U-21/U-23 三条 UI 取证仍然挂「真实开局取证通道」这个前置。本轮没有把
  导航层的自动开局入口做出来，所以三条依旧拿不到读数——这是**第四轮**把这个前置当理由了，
  下一轮应当要么做入口、要么按 §六.4 把它降级。
