## 一、旧顺序为什么错

R68 的收口写下轮起手是两件事：

1. `M-03 空转重绘` 的「最后一次机会」；
2. `U-19 HUD 对账` 之前「先验 `--skirmish-build-smoke-test` 能不能出世界帧」。

第 2 条被写成**一句话的前置验证**，实测它不是验证，是**要新建一条呈现通道**：

| 检查 | 结果 |
|---|---|
| `runRuntimeSkirmishBuildSmokeTest`（`RuntimeShell.cpp:77659`） | 建 `RuntimeWindowState`、部署 MCV、放 10 栋建筑、跑模拟——**全程没有 `CreateWindow`、没有 `WM_PRINTCLIENT`、没有渲染调用**；它的 `renderCheck=0.00ms` 就是因为那段根本没跑 |
| 17 条 smoke 的产物（`progress/regress/20261116-072113/artifacts/`） | 只有菜单页（`menu.bmp`/`skirmish*.bmp`）、载入页（`loadingpages/*.bmp` 14 张）、结果页（`result/*.bmp`）、`attest` 日志 —— **零张世界帧** |
| 与 R67 的载入页通道对比 | 载入页能出帧是因为它**真建了生产窗口**（`CONCORD_LOADING_PRESENTATION_ONLY`）；世界路径没有对应物 |

所以旧顺序的错不在优先级，在**估错了成本**：把「新建一条 B 级可观测性基建」写成「一句前置验证」，
下一步必然是「验一下没出帧 → 又一轮没有产品行为变化」。这与 §七.3 点名的 C-02 螺旋同型：
**问题范围在缩小，估值没变。**

第 1 条（M-03）也不该在本轮起手：它已连续两轮（R63 负结果、R64~R68 未动）没有产品行为变化，
按 §六.5 第 3 轮应当**强制换赛道**，而不是再给它「最后一次机会」。

## 二、三条候选的取证与否决（本轮唯一的实质产出）

本轮最初的三个候选都来自「用户双击后能看见」的清单，逐个证据如下。

### 2.1 FPS 叠加层默认常显 —— 早在 2026-11-12 就修了，是台账里的死结论

`reports/UI-01-正式版观感对账.md` §3.1 写着「`drawRuntimeFpsDisplay` 在每次提交帧后被**无条件**调用
（`RuntimeShell.cpp` L29275/L29347/L29358 三处），正式版没有这个面板 → **要改**」。今日实测：

```
grep -n "fpsOverlayEnabled" src/
src/runtime/host/RuntimeShell.cpp:29315:  if(c.state->config.fpsOverlayEnabled) drawRuntimeFpsDisplay(...)
src/runtime/host/RuntimeShell.cpp:29388:  if(state->config.fpsOverlayEnabled) drawRuntimeFpsDisplay(...)
src/runtime/host/RuntimeShell.cpp:29400:  if(state->config.fpsOverlayEnabled) drawRuntimeFpsDisplay(...)
src/runtime/config/RuntimeConfig.h:88:     bool fpsOverlayEnabled = false;
src/runtime/host/RuntimeMain.cpp:399:    if (argument == "--show-fps") { ... }

```

`git log -S fpsOverlayEnabled` → **`c1ccfe6 2026-11-12 04:28:02 fix: FPS 叠加层改为默认关闭`**。
即 UI-01 出报告的同一天就修了，**没人在 UI-01 上写「已废弃」**，于是它作为「可确证的差异（建议调整）」
在台账里活了 4 天。处置：UI-01 §3.1 就地标废弃（本轮 `docs:`）。

### 2.2 遭遇战第二行的国家列显示「???」 —— 那是 Random 的旗子图形本身

放大取证（`skirmish.bmp` 裁剪 40,55–400,135，3× 最近邻）：

- 第 1 行「Commander」：旗位 = 美国旗，国家列 = `美国`；
- 第 2 行「中等的敌人」：旗位 = 问号图形，国家列 = `随机`。

判定为**零售原样，不是缺陷**，三条依据：

1. `grep -rn '\?\?\?' src/` **零命中**——这个框里没有任何文字绘制路径会输出 `???`；
2. 该框只在 `flagFor()` 返回非空时 `shellBlit`（`RuntimeSkirmishMenu.cpp:3238`），
   否则是空框 → 能看见图形就说明位图加载成功；
3. `flagNameForCountry("Random")` 返回 `rani.shp`（`RuntimeSkirmishMenu.cpp:252`），
   Random 的旗子图形本身就是问号（RA2 的随机国旗）。

也就是说「看起来像缺字」的东西是美术内容。这条**不进清单**——但它是本轮的一个方法论收获：
**截图上的问号要先排除「它是位图」再排除「缺字」。**

### 2.3 放建筑 1.55 秒 —— 读数出自诊断兜底路径，不能当产品缺陷

`--skirmish-build-smoke-test` 报 `placementSearch=1553.58ms`（约 10 次放置，≈155ms/次），
看着像「每放一栋建筑卡 150ms」。查调用面：

| 位置 | 谁在调 | 是否用户路径 |
|---|---|---|
| `RuntimeShell.cpp:77889`（冒烟内） | `buildAndPlace` 在 `placementValid==false` 时兜底找格 | 诊断 |
| `RuntimeShell.cpp:28498` | `resetPreview` 分支里给**多人意图路由器**一个默认格 | 只在 `runtimeUsesGameplayIntentRouter` 为真时 |
| `selectRuntimeReadyPlacement` | 单人对战放建筑走这条 | **不走** `findRuntimePlacementCellNearBase` |

`findRuntimePlacementCellNearBase`（`RuntimeShell.cpp:6797`）是「按半径从地基往外扫」的**兜底**：
它只在「当前格非法 / 需要自动建议一格」时被调用。所以 1553ms 这个数**证不了**用户点放建筑会卡，
只能证明兜底扫描本身慢。要定级必须先有一条读数回答「真实放置路径有没有走兜底、走了几次」。

**处置**：不修、不登记为产品缺陷。读数需求写进本轮报告 §四「遗留」，交给下一轮决定要不要单独成条
（按 §一.6，新增条目必须等价归档一条，不为了一个未定性的疑点挤掉在办条目）。

## 四、本轮没做什么 / 遗留什么债 / 放弃了什么

**没做什么**

- 没有改任何产品代码（本轮源码树 `git diff --shortstat` 为空）。
- M-03 一点没碰——按 §六.5 主动换赛道，不是没时间。
- U-24 只登记方案与验收条件，没有动实现（§七.2：重排轮不许改产品代码）。

**遗留什么债**

1. **世界帧仍然一张都没有**。这是本项目第 5 次撞上「事实的生产者存在但入口不在清单里」的变体——
   前四次（S-08 读数在文件里 / M-13 通道一直在 / S-38 脚本手上已有值 / S-39 入口一直在）
   都是「入口其实有，只是没接进门禁」；这一次不同：**入口真的没有，要造**。下轮别再假设它存在。
2. 「放建筑是否卡 150ms」仍未定性，缺一条「真实放置路径有没有走兜底」的读数。
3. UI-01 的其余 3 条差异（羽化宽度 U-23 / 滑块 vs 箭头 / 蓝鹰是否该在无雷达时出现）仍是证据不足，
   它们和 U-19 卡在同一道门上——这也是 U-24 收益判 A 的理由。

**放弃了什么**

- 放弃了「本轮必出一条产品行为变化」。理由：三条候选在取证阶段全部被推翻，硬做一条就得在
  没有读数的情况下改行为，那是 §八 明令禁止的假完成。代价明确：**这将是连续第 4 轮无产品行为变化**
  （R65 起的 chore/门禁/文档），`rules.commit` 里那条「近 4 轮 fix: ≤1 → 下轮必须产出一条用户可观察的
  产品行为变化」**已经欠账，下轮 U-24 必须真的出图，否则按 §六.3 收口 U 线**。
- 放弃了给「国家列 ???」登记条目：证据指向零售原样，登记只会污染清单。
