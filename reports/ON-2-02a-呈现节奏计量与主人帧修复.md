# ON-2-02a：呈现节奏计量 + 「主人自己的帧被丢弃」修复

2026-11-11 · 自动化轮 · 源码提交见 RUNLOG（`ON-2 呈现层：主人自身帧不再被抢位规则丢弃`）

## 一句话结论

**屏幕"冻住"的主因不是 CGImage 缓存、不是没有失效、不是没有 present，而是 present 之前那道
抢位规则把「当前呈现主人自己」的后续帧全部拒掉了。** 一行判断修掉之后，主菜单的上屏提交从
**1 次/15s** 变成 **200 次/15s**，三帧取证得到三个互不相同的 dibHash 且全部 `match=yes`。

## 计量装置（CONCORD_PRESENT_STATS=1）

新增在 `compat/win32/src/RuntimeWin32CompatUser.cpp`，只计数、不改行为，默认零输出：

| 计数 | 含义 |
|---|---|
| `paints{queue,update,redraw,app}` | WM_PAINT 按**来源**四分：队列合成 / `UpdateWindow` / `RedrawWindow(RDW_UPDATENOW)` / 应用直投。四者之和必须等于总数，否则口径错了 |
| `dirtyMarks` / `merged` | `InvalidateRect`/`RedrawWindow` 置脏次数，以及"置脏时**已经脏**"因而被失效层合并掉的次数 |
| `attempts` / `blank` / `takeover{self,other}` | 进入呈现判定的次数、被空白过滤挡掉、被抢位规则挡掉（再分"挡的是主人自己"与"挡的是别的小控件"） |
| `submits` / `redundant` | 真正调用 `apple::present` 的次数，以及"与上一次提交同窗口/同尺寸/同可见性/采样签名相同"的重复上屏 |
| `rate` / `owner` | 提交速率、屏幕上那一幅画的尺寸 |

退出方式：`CONCORD_PRESENT_STATS_UNTIL_SEC=<n>` 到点打印汇总并 `_Exit`（世界视图的主循环没有
可靠退出路径，与 ON-3-01 的 attest 同一取舍）。

## 三组数字

### ① 主菜单挂机 15s（修复前）

```
paints=201 {queue=201 update=0 redraw=0 app=0} endpaint=201 dirtyMarks=201 merged=0
attempts=203 blank=2 takeover=200 {self=200 other=0} submits=1 redundant=0 rate=0.07/s
```

`paint-window #1 hwnd=... size=1024x640` 是全进程唯一在重绘的窗口，也正是屏幕主人。
**它自己的 200 帧全被拒**：抢位规则写的是"只能被**严格更大**者接管"，而主人与自己面积相等，
`area > gPresentedArea` 恒假。于是进程内部以 13.4 帧/秒画了 201 帧，屏幕只有第 1 帧。

### ② 同一场景修复后

```
paints=200 {queue=200 ...} attempts=202 blank=2 takeover=0 {self=0 other=0}
submits=200 redundant=0 rate=13.33/s owner=1024x640     user 2.89s / 15.58s ≈ 18.5%
```

`redundant=0`：这 200 次上屏**没有一次是重复内容**。也就是说"同一帧被贴多次"在菜单上不存在，
present 层不需要再做合并。

### ③ 游戏内世界 20s（修复后）

```
paints=888 {queue=0 update=887 redraw=0 app=1} attempts=890 blank=2 takeover=0
submits=888 redundant=881 rate=44.40/s owner=1024x640   user 12.36s / 21.03s ≈ 59%
```

世界走的是**相反**的绘制路径：888 次里 887 次来自 `UpdateWindow` 同步旁路（队列合成为 0），
而 44 次提交里有 881 次内容未变——这是帧循环在空转重绘，不是 present 层的问题（见下节分派）。

## 三帧上屏自证（ON-3-01 装置，`CONCORD_ONSCREEN_ATTEST_LIMIT=3`）

```
idx=1 layerHash=0x62361240 dibHash=0x62361240 match=yes
idx=2 layerHash=0x43fc9950 dibHash=0x43fc9950 match=yes
idx=3 layerHash=0x4e30f9e8 dibHash=0x4e30f9e8 match=yes
```

三个**互不相同**的 hash 且逐帧 `match=yes`：屏幕真的连续换了三帧，且每一帧都与同帧 DIB
逐像素一致。修复前这三帧里的后两帧根本到不了 present。

## 为什么这个缺陷能藏这么久

它同时满足"所有既有判据都是绿的"：

- `CONCORD_MENU_DUMP` 导出的是 **DIB**，DIB 每帧都是对的（201 帧全画了）；
- ON-3-01 的 attest 默认 `LIMIT=1`，只验第 1 帧——第 1 帧当然对；
- 进程不崩、不报错、CPU 也在动（13 帧/秒在画），只有"屏幕上的像素"是旧的；
- ON-2-01 当时把"屏幕不动"归因给了 CGImage 缓存（已回退），真正的门在缓存之前。

## 分派给后续任务

| 现象 | 归属 | 判据 |
|---|---|---|
| 菜单 redundant=0、merged=0 | **ON-2-02b 不需要做"脏帧合并"** | 无重复提交可合并 |
| 世界 redundant=881/888、update=887 | **ON-4-03（帧循环）** | 44 次/秒重绘同一画面，应在 tick→脏区阶段就不产生重绘 |
| 与显示刷新对齐（CVDisplayLink/CADisplayLink） | ON-2-02b，且仍排在 ON-4-03 之后 | 没有帧循环时"提交/渲染比"的分母≈0 |

## 局限（未验证）

- `redundant` 用 1/32 像素采样签名（每 4 行 × 每 8 列），是**上界**：小于采样格的局部变化会被
  算成"没变"。反过来不会发生，所以"有没有重复提交"的结论可靠，"重复了几帧"会偏低。
- 只覆盖主菜单与世界两档，遭遇战大厅/加载页仍需 ON-4-02 的合成输入。
- 世界 idle 场景 CPU 从 42–45%（S14a 记录）升到 59%，多出来的部分是 44 次/秒的纹理上传；
  这是"把该上屏的都上屏"的代价，真正的解法是 ON-4-03 让空转重绘不发生。
- 无 Windows 复核：真机上的 `WM_PAINT` 语义由系统负责，本层只是模拟。
