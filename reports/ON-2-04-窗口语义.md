## 一、红叉：从「点了没反应」到退出码 0

### 1.1 根因是注释与代码脱节

`pumpEvents` 里这一段：

```cpp
// 窗口关闭按钮走标准关闭路径：转成 quit，否则点了红叉没反应。
if (event.type == NSEventTypeAppKitDefined) continue;
```

注释说「转成 quit」，代码是 `continue`（直接丢弃）。而真正发生的是：没人实现
`windowShouldClose:` 时，**AppKit 自己把窗口 orderOut** —— 窗口从屏幕上消失，
compat 的 `GetMessageW` 只认 Win32 消息，完全看不见这件事，于是进程继续跑。
用户看到的是「窗口没了，但应用还在」。

### 1.2 改法：复用既有的输入事件通道

`.mm` 拿不到 `HWND`（头文件刻意不含 Win32 类型，见 `RuntimeAppleWindowSurface.h` 文件头），
唯一被允许的跨界方式就是 `InputEvent`。所以关闭事件也走这条通道，边界上不新增约定：

```
点红叉 → windowShouldClose:（delegate 拦下，返回 NO）
       → InputEvent::Kind::Close
       → compat 的 appleInputDispatch
       → SendMessageW(WM_CLOSE)
       → DefWindowProc → DestroyWindow → WM_DESTROY
       → 窗口真的没了 → PostQuitMessage(0) → GetMessageW 返回 0 → 进程退出 0
```

三个设计取舍：

- **`SendMessageW` 而不是 `PostMessageW`**：要让「窗口到底关没关」在这一刻可判定。
- **`PostQuitMessage` 只在 `!IsWindow(target)` 时发**：不违反 Q-11 的结论。Q-11 否定的是
  「DefWindowProc 里任何窗口销毁都代劳 quit」（子窗口、smoke 自建的 STATIC 壳会被误杀）；
  这里是「用户明确关掉了呈现窗口」这个具体事件的处理者，而且先验证了销毁已发生。
  产品将来若在 WM_CLOSE 里弹确认框阻止销毁，`IsWindow` 仍为真，就不会退出——语义正确。
- **`gInputSink == nullptr` 时返回 YES**：离屏 smoke 没有输入接收方，硬拦会让窗口变成关不掉的死窗口。

### 1.3 一个差点让自测假成功的坑

自测 `CONCORD_CLOSE_SELFTEST=1` 用 `performClose:`（与真实点击同一条路径）。
第一版直接放在 `present` 末尾，日志打出了 `close self-test: performClose` 却毫无效果：
窗口关了、进程还在跑，后面继续出 frame 30。

原因：compat 侧的 `setInputSink` 是在 `present` **返回之后**才调用的（它要用刚呈现的窗口
做 context）。第一次 `present` 时 sink 还是空，delegate 走了「没人接就放行」的分支。
改成 `if (!gCloseSelfTestDone && gInputSink != nullptr)`，等 sink 就绪再注入。

**教训**：自测"打了日志"不等于"走到了被测分支"。

### 1.4 验证

```
arm64 : [cocoa] close self-test: performClose   →  EXIT=0（不再出现 frame 3）
x86_64: 同上（Rosetta）                          →  EXIT=0
```

## 三、系统全屏：确认不可用，并显式禁用

这是本轮最重要的否定结论。

### 3.1 三条证据

| 尝试 | 结果 |
|---|---|
| 默认 `collectionBehavior` + `toggleFullScreen:` | `windowWillEnterFullScreen` 触发（styleMask=0xf），`windowDidEnterFullScreen` **永不触发**，90s 超时 |
| 显式设 `FullScreenPrimary` + 切换期间把 pumpEvents 的 run loop 从 2ms 放宽到 20ms | 同上，仍然只有 `willEnter` |
| 设 `FullScreenNone` | `willEnter` 不再出现，自测 61 帧后报 unsupported 并正常退出 0 |

### 3.2 根因与结论

全屏切换是 AppKit 的**动画状态机 + Space 切换**，需要 `[NSApp run]` 的完整生命周期持续驱动。
本项目的主循环是 compat 自己的 `GetMessageW`（每轮只给 2ms 的
`nextEventMatchingMask`），从不跑 `NSApp run` —— 那是整个兼容层的前提（Q-06 起就定了），
不能为一个窗口形态去动它。

**所以系统全屏（进入独立 Space）在此架构下不可用。**

### 3.3 为什么必须显式禁用，而不是「不支持就算了」

实测 `NSWindowCollectionBehaviorDefault` **挡不住**：全屏照样开始（`willEnter` 仍然触发），
照样走不完。也就是说，如果不设 `FullScreenNone`，用户按 Ctrl+Cmd+F 或点绿灯，
窗口会卡在「正在进入全屏」——比没有这个功能更糟。

现在绿灯是 **zoom**（同步 `setFrame`，纯窗口操作，不需要 run loop），点了只会把窗口
放到屏幕可用区域最大，不会卡住。这是当前架构下能给的最接近「全屏」的东西。

已记 **ON-2-04b（blocked）**，两条可选路线写在任务里，不在本轮展开。

## 四、顺带修掉：contentsScale 与 backingScaleFactor 脱节

跑 ON-2-03 的缩放自测时发现 `result=fail`，但四项里三项都是 yes。加诊断后看到：

```
# scale-test frame=1741x1143 view=1741x1111 contentsScale=2.0 backing=1.0 ... result=fail
```

`gView.layer.contentsScale` 只在**建窗口时**从 `backingScaleFactor` 抓一次，之后窗口的
backing 变了（系统状态、显示器切换、启动方式都会影响），layer 停在旧值上，两者脱节。
脱节的后果是画面要么糊、要么按错误倍数解释。

改为每帧同步（代价一个浮点比较 + 变化时才提交事务）：

```
# scale-test frame=1741x1143 view=1741x1111 contentsScale=1.0 backing=1.0 ... result=pass
```

**注意**：pass 的含义是「layer 跟随 backing」，不是「Retina 正确」。
本次运行里 `backing=1.0` —— 窗口没有以 Retina 模式运行，这与 PKG-01 记的
`retina_scale_measurement_trap` 是同一个现象（启动方式决定 backing）。Retina 的最终验收
仍需人工双击 `.app`。这条在报告里必须写清楚，不能让 `result=pass` 冒充「Retina 已达标」。

## 五、最小化：未自动验证

`present` 里已有 `if (gWindow.isMiniaturized) [gWindow deminiaturize:nil]`（切界面时自动恢复）。
但「最小化 → 恢复后保留最后一帧」没有自动取证：

- 用户点 Dock 图标恢复是 AppKit 的直接行为，**不经过本层代码**，本层没有可插入的判定点；
- layer 内容不会因最小化被清空，这是 AppKit 的保证，但没有本项目的实测证据。

所以这条**保持未验证**，不写成「已完成」。人眼验收（ON-3-03 剧本）里可以顺手确认。
