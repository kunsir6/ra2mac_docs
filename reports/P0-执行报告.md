## 二、关键发现：阻塞面比预期小得多

原方案估计「产品外壳要重写 60–70%」。实测结果推翻了这个估计：

**产品构建的编译图里只有 4 个 `win32/` 源文件**（其余 21 个全在 `if(WIN32)` 内被自动跳过）。整个产品可执行文件失败的是 **12 个翻译单元 / 共 120 个**（10%），不是整个 UI 层。

| 指标 | 原估计 | 实测 |
|---|---|---|
| `win32/` 路径下文件 | 97 文件 | 97 文件（25 `.cpp` / 42 `.h` / 28 `.inl` / 2 `.hlsl`） |
| `win32/` 源进入产品编译图 | 25 个 `.cpp` | **4 个 `.cpp`**（其余 21 个被 `if(WIN32)` 跳过） |
| 产品目标 TU 总数 | — | 120 |
| 编译失败 TU 数 | 数十个 | **12 个（10%）** |
| 需要重写的 UI 菜单 | 全部 | **3 个** |

原因：`.inl` 诊断文件与 `win32/` 实现大多挂在 `if(WIN32)` 下的独立 static library 上，macOS 上根本不创建。Windows 依赖主要是通过**头文件传染**（42 个头 + 28 个 `.inl`）进共享 TU 的。

## 四、跨平台一致性：还差一步

**重要澄清**：`concord_game_world_deterministic_hash_smoke` 是**自一致性 + 字段敏感度**测试，没有内置金标准哈希。它验证的是「哈希稳定、容器顺序规范、每个字段都参与哈希」。

所以 10/10 通过证明的是**内核逻辑完整**，**不等于**与 Windows 逐字节一致。

好消息：该测试会**打印**哈希值，可以直接做跨平台对照：

```
GameWorld deterministic hash smoke passed: hash=1585785091039784157
```

macOS 已捕获：`1585785091039784157`（`concord_game_world_deterministic_hash_smoke` 与 `concord_production_core_hash_smoke` 两个独立目标输出一致）。

**待办（需要 Windows 机器）**：在 Windows 上构建同样的 portable core，跑一遍采集脚本，然后对比。

## 五、已交付的基线工具

| 文件 | 作用 |
|---|---|
| `scripts/capture-core-baseline.sh` | 任意平台采集基线 → 单文件 JSON（OS/架构/编译器/CTest 计数/各 smoke 退出码/权威哈希） |
| `scripts/compare-core-baseline.py` | 对比两份 JSON，差异即退出码 1；已用「自比较」和「篡改哈希」双向验证过 |
| `baseline/core-macos-x86_64.json` | 本机已采集的基线（10/10 通过，哈希 `1585785091039784157`） |

### Windows 侧要执行的三条命令

```powershell
# 1. 构建 portable core（沿用现有 Build-Game.ps1 的工具链，只换选项）
cmake -S . -B build-core-win -G Ninja -DCONCORD_PORTABLE_CORE=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-core-win

# 2. 采集基线（Git Bash 中运行）
./scripts/capture-core-baseline.sh ConcordRTS/build-core-win baseline/core-windows-x64.json

# 3. 与 macOS 对照
python scripts/compare-core-baseline.py baseline/core-windows-x64.json baseline/core-macos-x86_64.json
```

**期望结果**：`一致：哈希、测试计数、退出码全部匹配。`
