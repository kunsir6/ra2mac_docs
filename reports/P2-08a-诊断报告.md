# P2-08a 诊断报告：RuntimeShell 与全项目 Win32 依赖拓扑

> 任务：P2-08 子步骤 a（**只诊断，不改代码**）
> 日期：2026-11-10
> 结论先行：这一轮的产出不是「怎么改 RuntimeShell」，而是**证明了不该去改它**。

---

## 0. 三句话结论

1. `RuntimeShell.cpp` 不是「89k 行全要改」：950 个函数里只有 230 个触及 Win32（占 42.5% 的行）；而这 42.5% 里又有 72.7% 落在 13 个 smoke/probe 函数内，**真正的运行路径只剩约 10.3k 行**。
2. 但「逐文件重写」也不是最优解：整个 macOS 产品构建图 **445 个 TU 里只有 42 个（9.4%）触及 Win32**，且它们合起来只需要 **74 个 Win32 API + 25 个类型**。
3. 因此建议把 P2-08 的目标从「改 RuntimeShell」改成「建一个 74 函数的 Win32 兼容层」——**既有源码改动接近 0**，Windows 侧逐字节不变。

---

## 1. 方法与口径

- 全部统计用 `python3` 直接读文件完成。**本机 `grep`/`sed` 是被代理的 shim，多模式与 `-c` 会静默返回空**（队列 `rules.note_grep` 已记录），本轮再次确认：`Grep` 工具对 `^\s*#\s*(if|ifdef)` 返回 "No matches found"，而 python 直接 `data.count('#if')` 得到 0 —— 两者恰好一致，属真值而非漏报。
- 函数切分：自写括号配对扫描器，先把注释/字符串替换为等长空白（保持偏移量不变），再对每个 `{` 记录「上一个 `;` / `}` 之后」作为签名区，配对 `}` 时若签名含 `(` 且非 `namespace/class/struct/enum` 则判为函数定义。识别出 **950 个函数定义**，覆盖 90937 行（含函数间空行）。
- Win32 判据：只认**类型名与 API 名**（`HWND/HDC/RECT/POINT/...`、`SelectObject/BitBlt/DrawTextW/...`），不认 `get/set/size/id` 这类成员名 —— 后者在 89k 行里全量出现，会把噪声放大到无意义（首版曾得出 `id:5853` 这种数）。
- 产品构建图口径：`ninja -C build-product-mac -t commands` 抽 `-c <src>` 去重，得 **445 个 TU**。

## 2. 事实 A：RuntimeShell.cpp 的函数级拓扑

| 指标 | 数值 | 占比 |
|---|---:|---:|
| 文件行数 | 89,114 | — |
| 函数定义数 | 950 | — |
| 触及 Win32 符号的函数 | 230 | 24.2% |
| 触及 Win32 的行数 | 37,888 | **42.5%** |
| 纯 std/逻辑函数 | 720 | 73.8% |

**关键**：`RuntimeShell.cpp` 里 **零条 `#if` / `#ifdef` / `#pragma`**（`data.count('#if') == 0`）。它是纯粹的 Win32 单体文件，从未被条件编译过。

这一条直接否掉了队列里 P2-08 子步骤 b 的原设计：

> ~~"把这些 include 移进 `#ifdef _WIN32` 块，先让 macOS 编译推进到『未声明标识符』阶段"~~

原因：文件里 42.5% 的行本身就在用 `HDC`/`RECT`/`SelectObject`。把 include 裹进 `#ifdef` 后，剩下的 42.5% 会**每一行都报错**，得到的是噪声而非"错误全集"。真正该先做的是**把整块代码排除掉**，不是把 include 排除掉。

**可达性证据链**（不是推测）：

- 声明：`src/runtime/host/RuntimeShell.h:249–285` 共 30 条，其中上表 5 个 smoke 入口逐一在一行内声明，**无任何条件编译**（该文件 308 行、零 `#if`）。
- 分派：`src/runtime/host/RuntimeMain.cpp` 是一串扁平 `if (commandLine.xxxSmokeTest) return runRuntimeXxxSmokeTest(config);`
  - `:869` render、`:873` interaction、`:877` resultPresentation、`:947` command、`:951` build。
- 入口：同文件 `:1008 #ifdef _WIN32 / :1025 #else int main(...)` —— **项目上游早就为非 Windows 留了 `main()`**，`RuntimeMain.cpp.o` 在 `build-product-mac` 里确实已构建成功。

**结论**：这 5 个函数只经 CLI 开关可达，用 `#ifdef _WIN32` 包裹「定义 + 声明 + 分派」三处是**零语义变更**，一次拿掉 23,972 行（占 Win32 面的 63%）。

**剩余真实移植面：10,326 行 / 217 个函数。** 热点前几名是 `RuntimeWindowSession`(1339)、`prewarmRuntimeFirstFrameResources`(785)、`drawRuntimeSidebar`(560)、`drawRuntimeCampaignScoreOverlay`(295)、`drawRuntimeRadarTerrainCache`(289)。

## 6. 事实 E：GDI 四子面（决定兼容层工作量与风险）

| 子面 | 调用次数 | API 数 | 主要项 | 实现难度 |
|---|---:|---:|---|---|
| 对象管理 | 1,133 | 7 | `SelectObject` 392 / `DeleteObject` 258 / `DeleteDC` 131 / `ReleaseDC` 106 | 低（句柄表 + 引用计数） |
| 文本 | 579 | 8 | `SetBkMode` 60 / `SetTextColor` 59 / `DrawTextW` 38 / `CreateFontW` 17 | **高**（字体度量） |
| 矢量绘制 | 473 | 10 | `LineTo` 112 / `MoveToEx` 90 / `FillRect` 74 / `CreatePen` 51 / `SetPixelV` 33 | 中（光栅化算法） |
| 位图传输 | 135 | 6 | `CreateDIBSection` 75 / `BitBlt` 34 / `StretchDIBits` 8 | 中（DIB 布局） |

> 注：`SelectObject` 在「对象管理」与「文本」两族各被统计一次，故四族之和（2320）大于去重后的调用数。

**唯一真正的高风险点是文本**：项目有像素金标准测试，而 Windows GDI 的 `DrawTextW` 字体度量（行高、字宽、`DT_*` 折行）依赖系统字体与 ClearType 提示，用 CoreText 复现不可能逐像素一致。

但量级允许规避：`DrawTextW` 只有 38 处、`CreateFontW` 只有 17 处，集中在 HUD/结算/菜单文字；游戏内文字走的是项目自己的 `WestwoodFontCodec` 位图字体。**可先让兼容层的 `DrawTextW` 走「近似但确定性」的位图字体后端**，并把像素级文本断言保留在 Windows 侧。

## 7. 事实 F：项目已有的可移植接缝

- `src/runtime/window/RuntimeSoftwareWindow.h` 定义了 `SoftwareWindow` / `SoftwareWindowEvents` / `SoftwareWindowOptions` 抽象，外加 `presentation::FramePresenter`。
- `src/runtime/window/sdl3/RuntimeSdl3Window.cpp`（238 行）已实现该抽象，但它是 **Windows 专用形态**：`#if defined(CONCORD_HAS_SDL3)` + `#include <windows.h>` + 运行时 `LoadLibraryExW("SDL3.dll")` + `GetModuleFileNameW`，且强行要求 `GetCurrentVideoDriver()=="windows"`。
- 消费方只有 4 个文件（`RuntimeSkirmishMenu.cpp`、`RuntimeSkirmishSoftwareWindow.inl`、`RuntimeSecondWindowContract.inl`、`RuntimeSoftwareWindow.h`）。

**含义**：窗口抽象已经存在，但**主路径没走它**——`RuntimeShell.cpp` 走的是 `RuntimeWindowHostWin32`。所以 SDL3 后端是「第二个窗口」实验，不是主窗口。macOS 侧需要的是**同一抽象的静态链接版本**（约 250 行，照抄现有实现去掉 LoadLibrary 分支）。

## 8. 三条路线对比

| | A：逐文件 port（原队列 P2-04…P2-09） | **B：Win32 兼容层（推荐）** | C：只做 headless |
|---|---|---|---|
| 改动既有文件 | 42 个 TU、含 89k 行单体 | **0～3 个**（只加 include 路径与 1 处条件编译） | 多 |
| 新增代码 | ~10.3k 行改写 | ~2.0–2.5k 行（74 函数 + 25 类型 + SDL3 窗口后端） | 中 |
| Windows 回归风险 | 每一处改写都是风险点 | **零**（shim 只在非 Windows 进 include 路径） | 零 |
| 可验证性 | 逐个 TU 编译过，直到最后才能链接 | 兼容层可独立单测（自建最小可执行） | 只有 CLI |
| 能否跑 GUI | 能（重写后） | 能 | 不能 |
| 主要风险 | 改坏 89k 行里的隐式语义 | 字体度量 / BitBlt ROP 保真度 | 产品不成立 |

**推荐 B**。理由：改动面从「42 个 TU / 10.3k 行」压到「1 个新目录」，且 Windows 路径天然零回归——这正好符合用户「保留多平台编译能力」的原始约束。

## 10. 风险与未知（必须承认的部分）

1. **字体度量保真**：`DrawTextW` 的行高/字宽若与 Windows 不一致，所有含文字的像素金标准测试在 macOS 上必然失败。对策：文本族排在最后、先确定性后保真、像素断言只在 Windows 跑。
2. **`BitBlt` ROP 语义**：项目用到 `BitBlt` 34 次，若含 `SRCAND`/`SRCINVERT` 等非 `SRCCOPY` 模式，兼容层要做掩码运算。**未逐点核对 ROP 参数**，属待查项。
3. **`wchar_t` 宽度**：macOS 是 4 字节、Windows 是 2 字节，全仓库 111 个文件用 `std::wstring`。兼容层的类型 shim 只能对齐 API 签名，**不改 `std::wstring` 本身的语义**；跨边界（文件/网络/存档）必须显式转 UTF-8。这是独立于本报告的风险，建议单列任务。
4. **`CreateFileW`/`WriteFile`**（`RuntimeAtomicFile.cpp`）：兼容层要么实现，要么改走 `std::filesystem`。前者会引入 Windows 路径语义（`\\?\`、盘符），后者改源码。**建议单独决策**，暂列未决。
5. **`GetModuleHandleW`/`GetModuleFileNameW`**：macOS 无对应概念，需用 `_NSGetExecutablePath` + 伪 module 句柄。
6. 所有"行数"是**代码行**，不含空行/注释的精确去除；用于估算规模足够，不作为验收口径。
