## 2. 污染机制（精确到一行）

`RuntimeSelectedPathRaster.h` 第 3–9 行依次 include `<algorithm> <array> <cstdint> <cstdlib> <list> <unordered_map> <vector>`。

前四个和 `<unordered_map>`、`<vector>` **在 RuntimeShell.cpp 文件顶部已经包含过**，include guard 已置位，在 L21848 处是 no-op。唯独 **`<list>` 从没在文件作用域出现过**，于是：

- 它在 L21848 被引入时，当前作用域是匿名命名空间内部；
- `<list>` 里 `_LIBCPP_BEGIN_NAMESPACE_STD` 展开的 `namespace std { ... }` 就落进了匿名命名空间，注册成 `(anonymous)::std` 的一份副本；
- 此后文件里每一处 `std::` 都二义，`31958 ambiguous + 18977 undeclared + 11343 no matching function` 全从这里长出来。

## 3. 对照实验：单行值 72,645 条错误

在 `/tmp/b0probe/` 造副本编译（不动仓库；`tests/` 用软链保证 `#include "../../../tests/..."` 可解析），编译选项与 `build.ninja` 一致，仅 `-O3→-O0` 加 `-fsyntax-only -ferror-limit=0`：

| 变体 | 内容 | 错误数 |
|---|---|---|
| A | 改造前的原文（无 `<list>`、shim 为 S2 时的 1617 行） | **73,291** |
| B | 原文 + 在 `namespace {` 前补两行 include（当时旧 shim） | 385 |
| C | 当前工作区（含 `#include <list>`，当前 shim） | **7** |
| D | 当前工作区**删掉**那一行 `<list>`（隔离变量） | **72,652** |

`C` vs `D` 是干净的隔离实验：同一份 shim、同一份源码，只差一行，差 **72,645 条错误**。

`B` 的 385 曾经误导过我一次——它不是「命名空间问题的残留」，而是**旧 shim 缺声明**造成的：353 条 `use of undeclared identifier`（VK_F13–F22 占 137、UnregisterClassW 27、GetKeyState 24、WS_EX_* 31、WHEEL_DELTA 12）+ 10 条 `unknown type name` + 11 条 `std::max/min` + 3 条 `wchar_t` 断言 + 3 条 `CreateFileW` + 3 条 `auto` 宽度 + 2 条其他。**它们全是真实缺口，与 b0 无关。** 换句话说：b0 修完的那一刻，问题就从「命名空间风暴」退化成「缺声明的清单」，而那份清单 S5 已经在填。

## 5. 并发写入：本轮最有价值的工程发现

采样到的文件时间戳：

| 文件 | 时间 | 变化 |
|---|---|---|
| `compat/win32/include/mmsystem.h` | 03:03:11 | 未知增量 |
| `src/runtime/host/RuntimeShell.cpp` | 03:00:36 → 03:06:53 | `+#include <list>`、6 处 `std::max` → `std::max<LONG>` |
| `compat/win32/include/windows.h` | 03:07:01 → 03:08:39 | 1617 → 1948 → 1961 行 |

`git status` 里同时出现 `RuntimeDiplomacyPage.inl`、`RuntimePlayerHotkeysUi.inl`、`RuntimeChatTextSmoke.inl` 等 9 个新修改——即 T-01、T-02 也在被同步推进（`RuntimePlayerHotkeysUi.inl` 的 `wchar_t` 分支写得比我打算写的更严谨：POSIX 侧按码点转换并把 U+10000 以上拆成代理对，而不是简单删掉 `static_assert`）。

后果，按严重程度排：

1. **同一轮的两个数字会互相矛盾**。我 03:00 测到 385、03:07 测到 22、03:12 测到 0，三次都是真的，因为中间 shim 和源码在变。任何「改造前后对比」必须固定时间窗并记录文件 mtime，否则会得出错误结论（我这份报告的 385 就差点被误读成「命名空间修复只完成 50%」）。
2. **两个进程同时构建会互相踩**。`build-product-mac/` 是共享的，`.o` 和 `.ninja_deps` 会被并发写。**这也是本轮我放弃跑全量构建的原因**——不是怕慢，是怕污染对方正在用的构建目录。
3. **会互相覆盖改动**。若两边都在同一文件上做原子替换，后写者赢，先写者的改动静默消失。

建议（下轮执行前先做）：在 `progress/` 下加一个 `LOCK` 文件约定——轮次开始时 `mkdir progress/.lock` 成功才继续，结束删除；失败则本轮直接转 diagnose-only 并记录「检测到并发实例」。这条应该写进 `rules`，因为它是流程问题，不是代码问题。

## 7. 诚实边界

- 只验证了 **RuntimeShell.cpp 这一个 TU**，不是 `concord_runtime` 整体。**链接层面完全未验证**——`concord_runtime` 是整体可执行文件，其他 TU 失败仍会让链接失败。
- 未跑全量构建（理由是避开共享构建目录的并发冲突，见 5.2）。
- `-O0` 编译通过不等于 `-O3` 通过，也不等于运行正确。
- 无法在 Windows 上复核 `std::max<LONG>` 与 `<list>` 这两处改动（本机无 Windows）。`std::max<LONG>` 在 Windows 上等价于 `std::max<long>`，语义不变，但这是推理不是实测。
