## 二、后端为什么不是 SDL3

任务标题写的是「SDL3 音频后端」，本轮改成了 **AudioToolbox / AudioQueue**。四条依据：

1. 本机无 SDL3：`build/dependencies/sdl3-3.4.16/` 不存在，`/usr/local/lib` 与 brew Cellar 均无。
2. `cmake/Sdl3Window.cmake` 明写 loader「verified on Windows only」，且「no automatic dependency
   installation is performed」——**不允许自动下载**。
3. P3-01（SDL3 窗口 host）已 superseded，窗口侧最终走纯离屏 S7。「与 P3 共用依赖」这个前提消失了。
4. 多平台方案 §P4 原文即允许 CoreAudio 路线：「优先 SDL3 Audio……需要低延迟再上 CoreAudio」。

**代价可控**：换回 SDL3 只需替换 `src/audio/apple/RuntimeAppleAudioOutput.cpp` 一个文件，
`AudioOutput` 接口与未来的 7 个工厂一行都不用动。

## 三、分层：底座 / 工厂 是两件事

```
        ┌─────────────────────────────────────────┐
        │ 产品代码（5 个设备接口，签名不变）        │
        │  RuntimeLegacyWaveDevice / MenuMusic…    │
        └───────────────┬─────────────────────────┘
                        │  P4-01b 才接
        ┌───────────────▼─────────────────────────┐
        │ 7 个 createXxxWin32 工厂（Apple 实现）    │  ← 本轮没做
        └───────────────┬─────────────────────────┘
                        │
        ┌───────────────▼─────────────────────────┐
        │ RuntimeAppleAudioOutput（本轮）           │
        │  decodeWav()      → DecodedPcm            │
        │  AudioOutput      → AudioQueue 输出流     │
        └─────────────────────────────────────────┘
```

分层的理由：解码和设备各自能用硬编码断言测；工厂只负责「会话语义」（谁拥有、替换时关不关上一个、
析构要不要停），那是另一类错误。混在一起时，一个静音可以被三种原因解释，测不出来。

**接口语义（b 轮别推翻）**

- `play()` 是**替换式**：先停并释放上一条流，再从零开始。对应被替换的 MCI `close → open → play from 0`。
- 内部**拷贝**一份 PCM。调用方按 MCI 语义「命令返回即交接」，会立刻丢掉 `DecodedPcm`。
- 循环播放在补喂回调里回绕，不重启队列。
- `framesConsumed()` 是**真实进度**（回调里按 `mAudioDataByteSize` 累加），不是"已提交"。
- 空缓冲显式拒绝。否则「播完了」和「从来没数据」长得一模一样。

## 四、素材实测：本项目全是 IMA ADPCM

扫了 152 个散装 WAV（`RA2/Taunts` 72 + `ConcordRTS-GameData` 90）：

| 格式 | 数量 | 说明 |
| --- | --- | --- |
| IMA ADPCM（tag 0x11）/ 22050Hz / **单声道** | 72 | Taunts |
| IMA ADPCM（tag 0x11）/ 22050Hz / **立体声** blockAlign=1024、samplesPerBlock=1017 | 10 | 菜单音乐 |
| IMA ADPCM（tag 0x11）其它 | 62 | GameData 其余 |
| PCM（tag 1） | **0** | —— |

也就是说：**只做 PCM 解码器 = 一句都听不到**。第一版我就只做了 PCM，真素材直接返回
"unsupported codec"。当时最容易的处置是「素材太老，先跳过」——那会让 b 轮收工后得到
"链接通过、完全静音"的假成功。

## 五、两个「错的期望值」（实现是对的，断言是错的）

1. **立体声 nibble 不是按帧交错**。标准布局是：每声道 4 字节块头 → 然后**按声道每 4 字节（8 个
   nibble）为一组**交错（ch0 的 4 字节、ch1 的 4 字节、循环）。我按 `frame*channels+ch` 实现，
   **单声道 72 个文件全绿**，一上立体声右声道从第 1 帧起全体错位（10 个菜单音乐全中）。
2. **`indexTable[0xF]` 是 8，不是 -1**。索引表只看 nibble 的低 3 位，0xF 的低 3 位是 7 → +8。
   所以 `0xF` 连续作用时步长索引一路涨（8→16→24…），差值越滚越大（-11、-30、-63…），不是每步 -11。

还有一次更普通的：24 位取高 16 位，我把 0x400000 的高 16 位写成了 `0x0040`（应为 `0x4000`）。

## 六、怎么证明「解对了」而不是「按我理解算对了」

自造样本 + 自洽断言只能证明后者。所以加了一条**外部参考**通路：

```bash
# 1) 系统解码器当参考
afconvert -f WAVE -d LEI16 in.wav ref.wav

# 2) 自己的解码器倒裸 PCM（自测二进制的隐藏模式）
concord_apple_audio_output_selftest --dump in.wav ours.pcm

# 3) 逐样本比对（python3：读 ref.wav 的 data 块 vs ours.pcm）
#    基线：files=144 bit-identical=144 mismatched=0 samples_compared=8095320
```

第 1 条同时暴露了「单声道全绿、立体声全错」——这正是纯自洽断言永远发现不了的那类错。

## 七、怎么证明「真的在播」

`play()` 返回 true 什么都不能说明。判据是**墙钟下界**：

```
300ms 素材 → play() → 轮询 isPlaying() → 转 false
要求 elapsed ≥ 250ms（实测 394–421ms）
```

「只把指针交给设备就返回」或「根本没建队列」的实现，这个下界立刻掉下来。另有
`framesConsumed() == 6615`（一帧不少地交给了设备）与「循环流 500ms 后仍在播、且消费帧数
越过素材长度」两条互证。

## 八、下一轮（P4-01b）开工前必须先定的三件事

1. **路径编码**：工厂入参是 `std::wstring` / `std::string`，macOS 上要转 UTF-8 才能 `open()`。
   与 T-02 同源（wchar_t 宽度 4 vs 2），不能靠 `reinterpret_cast` 糊过去。
2. **会话语义**：MCI 那套 alias + lease（weak_ptr 记录"谁拥有"、被取代的实例**不得**关闭新的
   所有者、析构只在仍拥有时才 stop）。照搬，否则会出现「旧实例把新实例关了」这类只有在
   快速重入时才会露头的 bug。
3. **全局语义**：`RuntimeAsyncSoundDevice` 是**进程级单例**播放（PlaySound 语义），不是每实例
   一路。b 轮要把"全局停止"做成真正的全局状态，而不是各自持有。

**b 轮验收**：链接缺口 8 → 0，`concord_runtime` 首次真链出来（这是整个项目从 V-01 起就没跨过的门槛）。
