## 2. 三个必须先定的事：答案

| 问题 | 决定 | 为什么不是另一个答案 |
| --- | --- | --- |
| 路径编码 | `wstring` → UTF-8，自写编码器：非代理码点直接编、`D800..DFFF` 当代理对合并 | `wcstombs` 按 locale 编（本机 `LC_ALL=C` 时会把中文编成 `?`）；`std::wstring_convert` 在 C++17 已废弃。macOS 的 `wchar_t` 是 4 字节（T-02 同源），但代码库里也有把 UTF-16 代理对塞进 `wstring` 的写法，所以两种都得收 |
| 会话语义 | 槽位表**进程级**静态共享 + lease（`shared_ptr` 相等比较） | 若每个设备实例各自持有输出流，"第二个实例 open 同一通道"会变成两路同时出声；MCI 的 alias 是进程级命名，第二次 open 是**替换** |
| 全局语义 | `AsyncSoundDevice` 共用一张只有 1 个槽的表，无租约，任何实例的析构都不停别人 | 这是 `PlaySound(SND_ASYNC)` 的语义：进程级单路、后一个顶前一个。`stopGlobal` 停的是同一路，所以另一个实例也能停 |

## 5. 与 Windows 侧的已知差异（记录在案，不是遗漏）

1. **`XAudio2Create` 返回 `E_NOTIMPL`**：多路语音（`RuntimeVoiceAudio` 的 source voice +
   输出矩阵混音）在 macOS 上没有实现，`ready()` 为 false、`lastError()==E_NOTIMPL`。
   为什么不给一个能返回 `S_OK` 的空壳：那会让每条语音"播放成功但不出声"，正好违反
   `rules.honest_success_vs_fake_success`（判据落在效果上）。已登记为独立任务 P4-02。
2. **open/play 的对应关系**：MCI 是两条命令（中间状态"已打开未播放"），这里是
   "open = 解码进槽并缓存 PCM，playFromStart = 起 AudioQueue"。`open` 的失败面因此
   与 MCI open 一致（文件不存在/格式不认识/截断）。
3. **音量单位**：MCI 是 0..1000（percent×10），这里吃 0..100 并由 AudioOutput 换成
   AudioQueue 线性增益。**不是** dB。
4. **`status mode` 三态 → 两态**：没有 pause 通道，只会回 playing / 非 playing。
   `isPlaying()` 的 `optional` 只承载"会话不存在"（对齐 MCI 命令报错）。
5. **`MainMenuMusicDevice` 运行期改音量不会立即生效**：AudioQueue 没有运行期改增益的
   接缝，重新起流会"跳回开头"，所以只在下次 `play` 生效（代码注释里写明）。
6. **`ForDiagnostics` 诊断接缝**：Windows 侧注入的是 WinMM 命令发送器，macOS 上没有
   对应物。非空钩子仍返回真实现（不降级），空钩子返回 unsupported——与 Windows 的
   `!send → unsupported` 一致。

## 6. 过程中踩到的两个坑（都已写进 queue.rules）

1. **把 core 与 device 源清单合成一个变量，会让 P4-01a 的自测连带需要 P4-01b 的桩**。
   cmake 不报警，只在链接期冒出一串 `makeUnsupportedXxx` 未定义。拆成
   `CONCORD_APPLE_AUDIO_CORE_SOURCES` / `..._DEVICE_SOURCES` 后消失。
2. **本机默认 `python3` 会卡在 U 状态**（未签名 Mach-O 的启动门禁，与 17:26 那次同源，
   只是这次是独立复现）。后果：`scripts/verify-win32-compat.sh` 第 1 层要算声明数，
   脚本**静默挂死 5 分钟**、日志停在 `1/14`。绕过：`/tmp/signedbin/python3` 包装
   （签过的实体二进制 + `DYLD_LIBRARY_PATH`）。这也是为什么本轮的验证脚本副本
   必须把 `python3` 换掉才能跑完 14 层。

  约为素材大小 ×2。菜单音效（毫秒级）无影响，长音乐需要后续优化。
