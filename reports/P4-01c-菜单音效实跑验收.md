# P4-01c · 菜单音效实跑验收（产品路径第一手证据）

- 日期：2026-11-10 22:20–22:35
- 任务：P4-01 / P4-01c（`verify` = 「菜单音效可播」）
- 结论：**产品级 `concord_runtime` 第一次真的出了声，并且能被对账证明**；同时修掉一个
  只有在产品路径上才会暴露的音频族缺陷。菜单的**交互音效**（点击/悬停）仍然拿不到，
  但原因不在音频层——是 `WM_TIMER` 根本没投递（已单独立为 S11）。

## 1. 上一轮为什么停在 `shell.pal`

上一轮从 `/tmp` 启动，`RuntimeConfig` 的两个相对根（`RedAlert2` / `local_data`）按
**工作目录**解析，于是所有资源都找不到。素材包其实早就准备好了：

```
ConcordRTS-GameData/
  runtime_config.ini 不存在 → 实际是 local_data/runtime_config.ini
  RedAlert2/GameMD ...                 ← ResourceRoot
  local_data/resources/mix_exports/... ← LocalDataRoot（15 个 .mix + 散装）
  local_data/runtime_audio_cache/      ← 音频解析缓存
```

`local_data/runtime_config.ini` 里明写「相对路径按启动工作目录解析，请在资源包根目录下
启动程序」。**在 `ConcordRTS-GameData` 下启动，`shell.pal` 报错立刻消失**，菜单进得去。

修法：不写死路径、不改配置，只是把工作目录设对。

```
$ cd ConcordRTS-GameData && concord_runtime
Runtime menu host: sharedWindow=yes sameProcess=yes titleStable=yes
Main menu Bink animation unavailable: Bink playback is unsupported on this
platform; using the original extracted first frame.
（此后持续运行，直到被 SIGTERM）
```

Bink 那条不是失败：Bink 视频在 mac 上没实现，产品按设计退回到"抽取出来的首帧"。

## 2. 观测面：`CONCORD_AUDIO_TRACE=1`

「play() 返回 true」证明不了出声——它只证明缓冲交给了 AudioQueue。而**产品自己的定时器
不能拿来当采样点**（见 §4：`WM_TIMER` 不投递，`isPlaying()` 根本不会被调用）。所以
观测点必须由输出流自己持有：

- `src/audio/apple/RuntimeAppleAudioDevices.cpp`：`open` / `play` / `stop` 各打一行，
  带上素材路径、帧数、采样率、声道、循环标志。
- `src/audio/apple/RuntimeAppleAudioOutput.cpp`：起播时开一个观测线程，每秒读一次
  `consumed_`（设备自报的已消费帧数），折算成秒并与墙钟对照。

默认完全关闭：不读时钟、不起线程、不打印。实测不设变量时 `[audio]` 行数为 **0**，
stdout 与加开关时逐行相同。

## 3. 修掉的缺陷：三个"单槽"族共用同一张槽位表

第一次带取证运行时，只出现**一条**观测序列，而且 `consumed` 从一开始就恒定在 `12981`——
这正是滑入音效 `uslide1` 的总帧数。音乐那条序列根本没出现。

根因在槽位表的模板参数：

```cpp
template <std::size_t N> struct SlotTable { ... };
template <std::size_t N> std::shared_ptr<SlotTable<N>> table();   // 只按容量 N 实例化
```

`AsyncSoundApple`、`MainMenuMusicApple`、`SkirmishMusicApple` 三个类都用 `table<1>()`，
于是它们拿到的是**同一个静态实例**、同一个 slot 0。后果：菜单进场的滑入音效
（0.59s）直接把菜单音乐从槽里顶掉，音乐此后永久消失。

Windows 侧这三个族是彼此独立的 MCI 设备（`PlaySound` / `mainmenu` / `skirmish`
三条别名），共用槽位是纯偏离。修法：给每个族一个空 tag 类型做模板参数，
`SlotTable<Family, N>` 让类型系统保证不同族不会撞车。

```cpp
struct AsyncSoundFamily {};
struct MenuSoundFamily {};
struct LegacyWaveFamily {};
struct MainMenuMusicFamily {};
struct SkirmishMusicFamily {};
struct CampaignMapAudioFamily {};
```

修完以后的观测是**两条独立序列**，音乐一直在走：

```
[audio] main-menu-music open .../thememd/drok.wav frames=3424239 rate=22050 ch=2
[audio] main-menu-music play loop=1 vol=100 frames=3424239 rate=22050
[audio] async play .../bag_uslide1_..._ima_block_v4.wav frames=12981 rate=22050 ch=2
[audio] output probe t=1s consumed=20480 playedSec=0.93 wallMs=1009 ... playing=1
[audio] output probe t=1s consumed=12981 playedSec=0.59 wallMs=1003 ... playing=0
[audio] output probe t=10s consumed=221184 playedSec=10.03 wallMs=10070 ... playing=1
[audio] output probe t=10s consumed=12981 playedSec=0.59 wallMs=10077 ... playing=0
```

- 音乐：`drok.wav` 3,424,239 帧 / 22050Hz ≈ **155.3 秒**，循环播放；14 秒里
  `playedSec` 从 0.93 走到 10.03，`wallMs` 从 1009 走到 10070，**比值 0.996**。
  这就是"CoreAudio 真的按时钟在消费"，而不是"缓冲交出去之后躺着没人取"。
- 音效：`uslide1` 12,981 帧 = 0.589 秒，`consumed` 停在 12981 且 `playing=0`，
  即**整段播完**（不是开播即失败）。

## 4. 新发现：`WM_TIMER` 不投递，菜单循环是死的

菜单的音乐看护、动画、动态状态全挂在 `WM_TIMER`（`SetTimer(window, 1, 16, ...)`）上：

```cpp
case WM_TIMER:
    state->audio.ensureMusicPlaying();
    if (updateDynamicState(*state) && IsWindow(window)) InvalidateRect(...);
```

但主循环是阻塞的 `GetMessageW`，而这条路径上**没有任何定时器消息被投递**。证据：

1. 把观测点放进 `isPlaying()`（菜单每秒会调一次）——**一条都不打印**，
   说明 `ensureMusicPlaying()` 从未被调用；
2. 进程 CPU 时间：3 秒时 `0:00.45`，11 秒时 `0:00.66`——8 秒只用了 0.21 秒 CPU，
   即没有在跑帧，而是阻塞在取消息上；
3. 音乐之所以还是响的，是因为 `startPageMusic()` 在进循环**之前**被直接调用了一次。

所以现在的真实能力边界是：**进场音乐 + 一次滑入音效会响，之后的任何声音都不会响**
（点击音效要等鼠标消息 + 定时器，EOF 重启要等 `ensureMusicPlaying`）。

这属于 S7/S9 的窗口-消息-定时器族，不在音频层。已立新任务 **S11**，附证据与判据。

### 新增 9 条断言，并用变异测试证明它们真的会红

```
$ # 把 MainMenuMusicFamily 改成 AsyncSoundFamily 的别名（复现改造前共享槽位）
FAIL cross: async sfx does not disturb main music
FAIL cross: skirmish music does not disturb main music
FAIL cross: menu sfx does not disturb main music
AudioDevices: checks=85 failures=3
$ # 恢复
AudioDevices: checks=85 failures=0
```

顺带一条方法论：这条断言第一次写成"音效起播后等 120ms 再问音乐是否在播"，结果
**变异后仍然是绿的**——因为那 300ms 的音效自己还在播，`isPlaying()` 问的是共享槽，
答案当然还是"在播"。等待时间必须**超过被顶掉素材的时长**（改成 500ms）才成为真判据。
同类问题在 P4-01a 已经踩过一次（"播完了"和"从来没数据"看起来一模一样）。

## 7. 未验证 / 下一轮

- **交互音效**（点击、悬停、按钮）仍为 0 证据：要等 S11 把 `WM_TIMER` 与鼠标消息接通。
- **听感**：只有"帧被消费"的量化证据，没有人耳确认（我这边没有扬声器回路）。
- **EOF 重启**：`drok.wav` 155 秒，本轮只跑了 14 秒，循环与重启路径未覆盖。
- **音量**：`setVolumePercent` 在播放中改音量不即时生效（AudioQueue 无增益接缝），
  仍未变。
- 造假的"成功"还没排除：`AudioQueueSetParameter` 的返回值被忽略，静音设备上依旧
  会显示 `consumed` 增长。要证明"有声音"最终仍需一次人耳/环回采集。
