## 一、本轮做什么

P5-03 放回 MapNativeOverlay 后，产品菜单系统（RuntimeMainMenu / RuntimeCampaignMenu /
RuntimeSkirmishMenu / RuntimeShell 等）在 macOS 构建里引用了 21 个输入 / 光标 / 捕获 /
定时器族 Win32 API，但 compat 层尚未实现。本轮补全。

## 三、三个关键设计决策

1. **LoadCursorW 标准 ID 必须返回非 NULL**。`SetCursor(LoadCursorW(nullptr, IDC_ARROW))`
   里，如果 LoadCursorW 返回 NULL，SetCursor 的语义是"隐藏光标"——把"加载失败"静默
   改成了"故意隐藏"。所以标准系统光标 ID 返回稳定伪句柄（编码原 ID），只有自定义
   字符串名（真加载失败）才返回 NULL。

2. **捕获是逻辑状态，不是鼠标路由**。SetCapture/GetCapture/ReleaseCapture 的本质是
   "哪个窗口当前拥有鼠标捕获"的逻辑状态，不依赖真实鼠标路由。维护这个状态让产品里
   `SetCapture(w); GetCapture()==w` 的判据成立，比一律返回 NULL 更接近 Win32 语义。

3. **定时器返回 TRUE 的桩比返回 FALSE 诚实**。无事件循环派发 WM_TIMER，返回 TRUE 和
   返回 FALSE 都不会让菜单自动刷新；但返回 FALSE 会让调用方误判"出错"走错误分支。
   所以 TRUE（登记成功、只是永不触发）是更安全的选择。

## 四、本轮踩的坑（重要）

`applyRop2` 保留**目标** alpha 字节（`(dst & 0xFF000000) | (value & kRgbMask)`），不保留
笔的 alpha。因此：

- 黑笔（RGB 0）画在 alpha=0 的透明 DIB 上 → 结果仍是 `0x00000000`（全零），"画了等于没画"。

这不是 bug，而是 32bpp BI_RGB 不带 alpha 语义的正确行为。但 selftest 第一版用
"位图里是否存在非零像素"来断言 DrawFrameControl "真画了"，于是黑框画在透明背景上
测不出。

**修正**：selftest 先 `PatBlt(WHITENESS)` 填不透明白背景，再画黑框，断言边框像素
`== 0xFF000000`（不透明黑）。

**通用教训**：断言"真画了"时，笔色不能是 RGB(0,0,0) 且背景不能是透明的——两者叠加
会让"真的画了"和"完全没画"在像素层面不可区分。
