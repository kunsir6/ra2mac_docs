# P5-06 · 收口文本 / 字体族

> 缺口 149 → 138（C-linkage 86 → 75，项目 C++ 63 不变），兑现 11 个符号、零新增。

## 一、本轮做什么

P5-05 之后剩余 C-linkage 86 = 窗口/消息 60 + 文本/字体 11 + 其他 13 + GetThreadDesktop 1 +
XAudio2Create 1。本轮收口文本/字体族的 11 个符号。文本绘制是"硬活"——无 CoreText 后端时，
诚实的选择不是"返回 TRUE 但不画"（静默不画），而是画"缺字形"豆腐块（□）占位。

## 二、兑现清单

| 符号 | 类别 | 实现策略 |
|---|---|---|
| GetTextAlign / SetTextAlign | DC 状态 | `textAlign` 字段，SaveDC/RestoreDC 一并保存恢复 |
| GetThreadDpiAwarenessContext / GetAwarenessFromDpiAwarenessContext | DPI 感知 | 返回 `PER_MONITOR_AWARE` 哨兵并映射回 `DPI_AWARENESS_PER_MONITOR_AWARE` |
| CreateFontW | 字体对象 | 新建 `ObjectKind::Font` 对象，完整存 LOGFONTW 入参 |
| GetTextExtentPoint32W | 度量 | `cx = c × 字宽`，`cy = 字高`，与 TextOutW 共用同一套 fontMetricsFor |
| TextOutW / ExtTextOutA / DrawTextW / DrawTextA | 绘制 | 每个码点画一个"缺字形"豆腐块（空心框） |
| GetGlyphIndicesW | 字形索引 | 诚实返回 GDI_ERROR（无字形表，不伪造恒等映射） |

## 三、关键设计决策

1. **文本绘制 = 豆腐块占位，不是静默 no-op**。判据（`honest_success_vs_fake_success`）：
   调用方要的效果是"菜单上有可读文字"，而无 CoreText 时这个效果**无法成立**。所以不能
   "返回 TRUE 但不画"（静默不画，任务卡点名的风险）。豆腐块让文本：①可见（不是隐身）；
   ②占满正确布局空间（度量与绘制同一套 fontMetricsFor）；③一眼可辨"字形还没接进来"
   （□ 是"缺字形"的通用约定），不会被误当成渲染 bug。S4 换 CoreText 时，只需把
   `drawTofuGlyph` 换成按码点查真实字形，调用点不变。

2. **DPI 必须返回 PER_MONITOR_AWARE，不是"未感知"默认**。这是产品硬门槛：
   `MapNativeOverlayWin32::begin` 里 `GetAwarenessFromDpiAwarenessContext(
   GetThreadDpiAwarenessContext()) != DPI_AWARENESS_PER_MONITOR_AWARE` 会直接
   `p.fail("native-reference-DPI-contract")` 返回 nullptr，让 P5-03 刚放回的 native overlay
   失效。软件帧缓冲不缩放、按原生像素渲染，本就等价于"每显示器感知"，所以返回
   PER_MONITOR_AWARE 是**如实**而非迁就。

3. **GetGlyphIndicesW 诚实返回 GDI_ERROR**。无 Unicode→字形索引表，编造"恒等映射"
   （glyph[i]=码点）会让调用方以为能拿到真实字形索引。唯一调用点是
   `RuntimePlayerDefeatNoticeSmoke` 的"字体是否覆盖所需汉字"判据，返回 GDI_ERROR 让该
   诊断如实报出"字体缺字形"——这正是 mac 上的真相。相比之下，把每个码点画成豆腐块的
   TextOutW 之所以能"成功"，是因为它确实画了可见的东西（占位），两者判据不同。

4. **库存字体的 LOGFONT 如实回填零值**。P5-05 及之前，`GetObject(font)` 对字体返回 0
   （诚实失败）。P5-06 起 CreateFontW 把入参存进 `fontLog`，GetObject 如实回填；库存字体
   （DEFAULT_GUI_FONT 等）无参数，回填零值 LOGFONT（lfHeight=0）——这与 Win32 一致
   （Win32 对库存字体同样返回系统定义的 LOGFONT）。度量侧对零值字高回落到 16px 默认。

## 四、字体度量（fontMetricsFor）

- 字高 = `lfHeight` 绝对值；0（库存字体 / 未指定）回落 16px。
- 字宽 = `lfWidth` 绝对值；0（"按比例自适应"）按 5:7 固定比例 `round(h × 5 / 7)`。
- GetTextExtentPoint32W 与 TextOutW 共用这个函数，于是"先量后画"的居中/对齐代码不错位。
  selftest 用字面量断言（`-16` 字高 → 字宽 11 → 两字符宽 22），不拿常量自比。

## 五、本轮踩的坑 / 连带修正

1. **GetObject 语义变更牵动旧断言**。`CompatDcStateSemantics.cpp` 里有一条
   "字体对象暂不给 LOGFONT（诚实失败）== 0"的断言，本轮 GetObject 兑现字体 LOGFONT 后
   变成 `sizeof(LOGFONTW)==156`。已同步更新该断言，避免"实现改了、断言没跟上"造成的假红。
   教训：改一个已有 API 的返回值语义，要全仓 grep 它被谁断言过。

2. **windows.h 加 4 个 DPI 哨兵常量**（`DPI_AWARENESS_CONTEXT_UNAWARE/-2/-3/-4`）会触发
   全量重编（所有 include windows.h 的 TU），这是预期内的、不是回归。
