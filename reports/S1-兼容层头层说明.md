## 1. 接入方式：靠 include 路径优先级，不改源码

`cmake/PlatformApple.cmake` 新增 `concord_apple_enable_win32_compat()`：

```cmake
include_directories(BEFORE "${CONCORD_APPLE_WIN32_COMPAT_INCLUDE_DIR}")
```

由 `CompilerAndPlatform.cmake` 的 `elseif(APPLE)` 分支调用。效果：

- 全部源码的 `#include <windows.h>` 原样不动，只是搜索路径变了；
- `build-product-mac/build.ninja` 里 **1067 条编译规则的 `INCLUDES` 第一项**就是 `compat/win32/include`，排在 `-I src` 之前，因此 `<windows.h>` 不会去碰系统头（本来也不存在）；
- Windows 构建图完全不经过这段代码，一个字节都不受影响。

**双向守卫**：三个 shim 头第一行都是

```cpp
#if defined(_WIN32)
#error "compat/win32/include/windows.h is the non-Windows shim; ..."
#endif
```

实测 `-D_WIN32` 编译立刻命中该 `#error`。所以即使将来有人误把这个目录加进 Windows 的 include 路径，也会**在 configure/编译期炸掉**，而不是静默遮蔽真正的 SDK 头。

## 2. 为什么是"声明层"而不是"实现层"

分流原则：**能在头里内联的纯数学语义就内联，需要真实后端的只声明**。

- 内联（12 个）：`SetRect` / `CopyRect` / `InflateRect` / `OffsetRect` / `IsRectEmpty` / `EqualRect` / `PtInRect` / `IntersectRect` / `UnionRect` / `SubtractRect` / `SetRectEmpty`。
  这些在 Win32 里是导出函数，但语义是纯算术且**左闭右开**——内联掉可以少 10 个实现，而且行为与 Windows 完全一致。
  另外 `_dupenv_s` 也内联实现（MSVC CRT 安全版 getenv，malloc 分配、调用方 free）。
- 只声明（276 个）：凡是需要句柄表、窗口后端、字体栅格化、文件系统的，全部留空。**未实现的符号会在链接期暴露**，这是刻意的——S2–S5 分族补齐时，漏一个就是一条明确的 undefined symbol，不会静默降级。

## 4. 关键发现：`<list>` 被 include 在匿名命名空间内部

这是本轮最有价值的发现，也是一个**与本次改动无关的既有结构隐患**。

`RuntimeShell.cpp`：

- 第 243 行 `namespace {` 打开匿名命名空间；
- 第 21848–21849 行在**该命名空间内部**（实测花括号深度 = 1）执行
  `#include "ui/selection/RuntimeSelectedPathBatch.h"` 与 `RuntimeSelectedPathRaster.h`；
- 后者第 7 行 `#include <list>`。

于是 libc++ 的 `<list>` 被展开在 `namespace { ... }` 里，`_LIBCPP_BEGIN_NAMESPACE_STD` 开出的 `std` 落在匿名命名空间内部，`pointer_traits` / `__rebind_pointer` / `bidirectional_iterator_tag` 全部找不到——一次 400 条错误里 146 条是 `no member named X in namespace X`。

**证明这不是 shim 的问题**：把同样的 include 链放到文件作用域单独编译，零错误：

```cpp
#include <windows.h>
#include "ui/selection/RuntimeSelectedPathBatch.h"
#include "ui/selection/RuntimeSelectedPathRaster.h"
// → 退出码 0
```

结论：这两个 include 需要移到文件顶部（或把匿名命名空间在它们之前关闭）。**这属于 b1/b2 的活**，本轮不动——它需要精确找到匿名命名空间的闭合点，而该文件 89k 行里花括号深度在 21848 处为 1、到 21860 处为 3，说明这个命名空间跨了非常多代码，移动 include 必须非常小心。

## 5. 冲突与排除清单（S2 起必须处理）

### 5.1 五个 TU **自己伪造了 Win32**，与真 shim 必然冲突

| TU | 伪造的函数（举几例） |
|---|---|
| `tests/infrastructure/KeyboardIngressControllerContract.cpp` | `HWND GetCapture()`、`void InvalidateRect(HWND, std::nullptr_t, int)`、`int GetKeyState(int)`、`void GetClientRect(HWND, RECT*)` |
| `tests/infrastructure/KeyboardRouterControllerContract.cpp` | `int GetKeyState(WPARAM)`、`void RedrawWindow(int, void*, void*, unsigned)` |
| `tests/infrastructure/MapRightPointerControllerContract.cpp` | `std::intptr_t GetWindowLongPtrW(int,int)`、`void SetFocus(int)`、`std::intptr_t DefWindowProcW(int,uint32_t,WPARAM,LPARAM)` |
| `tests/infrastructure/MenuKeyControllerContract.cpp` | `void GetClientRect(Model*, RECT*)`、`void InvalidateRect(Model*, void*, bool)` |
| `tests/infrastructure/SessionKeyControllerContract.cpp` | `void DestroyWindow(int)`、`void InvalidateRect(int, void*, bool)` |
| `tests/infrastructure/fixtures/PointerIngressOld.inl` | `int PtInRect(const RECT*, POINT)`、`void SendMessageW(HWND,UINT,int,int)`、`int DefWindowProcW(HWND,UINT,WPARAM,LPARAM)` |

这 5 个 TU（+1 个 fixture）用**故意不同签名**的桩替换 Win32，好在没有真实窗口的前提下测输入控制器。它们与任何忠实的 shim 都不可共存。

**处置**：在 macOS 构建图里排除这 5 个 TU。理由充分——它们测的是 Windows 输入控制器，而这个项目保留 Windows 构建，这些测试在 Windows 上照常跑。机制上归入 b2 的「非 Windows 退出构建图」清单。

### 5.2 不覆盖的子系统（需要在 macOS 上退出构建图，而不是 shim）

| 子系统 | 符号 | 位置 |
|---|---|---|
| Schannel TLS | `AcquireCredentialsHandleW` / `InitializeSecurityContextW` / `AcceptSecurityContext` / `QueryContextAttributesW` / `FreeContextBuffer` | 与 `RuntimeInternetTlsTransport.cpp` 相关 |
| BCrypt | `BCryptOpenAlgorithmProvider` / `BCryptHash` / `BCryptCloseAlgorithmProvider` | 同上 |
| XAudio2 | `XAudio2Create` | `src/audio/backend/win32/` |
| DbgHelp | `SymInitialize` / `SymFromAddr` / `SymGetLineFromAddr64` / `SymCleanup` | 崩溃栈符号化 |
| Job 对象 | `CreateJobObjectW` / `SetInformationJobObject` | 多进程 smoke |
| COM 激活 | `CoCreateInstance` | 暂只声明了 `CoInitializeEx` / `CoUninitialize` |

这些没有"合理的 macOS 等价物"——不是缺声明，是缺后端。**shim 只声明不实现是正确选择**：它们会以 undefined symbol 的形式出现在链接期，逼着我们在那之前做"排除 TU"或"换后端"的显式决定。

## 7. 已知偏差（必须承认）

1. **`wchar_t` 宽度**：macOS 4 字节、Windows 2 字节。`LPCWSTR` 在本层定义为 `const wchar_t*`，macOS 内自洽，但与 Windows **二进制不兼容**。凡跨边界（存档、网络、资源清单）的 `std::wstring` 必须显式转 UTF-8。
2. **`WPARAM`/`LPARAM`/`LRESULT` 按 Win64 取指针宽度**。若将来要支持 32 位目标，需重新核对。
3. **`#define ERROR 0`**：真 Win32 在 `wingdi.h` 里就这么定义（`GetClipBox` 失败返回值）。为降低撞名风险，本层用了 `#ifndef ERROR` 包裹。
4. **UNICODE 别名宏**（`#define GetObject GetObjectW` 等 60 余条）：项目源码里 `GetObject` 与 `GetObjectW` 混用，与 Windows 在 `UNICODE` 下的行为一致。但这些宏会**污染整片命名空间**，若将来项目里出现同名函数会被改写。
5. 276 个声明中有约 60 个**当前产品图并不使用**（如 `CreateProcessW`、`RegOpenKeyExW`、`CreateThread`），是为测试 TU 与后续 S5 预留的。它们不影响编译，但会让"未实现符号"清单在链接期更长——这是有意的取舍。
