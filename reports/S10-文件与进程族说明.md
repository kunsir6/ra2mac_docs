# S10 · 文件与进程族说明

结论先行：**17 个 C-linkage 符号 + 1 个自造窄参 `CreateFileW` 重载全部落地，链接缺口
225 → 207（C 124→107，项目 C++ 101→100），S10 段零残留。**
新增第 10 层自测 `CompatFileSemantics.cpp`（147 条断言），十层验证全过。
产品构建图仍是 0 编译错误。

---

## 一、先纠正任务卡里的一个前提

S10 的任务卡写的是：

> `src/core/io/RuntimeAtomicFile.cpp:180` 是生产路径（原子存档），只补窄参重载
> 等于给存档链路留一个"能编译、一调就崩"的入口。

**这个前提在 macOS 上不成立。** `RuntimeAtomicFile.cpp` 用 `#ifdef _WIN32` 分叉，
而 Apple 构建图**不定义 `_WIN32`**（兼容层的 `windows.h` 还专门 `#error` 拒绝
`_WIN32`），所以那个 TU 在 macOS 上编译的是 **POSIX 分支**（`::open` / `::close` /
`errno`）。证据不是推测，是链接器的引用点清单：

```
WriteFile  → RuntimeCursorSmokeDetail::writeNewBytes (...) in RuntimeCursorSmoke.inl
```

只有一处引用，来自**诊断走查**，不是存档链路。

这件事改变了风险判断，方向是变好：窄参重载要兑现的路径不是"保存游戏"，
所以"半成品会毁存档"的担忧不成立。但**没有改变必须做对的理由**——它仍是
`CreateFileW(path.c_str(), ...)` 这种形态的唯一入口，写错了照样是"能编译、一调就崩"，
只是崩在检查里而不是存档里。

顺带记一笔：POSIX 分支的 `maximumNativePathUnits` 是 4096（Windows 是 32760）。
这不是本层的事，但将来若要跨平台做路径长度边界测试，必须知道这个数不同。

## 二、这一族的难点不在实现，在"哪些必须说谎、哪些必须诚实"

### 必须诚实（返回失败）

| 符号 | 假装成功的后果 |
|---|---|
| `GetModuleHandleW(具名)` / `GetProcAddress` | 项目用它们加载 `binkw32.dll`。返回"看起来有效"的指针，调用方会把随机地址当函数调用——崩得很晚。返回 NULL + `ERROR_MOD_NOT_FOUND`，整条 Bink 路径一致地走"没有视频库"分支，那正是这台机器上的真实情况。 |
| `GetEnvironmentVariableW(不存在)` | 项目一半的诊断开关是 `GetEnvironmentVariableW(L"FLAG", buf, 2) == 1`。假装"空值也算有"会让全部诊断开关默认打开，且所有断言照旧通过。 |
| `MultiByteToWideChar(非法字节, MB_ERR_INVALID_CHARS)` | 调用点 `toWide()` 正是**靠这次失败**判定"这不是 UTF-8"，然后才回退 `CP_ACP`。悄悄替换成 U+FFFD，回退分支永远走不到，而结果"看起来没坏"。 |
| `QueryPerformanceCounter(nullptr)` / 未知码页 | 返回 0 而不设错误码，调用方读到的 `GetLastError` 是上一次的残留值。 |

### 必须等价（返回成功）

`GetCurrentProcess` / `GetCurrentProcessId` / `GetCurrentThreadId` / `Sleep` /
`GetTickCount64` / `QueryPerformanceCounter` / `GetSystemTime` —— 这些没有"平台做不到"
的成分，只有"用哪个内核接口"的差别。

## 三、五个"换成表层等价物就会静默改行为"的地方

### 1. `GetLastError` 必须是线程局部，且成功的调用不清它

全局 `DWORD` 会让窗口线程读到渲染线程的错误码，症状是"偶发地进了错误的失败分支"——
不能稳定复现，也不会在任何单线程自测里出现。

另一半更容易写错：**成功的调用不清 LastError**。如果为了"干净"在每个函数入口清 0，
调用点惯用的"先做一件可能失败的事，再读 `GetLastError`"就会读到 0。本层所有成功路径
一行都不写它。自测用 `GetTickCount64()`（无参数、不可能失败）之后 `LastError` 必须
仍是 4321 来钉这条。

### 2. `CloseHandle` 收到 GDI 指针时不能把指针当 fd 关掉

本层的 `HANDLE` 是 `void*`，而同一进程里同时存在文件句柄、GDI 对象/DC 指针。
`CloseHandle(bitmap)` 若走进 `close((int)(intptr_t)ptr)`，关掉的是一个毫不相干的 fd；
若先解引用 magic，则在野指针上立刻段错误。

判据只能是**登记表里有它吗**——查表只比较指针值，不碰它指向的内存。这是唯一安全的
做法，也是为什么本层拒绝"给每类加 magic 字段"的方案。自测除了断言 `FALSE`，还断言
**被拒绝之后位图依然有效**（`GetObjectW` 仍返回 `sizeof(BITMAP)`、`bmWidth` 仍是 8）：
只断言返回值不够，实现完全可能"返回 FALSE 但已经把 fd 关了"。

### 3. `CreateFileW` 的失败码决定重试循环走哪条路

`RuntimeAtomicFile` 的临时文件重试是：

```cpp
if (result.error == ERROR_FILE_EXISTS || result.error == ERROR_ALREADY_EXISTS) continue;
if (result.error == ERROR_ACCESS_DENIED && GetFileAttributesW(...) != INVALID_FILE_ATTRIBUTES) continue;
```

所以 `errno → Win32 错误码` 的映射表是按**调用点真正会比较的那几个值**写的：
`EEXIST→ERROR_FILE_EXISTS(80)`、`ENOENT→ERROR_FILE_NOT_FOUND(2)`、
`EACCES/EPERM/EISDIR→ERROR_ACCESS_DENIED(5)`、`ENOSPC→ERROR_DISK_FULL(112)`、
`EMFILE/ENFILE→ERROR_TOO_MANY_OPEN_FILES(4)`、`ENAMETOOLONG→ERROR_FILENAME_EXCED_RANGE(206)`。

未知错误给 `ERROR_GEN_FAILURE(31)`，**不是** `ERROR_ACCESS_DENIED`——后者会把排查
方向引到权限上，而真实原因可能是任何别的东西。

### 4. 4 字节的 emoji 在本平台占**一个** `wchar_t`

本平台 `wchar_t` 是 32 位（UTF-32），Windows 是 16 位（UTF-16）。U+1F600 在 Windows 上是
两个代理项 `wchar_t`，在这里是**一个**。

这不是"差不多"的差别：凡是 `size()` 参与判据的地方（截断阈值、缓冲区长度），两平台
的数字本来就不同。自测把这条钉成硬断言（`MultiByteToWideChar("😀") == 1`，
`WideCharToMultiByte(U+1F600) == 4 字节`）。**本层保证的是码点序列一致，不保证
`wchar_t` 个数一致**——将来若要跨平台逐字节对拍，得先把这些判据改成按码点数。

### 5. 非法 UTF-8 的判据比"能解出来"严

Windows 在 `MB_ERR_INVALID_CHARS` 下拒绝的不只是"字节不够"，还包括：

- 过长编码（overlong：`C0 80` 表示 U+0000）
- UTF-8 里编码代理项（`ED A0 80` = U+D800）
- 超出 U+10FFFF
- 截断的多字节序列、孤立的后续字节

放宽任何一条，"严格模式失败"这条契约就悄悄失效了。自测把五种非法输入逐个喂进去，
既断言严格模式返回 0 + `ERROR_NO_UNICODE_TRANSLATION`，也断言**非严格模式成功且产出
U+FFFD**——两条一起才说明"严格"是个有意义的开关，而不是"永远失败"。

## 四、两个时钟，两条语义，不能混用

`GetTickCount64` 与 `QueryPerformanceCounter` 底层用**两个不同**的内核时钟：

| Win32 | 语义 | 本平台对应 |
|---|---|---|
| `GetTickCount64` | 开机以来的毫秒数，**包含系统睡眠** | `mach_continuous_time` |
| `QueryPerformanceCounter` | 不变计数器，纳秒级，不保证跨睡眠累加 | `mach_absolute_time` |

为什么这个区分不能省：项目用 `deadline = GetTickCount64() + N` 做超时判据。若底层用
`mach_absolute_time`（不含睡眠），合盖一夜再打开，所有截止时间都"还没到"——超时全部
失效，且没有任何日志。反过来把 QPC 接到 `mach_continuous_time` 上，则一段睡眠会被
算进"渲染耗时"，性能统计直接失真。

QPC 的计数单位直接取纳秒（等价于频率 1e9）。`QueryPerformanceFrequency` **刻意没有
实现**：它不在缺口里（没有 TU 引用），而只实现 QPC 不实现 QPF 不会造成误用——
调用 QPF 会得到链接错误，那是最好的失败方式。

## 五、把两套编解码合成一套（本轮唯一的重构）

S9 的 `RuntimeWin32CompatMisc.cpp` 里有一对本地 UTF-8 助手，当时刻意不复用
`MultiByteToWideChar`/`WideCharToMultiByte`（那两个还不存在，自我调用就是循环依赖）。
现在它们存在了，两份实现同时存在是隐患：一份把非法字节替换成 U+FFFD、另一份截断，
同一条路径在不同调用点上表现就不同——而差异只在喂进非法字节时才显形。

本轮把编解码内核抬到 `compat/win32/src/RuntimeWin32CompatInternal.h`，S9 的助手改成
一行委托，`MultiByteToWideChar`/`WideCharToMultiByte` 走同一个 `decodeUtf8`/`decodeWide`。
分叉从此不可能发生。

代价是本轮把解码判据**收紧**了（加了 overlong / 代理项 / 超范围三查）。S9 的 52 条
断言全部仍然通过——这是"收紧没有改变合法输入行为"的证据，比读代码可靠。

同一个头里还有两件共用件：`LastError` 的线程局部槽，和句柄登记表。**句柄表刻意设计成
可被 S7/S8 复用**（登记时带 kind 字符串 + 析构函数），否则下一轮会再写一张表，
两张表的 `CloseHandle` 一定会打架。

## 七、边界（不能说成"成了"）

- **仍然没有可运行二进制。** 这些函数确实被调用了（自测里真的打开了文件、写了字节、
  读了回来），但产品侧的调用点要等链接通过才会真的跑起来。
- **`dwShareMode` 无法实现。** POSIX 没有共享模式，这里接受但忽略。刻意不假装
  "已按共享模式打开"——没有任何观测点能区分，而假装会让将来真的需要排除性打开时
  找不到线索。
- **`CreateFileW` 的 `SECURITY_ATTRIBUTES` 被忽略**：一律 `O_CLOEXEC`（不可继承），
  对应 Windows 上"属性为空 ⇒ 不可继承"。**传入可继承属性时不会真的可继承**。
- **只支持 UTF-8 码页。** `CP_ACP` / `CP_OEMCP` 映射为 UTF-8（macOS 的 ANSI 码页就是
  UTF-8），其余码页一律 `ERROR_INVALID_PARAMETER` + 一次 stderr 说明。项目里没有
  非 UTF-8 的调用点，但这是真实的缺口。
- **`GetCurrentThreadId` 永不复用。** Windows 的 ThreadId 在线程退出后可被复用；
  本层是进程内自增。调用点只做"是不是同一个线程"的比较，两种语义都满足——但如果
  将来有代码拿 ThreadId 当"线程槽位"（先查表再断言"这个 id 已失效"），就会不一致。
- **没有 Windows 金标准可对拍。** 147 条期望值是按 Win32 文档语义写死的，不是从
  Windows 采集的。`rules.selfconsistency_ceiling` 这条限制仍然成立。

## 九、下一轮建议

缺口现在是 207 = **C 107 + 项目 C++ 100**。两条路线的性格完全不同：

**A. S7（窗口/消息/输入，92 个）** —— 数量最大，但**卡在选型**：窗口后端建在
SDL3 之上（`CONCORD_APPLE_SDL3_WINDOW=OFF`）还是直接用 Cocoa？这个决定会影响
92 个符号里至少 40 个的形态（`GetMessageW`/`PeekMessageW` 是"泵真实事件"还是
"合成事件"）。**不建议在没有选型的情况下开这一项。**

**B. S4（GDI 文本，14 个）** —— 数量小，但需要一个真实字形光栅器：CoreText 出位图
再贴回软件帧缓冲。开写之前必须定三件事：字体族名映射（`"MS Shell Dlg"` → ?）、
度量语义（`GetTextExtentPoint32W` 必须与实际排版宽度一致，否则所有按钮居中错位）、
CJK 覆盖。**有选型风险，但风险集中在三件事上，可以先做一轮"选型 + 最小可验证"。**

**C. P5-01（100 个项目 C++ 符号的分文件判断）** —— 纯分析、零风险、且直接决定
链接里程碑还有多远。上一轮已经初步判断：字体文字 30 / MapNativeOverlay 20 /
合成背缓冲 13 只是"住在 `win32/` 目录里的纯逻辑"，S3/S4 到位后可以直接放回构建图，
真正平台绑定只有 D3D11 presenter。**如果下一轮不想背选型风险，就做这个。**

推荐顺序：**C → B → A**。C 能把 207 里最大的一块不确定性变成一张明确的表，
B 只需要在一次"选型 + 最小可验证"里就能定性，A 应该等到前两者给出结论。
