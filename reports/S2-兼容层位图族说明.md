## 3. 三个由实测数据决定的边界

这三条不是设计偏好，是先量后定的：

| 边界 | 实测依据 | 后果 |
|---|---|---|
| **只支持 32bpp BI_RGB** | 11 处 `CreateDIBSection` + 5 处 `StretchDIBits` + 1 处 `SetDIBitsToDevice`，**全部** `biBitCount=32`、`biCompression=BI_RGB`、`biHeight<0` | 不需要调色板、不需要行翻转；8/24bpp 一律 `nullptr` + stderr 说明 |
| **ROP 白名单** | 14 处 `BitBlt`/`StretchBlt`/`PatBlt` 中 13 处 `SRCCOPY`、1 处 `DSTINVERT` | 支持 SRCCOPY/DSTINVERT/BLACKNESS/WHITENESS/SRCAND/SRCINVERT/SRCPAINT；`MERGECOPY`/`PATPAINT` 等返回失败并打印 ROP 值 |
| **HALFTONE 显式失败** | 所有拉伸前都调 `SetStretchBltMode(dc, COLORONCOLOR)`；`COLORONCOLOR` 语义即「删像素」= 最近邻 | 实现 NN；若调用方设过 `HALFTONE` 则返回失败，不做近似 |

**为什么失败比降级好**：把未知 ROP 静默当 `SRCCOPY`，画面「看起来对、合成全错」，这种 bug 在截图对比里几乎查不出来；直接返回 `FALSE` 会在调用点立刻炸出位置。

## 4. 80 条断言覆盖了什么

| 分组 | 断言数 | 关键点 |
|---|---:|---|
| 对象生命周期 | 14 | 库存对象句柄跨调用稳定、删除必然失败、越界编号返回空；**仍被选中的笔/画刷删除必须失败**，还原后成功；重复删除不崩 |
| DIB 创建与像素格式 | 14 | 8bpp 被拒绝且 `ppvBits` 保持空；`COLORREF(0x00BBGGRR)` ↔ DIB 内存 `0xAARRGGBB` 双向往返；自底向上位图「内存首行 = 图像末行」 |
| BitBlt | 10 | SRCCOPY 逐像素相等、偏移复制对齐、DSTINVERT 不看源、两个不支持 ROP 必须失败、越界裁剪后源坐标同步平移、**同位图重叠自拷贝等价于 memmove** |
| StretchBlt | 5 | 2× 放大每个 2×2 块同色且与源像素对应（真正验证最近邻而非插值）；HALFTONE 必须失败 |
| StretchDIBits / SetDIBitsToDevice | 7 | 返回值非 `GDI_ERROR` **且等于扫描线数**（调用方靠 `!= GDI_ERROR` 判成功）；不支持 ROP 返回 `GDI_ERROR`；1:1 偏移写入不污染矩形外 |
| PatBlt 与状态栈 | 11 | 三种 ROP；`PATCOPY` 只填指定矩形；空画刷 `PATCOPY` 失败；`SaveDC`/`RestoreDC(-1)` 还原文字色与 BkMode |

验证入口固化为 `scripts/verify-win32-compat.sh`（三层：声明层仅编译 / 内联语义 / 实现语义），避免每轮靠记忆重敲命令。**刻意不注册到 CTest**：基线对账会比对 `registered` 数量，加一个 macOS 专属测试会让每次采集都显示差异。

## 5. 本轮修掉的三类问题

首次运行 80 条里有 7 条失败，正好覆盖三种不同性质：

1. **实现缺陷（1 条）**：`SelectObject` 只对位图累加 `selectedCount`，笔/画刷/字体没记，导致「选中中的画刷删除失败」这条 Windows 语义没实现。已改为四类对象统一计入。
2. **设计判断（1 条）**：`DSTINVERT` 原本按 32 位整体取反，`0xFF102030 → 0x00EFDFCF`，**alpha 被抹成 0**。真实 GDI 对 32bpp BI_RGB 不解释高 8 位，但本项目后续任何把该 DIB 当 RGBA 源的路径都会突然全透明。已改为只翻转 RGB、保留 alpha（`invertRgb()`），并在代码里写明理由。
3. **测试自己算错（5 条）**：`COLORREF` 与 `0xAARRGGBB` 的移位方向、`peekBits` 返回原始像素而非 `COLORREF`、未写区域保持初始零值而非不透明黑。全部按实际语义修正，**没有为了过测试去改实现**。

## 7. 新发现（本轮最重要）：shim 的**类型同一性**问题

复跑普查时 `RuntimeCampaignMenu.cpp` 报了这条：

```
error: no matching function for call to 'max'
  const int clientWidth = std::max(1L, client.right - client.left);
note: deduced conflicting types for parameter '_Tp' ('long' vs. 'LONG' (aka 'int'))
```

根因不在调用方，在 S1 的 shim：Windows 的 `LONG` 是 `long`，而 shim 里写成 `std::int32_t`（= `int`）。于是 `std::max(1L, LONG-LONG)` 在 Windows 上合法、在 macOS 上不合法。

**这不能靠把 shim 的 `LONG` 改成 `long` 来解决**：macOS 上 `long` 是 64 位，`RECT`/`BITMAPINFOHEADER` 布局会立刻从 16/40 字节变成 32/72 字节，与 Windows 位图格式彻底不兼容——比编译错误严重得多。`LONG`/`DWORD` 必须继续锁 32 位。

同类问题还有 `std::filesystem::path::string_type`：Windows 上是 `std::wstring`、POSIX 上是 `std::string`，于是 `MenuAudio.original.inl:70` 的 `const wchar_t[7]` 比较失败。这两类都属于「源码依赖了 Windows typedef 的具体类型身份」，需要**在调用点做窄/宽或显式模板参数适配**，属于独立工作项。

已作为新任务 **T-01（类型同一性对齐）** 入队，不在 S2 内消化。

## 9. 风险与未决

1. **链接级验证仍为零**。`concord_runtime` 依旧是整体可执行文件，`RuntimeShell.cpp` 不通就永远到不了链接。本轮的 80 条断言是「函数级正确」，不是「接入后正确」。
2. **GDI 文本度量保真**依旧是最大未验证风险（`DrawTextW` 38 处 / `CreateFontW` 17 处），S4 必须先用确定性位图字体后端，像素金标准测试留在 Windows 跑。
3. **栈上 `CompatDevice` 用 `std::vector` 存 SaveDC 栈**：项目内 `SaveDC` 9 处、`RestoreDC` 10 处，嵌套深度都很浅；但若将来出现深递归保存，vector 的 realloc 会让保存的 `HGDIOBJ` 失效——目前保存的是句柄而非指针，故安全。
4. **线程安全**：与 Win32 一致，不加锁。
