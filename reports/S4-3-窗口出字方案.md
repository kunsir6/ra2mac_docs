# S4-3 方案：窗口客户区出字闭环

> 2026-11-10 14:30 · 本轮为 diagnose-only（检测到并发实例在跑 D3D11 presenter，零代码改动、零构建）
> 目的：把 S4 从「实现齐了但没法验收」推进到「可验收」。本文只定方案，不含代码改动。

## 一、为什么 S4 现在还不能标 done

S4 的 verify 是「菜单／HUD 文本渲染出可读内容」。S4-1 放回了 7 个字体 TU，S4-2 落地了 CoreText 真字形
光栅（135 checks / 0 failures），但**这两轮的所有断言都在测试自建的 DIB 上跑**：

- `compat/win32/selftest/CompatTextSemantics.cpp` —— 兼容层自测，画到 `CreateDIBSection` 的临时画布。
- 产品侧 3 个菜单字体类（MainSystemFonts / CampaignSystemFonts / HudSystemFont …）在 macOS 上
  只有 `concord_add_profiled_leaf` 注册进 `concord_runtime`
  （`cmake/MainSystemFontContracts.cmake:26-27`），
  **`concord_main_system_font_native_contract` 只建在 `if(WIN32)` 分支**（同文件 L15-23）。

结论：产品代码一次也没有把字画到「窗口」上过。屏幕上没有字，不是渲染错了，是**没人渲染**。

## 二、验收链已经存在，不需要新增兼容层代码

S7 选了纯离屏窗口后端（`compat/win32/src/RuntimeWin32CompatUser.cpp`），它恰好提供了端到端所需的一切：

| 能力 | 位置 | 事实 |
|---|---|---|
| 窗口客户区表面 | `ensureSurface` L156-182 | 每窗口一块 32bpp top-down DIB + 缓存 DC |
| 取绘制 DC | `BeginPaint` L696-710 / `GetDC` L682-687 | 直接返回缓存 DC，`rcPaint` = 整个客户区 |
| 消息驱动重绘 | `PostMessageW` / `DispatchMessageW` | 可投递并派发 WM_PAINT |
| 像素回读 | `BitBlt`（S2 已实现） | 窗口 DC → 测试自有 DIB |
| 存图给人看 | `Bitmap::Save`（S6 已实现） | DIB → PNG |

因此 S4-3 的全部工作 = **一个测试 TU + 一个 APPLE 分支的可执行 target**。

## 三、做法（下轮照此执行）

1. `cmake/MainSystemFontContracts.cmake`：在**既有** `elseif(APPLE)` 分支内追加
   `add_executable(...)` + include/compile_features + 链接 `concord_main_system_font_win32` 与兼容层。
   不动 `if(WIN32)` 分支内部任何一行。
2. 新增 `tests/ui/main_system_font/MainSystemFontWindowPaint.cpp`：
   - `RegisterClassExW` + `CreateWindowExW`，客户区 800×600；
   - 窗口过程 `WM_PAINT` → `BeginPaint` → 真实 `MainSystemFontsWin32::initialize()` →
     画英/中混排若干行（`DT_CENTER|DT_VCENTER`、含一个裁剪区、含一个 `DT_WORDBREAK` 长句）→ `EndPaint`；
   - `PostMessageW(hwnd, WM_PAINT)` + `DispatchMessageW` 触发；`GetDC(hwnd)` → `BitBlt` 回读。
3. 断言（都要能失败，不能只打印）：
   - 墨迹像素数 > 0，且逐字符串的墨迹包围盒落在预期前进宽度内；
   - CJK 字形覆盖非零（区分「画了 .notdef 方块」与「画了字」）；
   - 同一内容画两次逐字节一致（证明无非确定性）；
   - 客户区外像素未被写（裁剪/边界不越界）。
4. 用 S6 的 GDI+ 路径把客户区存成 PNG，作为肉眼验收物。

## 四、顺带修一处「静默丢弃」

`RuntimeWin32CompatGdi.cpp:1545` 的 `drawTextRun` 首行守卫是 `device->bitmap == nullptr → return`，
而录制型 DC 的 device 没有 bitmap（同一文件 L1759-1768 只挂 `recording`）。结果是
`TextOutW / DrawTextW / DrawTextA / ExtTextOutA` 在录制 DC 上**返回 TRUE、不画、不记录、不打日志**，
与图元族 10 处显式 `reportUnsupported("recording DC has no pixel surface")` 不一致。

处置 3 行：在守卫里对 `device->recording != nullptr` 打一条 `reportUnsupported`。不改行为，只让静默变显式。

目前未爆，是因为三个产品录制点都先合成到 memory DC 再 BitBlt；但 campaign 的 `completeFrameOnly`
与 loading 的 `unexpectedRecord` 都把「除 blit 外不许出现记录」写成硬断言——真有路径把文本画进录制 DC 时，
审计会通过、文本会消失。

## 五、本轮不改的三件事（及原因）

| 项 | 为什么押后 |
|---|---|
| DT_WORDBREAK / DT_END_ELLIPSIS | 产品在 `RuntimeCampaignMenuUi.inl:110` 真用这对 flag，现在超长标题直接溢出。但它是排版器（逐词度量 + 二分收缩），单独一轮更干净 |
| EMR_EXTTEXTOUTW | 录制 DC 目前是 blit-only 设计，三个产品录制点都不需要它；先做显式告警，等真有需求再实现记录类型 |
| 比例前进宽度 | `runAdvance(text, count, narrow, tall)` 签名里没有 FaceSpec，算不出比例宽度；要改就得把 FaceSpec 穿进 `rasterizeGlyph` 的掩码宽，波及 `Gdi.cpp` 4 处调用点。**在能看见字之前动它，会把「字排错了」和「字宽算错了」混成一个现象** |
