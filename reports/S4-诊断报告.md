## 1. 核心结论（推翻 queue 里对 S4 的风险判断）

queue 把 S4 描述为"全项目最难的一块，需要一个真实字形光栅器"。本轮实测：**文本族的"编译面"只差 2 个字符级的改动，不是差一个光栅器。**

对 `src/ui/text/win32/` 全部 7 个 TI 做只读 `-fsyntax-only -ferror-limit=0`（`-Icompat/win32/include -Isrc`）：

```
exit=1  errors=1  RuntimeCampaignScoreSystemFontWin32.cpp   static_assert(sizeof(wchar_t)==sizeof(char16_t)) → 4 == 2
exit=1  errors=1  RuntimeCampaignSystemFontWin32.cpp        同上
exit=1  errors=1  RuntimeHudSystemFontWin32.cpp             同上

```

**7 个 TU 全部只有 1 条错误，且都不是功能错误。** 去掉这两条，这 6 个 TU 就能进构建图，对应 P5-01 判定的类①c「前提 S4」的 29~30 个项目 C++ 符号。

依赖面也很窄——7 个 TU 用到的 Win32 token 去重后只有 18 个，其中已实现的 16 个：

```

OffsetRect   RGB           SelectObject  SetBkMode    SetTextColor  TextOutW  SendMessageW(已声明)
缺：WM_SETFONT / WM_GETFONT 常量（shim windows.h 2659 行里两个都没有）
```

`SendMessageW` 已声明但无实现（属 S7）。Skirmish 用它发 `WM_SETFONT`——在 mac 上是一条"无窗口即无意义"的消息，诚实 no-op 返回 0 即可，不影响出字（字体由 `SelectObject` 选定）。

## 2. queue 里 S4 要求先答的三个选型问题，实测答案

### ① 字体族名映射：不需要通用映射表，只需要 4 项

`CreateFontW` 全项目 17 次调用、8 个文件，字面量族名去重后只有 4 个：

| 族名 | 用语 |
|---|---|
| `Microsoft YaHei` | HUD 通知/航点标签 |
| `Microsoft YaHei UI` | 外交回退、战役、结算、遭遇战 |
| `Arial` | 战役评分 |
| `Arial Narrow` | 主菜单 |

另加 `DEFAULT_PITCH` / `CLEARTYPE_QUALITY` / `NONANTIALIASED_QUALITY` 三个质量档，字高 —18 / —16 / —14 三档。

结论：**映射表 4 项 + 一个缺省回退**，不需要 Windows 字体族名的通用解析。真正决定观感的是**字高档**（-18/-16/-14 = 像素字高），这可以直接对位到位图字体的 `charHeight`。

### ② 度量语义：爆炸半径只有 2 个调用点

`GetTextExtentPoint32W` 全项目**只有 2 处调用**：`HudSystemFontWin32::measure`、`RuntimePlayerDefeatNoticeSmoke.inl`。
`GetTextAlign` 4 处、`SetTextAlign` 5 处、`GetGlyphIndicesW` 1 处、`DrawFrameControl` 1 处（外交页复选框 fallback）。

也就是说 queue 里担心的"按钮居中全错位"**不成立**——菜单按钮的排版走的是位图文本（`RuntimeMainBitmapText` 等），不是 `GetTextExtentPoint32W`。度量契约只需要保证「量一次、画一次、两者同源」（P5-06 的 `fontMetricsFor` 单点实现正好是这个判据）。

### ③ CJK：位图字体覆盖不了，这是 S4 唯一的真实硬点

- 字符串字面量里的中文字符合计 **3026 个 / 48 个文件**（已排除注释，只统计引号内）。集中在 `RuntimeRandomMapMenu.inl`(202)、`RuntimeRandomMap.cpp`(201)、`RuntimeKeyboardMenu.inl`(195)、`RuntimeMatchReplayRuntime.inl`(172)、`RuntimeCampaignMenuController.cpp`(158)。
- 而确定的位图字库 `game.fnt` 有两份：`ConcordRTS-GameData/RedAlert2/GameMD/game.fnt`、`.../mix_exports/ra2/local/game.fnt`。Westwood FNT 是 CP1252 时代的单字节字库，**没有 CJK 字形**。
- 字体类选 `Microsoft YaHei` 这个 CJK 家族本身就说明：产品要出的中文只能来自系统字体，不可能来自 game.fnt。

**因此 S4 的诚实边界是**：
- 位图字体（`WestwoodFontCodec` + `Runtime*BitmapText`，**已在 macOS 构建图里**）负责英文/数字/标点，确定性、逐像素可断言；
- CJK 必须走 CoreText 回退，且与位图路径共用同一个 `fontMetricsFor`，否则中英混排的宽度会两套算法打架；
- 像素金标准断言只留给位图路径（CoreText 抗锯齿结果不可跨版本稳定）。

## 3. 路线判断：放回，而不是另写 Apple 后端

`src/ui/text/Runtime*SystemFont.h` 这 5 个接口头是**纯平台无关的**：只用 `char16_t`/`wchar_t` 模板参数（`BasicMainSystemTextRequest<Character>`）、`RuntimeInputPixelRect`、`RuntimeRgbColorValue`，**一个 Win32 类型都不出现**。

但 3 个菜单 TU（`RuntimeMainMenu.cpp` / `RuntimeCampaignMenu.cpp` / `RuntimeSkirmishMenu.cpp`）与 `RuntimeShell.cpp` 是**无条件** `#include "ui/text/win32/...SystemFontWin32.h"` 的，外面没有 `#if`。

于是只有两条路：

| 路线 | 代价 | 风险 |
|---|---|---|
| **A. 放回 6 个 win32 TU**（推荐） | shim +2 常量；6 处 `static_assert` 用 `#if defined(_WIN32)` 包住（纯新增行，Windows 侧逐字节不变），与 T-02 对 `sizeof(wchar_t)==2` 的处理同一套路 | 与 P5-01「不要为这些类写 macOS 平行实现」的原则一致，两套渲染路径不分叉 |
| B. 新写 `RuntimeMainSystemFontApple` 等 6 个后端 | 6 个新 .cpp + 改 4 个文件的无条件 include | 立刻制造两条实现路径，Windows 侧修复永不同步；违反 P5-01 明确写的「不要做的」 |

**选 A。** 顺带记录 A 的已知缺陷面（必须写在 RUNLOG 里，不能留到运行期才发现）：放回后宽路径是「u16 码元逐个扩宽成 wchar_t」。BMP 内码（含全部中文）逐码点等价、无损；只有**代理对**（emoji、BMP 外字符）会被拆成两个孤立码点。这与 T-02 记的风险是同一件事，不是新问题，但放回后它就从"编译面之外"变成"运行面之内"。

## 4. 下一轮建议

**优先 S4-1（放回 6 个字体 TU）**，因为它是本轮实测出来的、代价最小、收益最大的一步：

1. `compat/win32/include/windows.h` 追加 `WM_SETFONT 0x0030` / `WM_GETFONT 0x0031`（纯新增，紧邻既有 WM_ 常量块）；
2. 6 个字体 TU 的 `static_assert(sizeof(wchar_t)==sizeof(char16_t));` 用 `#if defined(_WIN32)` 包住（只在断言外新增两行，断言原文不动）；
3. 把这 6 个 TU 所在的 leaf 的 `if(WIN32)` 扩成 `if(WIN32 OR APPLE)`（P5-02 已建立的套路）；
4. `ninja -C build-product-mac -k 0 concord_runtime` + 重链接，预期缺口 **138 → 约 108**（30 个 C++ 字体符号）。

若 S4-1 超时，退路：S6（GDI+ PNG 导出，机械 45min）或 S8（multiplayer smoke，独立 target 不碰共享构建目录）。
