## 3. 根因一：Interlocked 不是"实参类型不匹配"，是**既有声明的类型宽度错**

- `compat/win32/include/windows.h:94` → `using LONG = std::int32_t;`（4 字节，符合 Win32）
- `compat/win32/include/windows.h:1484-1487` → 声明写的是 **`long`**，macOS/LP64 上 **8 字节**
- 调用点（`tests/.../RuntimeMultiplayerTwoProcessSmoke.cpp:33,52`）→ `volatile LONG status` / `volatile LONG sessionPort`（4 字节）

所以 10 条错误是"8 字节指针 vs 4 字节指针"，报 `no matching function` 是**对的**。

> ★ 最危险的地方在"绕过它"：如果为了让编译过而写成 `reinterpret_cast<volatile long*>(&status)`，
> 就会拿 **8 字节**的 `InterlockedExchange` 去写一个 **4 字节**字段，把相邻字段（`completedTick`）踩掉。
> 这个错误在两进程 smoke 里表现为"另一个进程的状态字随机变成垃圾"，在本机 x86_64 上还**不会崩**，
> 只会让断言偶尔红。签名必须钉在 32 位上，不能靠类型转换迁就旧声明。

`InterlockedExchangePointer` / `InterlockedCompareExchangePointer` 在 HEAD 只有声明、无定义，
链路缺口为 0 说明当前无人调用——不动它们。

## 4. 根因二（本轮最重要的新事实）：错误恢复掩盖了 **5 条**，所以"修完清单"修不干净

在影子树里把 queue 列的修复全部落地（常量 6 个 + 结构 + 3 个声明 + `_TRUNCATE` + Interlocked 改 `LONG`），
再跑同一条命令：

```
ERRORS: 5
:128:23  use of undeclared identifier 'OpenFileMappingW'
:200:5   use of undeclared identifier 'strncpy_s'    (did you mean 'strncpy'?)
:686:5   use of undeclared identifier 'strncpy_s'
:953:34  use of undeclared identifier 'SetInformationJobObject'
:1020:14 use of undeclared identifier 'SetInformationJobObject'
```

这 5 条在 HEAD 的 36 条里**一条都没出现**。机制：当同一个调用表达式里已经有错误实参
（`OpenFileMappingW(FILE_MAP_ALL_ACCESS, ...)` 的实参未声明；`strncpy_s(..., _TRUNCATE)` 的实参未声明），
clang 不再单独报"被调函数未声明"——于是这 5 条被完全遮住。

**连带纠正 queue 的一句话**：`SetInformationJobObject` 记的是"最后这个可能已有"——**没有**。
全仓（`compat/**` + `src/**` 的 .h/.inl）只有 `windows.h:21` 的一句注释提到它。`strncpy_s` 与
`OpenFileMappingW` 同样**任何头文件里都不存在**。

→ 结论：**如果照着 queue 的清单改，本轮会停在"还剩 5 条"，然后很可能被误判成"改出新错误"或"改坏了"，
再花一轮去查。** 这是本轮最有价值的产出。

## 5. `strncpy_s` 必须是**数组重载**，C 签名不够

调用点是 `strncpy_s(result.message, message.c_str(), _TRUNCATE)`，`result.message` 是 `char message[256]`
（`ProcessResult`，smoke:47）——**3 个实参**，走的是 Windows 的模板重载
`template<size_t N> errno_t strncpy_s(char (&)[N], const char*, size_t)`。

实测：先加 4 参 C 声明 `errno_t strncpy_s(char*, size_t, const char*, size_t);` → 仍 **2 条**
`no matching function for call to 'strncpy_s'`；再加数组模板 → **0 条**。

语义也要对：`_TRUNCATE`（`((size_t)-1)`）的含义是"**截断并返回 STRUNCATE(80)**"，不是"溢出即失败"。
Secure-CRT 的默认行为（溢出时把目标首字节置 0 并返回 EINVAL）在这里会**清空唯一的一行失败诊断**——
smoke:1050 的断言 `handles.shared->host.message[0] != '\0'` 直接依赖它。

## 8. 纠正 queue detail 的一句判断

queue 说这个 smoke "属于独立 target……不参与 concord_runtime 的编译，所以 ninja 建 concord_runtime 永远不会报它"。
前半对、**"产品构建图看不到"不准确**：`cmake/DevelopmentTargets.cmake:602` 的
`add_executable(concord_multiplayer_two_process_smoke ...)` 是**无条件**的（不在 `if(WIN32)` 里），
`ninja -C build-product-mac -t commands | grep RuntimeMultiplayerTwoProcessSmoke` **能抓到这个 TU**。
准确说法是：**它不是 `concord_runtime` 的依赖**，所以 `ninja concord_runtime` 不碰它；但完整 `ninja`（默认 all）
会尝试建它并失败，census 也把它算进分母（所以 census 的 30/31→31/31 是有效判据）。

## 9. 验证天花板（S8 做成也仍然成立的事实）

- Job 对象本轮**只声明不实现** ⇒ `concord_multiplayer_two_process_smoke` **仍然链接不出来**，
  两进程 smoke **一次都跑不了**。S8 的天花板就是 `-fsyntax-only 0` + census 分子 +1。
  把 S8 标 done 时必须把这句写进 RUNLOG，否则下一个读到 "S8 done" 的人会以为 smoke 跑过。
- `SetInformationJobObject` / `AssignProcessToJobObject` 返回 `bool` 是**权宜**：Win32 是 `BOOL`，
  且真实语义要靠进程组/信号在 macOS 上重新设计（`rules` 里已有 "S7 之后再说" 的判断，此处不推翻）。
- 跨进程内存序只有 `__ATOMIC_SEQ_CST` 一条路可走：本机 x86_64 是强内存模型，**任何内存序错误在这里都测不出来**，
  要到 ARM（Apple Silicon 目标平台）才有机会暴露。所以这条不能用"本机跑绿"当证据。
