# S9 · 小族收口：EMF / COM / 定时器 / MCI / MSVC CRT

2026-11-10 · 链接缺口 **280 → 267**，C-linkage **180 → 167**

---

## 1. 一句话结论

**13 个符号兑现，三个族归零。** 但这一轮真正的产出不是"少了 13 个未定义符号"（那只是
0.9% 的进度），而是**三个"换成表层等价物就会静默改变行为"的点被识别并钉住了**——
它们每一个都能编译、都能通过现有断言，然后让程序在别处错。

`CreateFileW` 的窄参重载被**刻意留在缺口里**，理由见 §6。

---

## 2. 13 个符号分三类，理由完全不同

| 类别 | 符号 | 为什么 |
|---|---|---|
| **可以诚实成功** | `CoInitializeEx` / `CoUninitialize` / `timeBeginPeriod` / `timeEndPeriod` | 它们要的**效果**在 macOS 上已经成立，返回成功是在描述结果状态 |
| **必须诚实失败** | `mciSendStringW` / `mciGetDeviceIDW` | 假装成功会让"音乐正在播"成立而一个采样都没出声 |
| **真实现** | EMF 4 个 + `_putenv_s` / `_wgetenv_s` / `gmtime_s` | 没有表层等价物，硬顶替就会改语义 |

### 2.1 CoInitializeEx 为什么返回 S_OK 而不是 RPC_E_CHANGED_MODE

两种返回在调用方看来"都能继续跑"，但契约不同：

```cpp
const HRESULT com = CoInitializeEx(nullptr, COINIT_MULTITHREADED);
impl_->uninitializeCom = SUCCEEDED(com);          // 成功 ⇒ 必须配对
if (FAILED(com) && com != RPC_E_CHANGED_MODE) { ...失败... }
```

- 返回 `S_OK` → `uninitializeCom = true` → 析构里调 `CoUninitialize`（本层空操作）。契约成立。
- 返回 `RPC_E_CHANGED_MODE` → 调用方**既不配对也不失败**，表面也能跑通。但它宣称
  "这个线程已被初始化成另一种模式"——一件没发生过的事。

撒谎换来的等价行为不值得，所以返回 `S_OK`。

### 2.2 timeBeginPeriod 返回 TIMERR_NOERROR 是不是在骗人

Windows 上它改的是**全局**定时器滴答（默认约 15.6ms），`Sleep(1)` 因此真能睡 1ms。
macOS 没有这个全局滴答：`nanosleep` 本身就是亚毫秒精度，调度器也不按 15.6ms 对齐。

所以返回 `TIMERR_NOERROR` 说的是**结果状态**——"你要求的 1ms 粒度为真"——而不是
"我调了一个内核接口"。唯一不成立的是 Windows 才有的副作用（别的进程也受影响），
而本项目没有任何代码依赖跨进程定时器精度。

### 2.3 MCI 为什么必须返回错误

`mciSendStringW` 的调用方判据是 `error == 0` 和 `mciGetDeviceIDW(alias) != 0`。
如果这里假装成功：

- `RuntimeMenuSound` 会认为音乐在播；
- `RuntimeMciPathProducerSmoke` 会认为取到了播放位置（它会去解析 `status ... position`
  的输出串，得到 0 → 由 `milliseconds == 0` 判据拦下，但那是运气好）；
- `RuntimeLegacyWaveDeviceWin32::open()` 里 `mciGetDeviceIDW(alias) != 0` 是"我真的持有
  通道"的唯一凭据，返回非 0 会让它建一个指向虚空的所有权。

返回 `MCIERR_DEVICE_NOT_INSTALLED`（306，取自 `mmsyscom.h` 的 `MCIERR_BASE + 50`，
值不是编的）让所有调用方一致地走"设备不可用"分支——这正是设备真的不存在时 Windows
给出的答案。

## 3. 三个"表层等价物会静默改变行为"的细节

这一节是本轮最有价值的部分。三个都是**能编译、能跑、断言照旧通过**的错误实现。

### 3.1 `_putenv_s(name, "")` 是**删除**，不是设成空串

项目里"关闭诊断"的写法是：

```cpp
_putenv_s("CONCORD_DEBUG_TURRET_FACING", "");
...
if (const char* value = std::getenv("CONCORD_DEBUG_TURRET_FACING")) { /* 打开了 */ }
```

如果实现成 `setenv(name, "", 1)`，`getenv` 会返回一个**非空**的 `""`，于是
`if (const char* value = ...)` 成立 → 诊断图形永远打开，而所有断言照旧通过。

MSVC 语义：`value_string` 为空串时把变量从环境中移除。实现里走 `unsetenv`。

自测直接钉住这一点（`CompatMiscSemantics.cpp:testPutenvRemoves`）：

```
check(std::getenv(kName) == nullptr,
      "空串表示**删除**变量：getenv 必须返回 nullptr，而不是指向 \"\" 的指针");
```

### 3.2 `_wgetenv_s` 的两段式调用必须两次给同一个 count

调用方的写法是"先查长度、再按长度分配、再读"：

```cpp
if (_wgetenv_s(&count, nullptr, 0, L"...") != 0 || count < 2) { error }
std::vector<wchar_t> text(count);
if (_wgetenv_s(&count, text.data(), text.size(), L"...") != 0) { error }
```

三种返回形态必须同时成立，差一个就断链：

| 情形 | 返回 | `*pReturnValue` | 缓冲 |
|---|---|---|---|
| 变量存在 | 0 | 所需元素数（含 NUL） | — |
| 变量不存在 | **0**（不是错误） | **0** | 空串 |
| 缓冲不足 | `ERANGE` | 仍给所需大小 | 空串 |

自测对三种都断言，包括"`ERANGE` 时 count 仍等于第一段查到的值"——这是扩容重试能成立的前提。

### 3.3 `gmtime_s` 的参数顺序与 `gmtime_r` **相反**

```cpp
gmtime_s(struct tm* tmDest, const std::time_t* sourceTime);   // MSVC
gmtime_r(const time_t* sourceTime, struct tm* tmDest);        // POSIX
```

两个都是两个指针，写反了**照样编译**（在 C 里更糟），运行期是往一个 `time_t` 大小的
位置写 `struct tm`——当场崩或静默错值。

自测用 1970-01-01 与 2023-11-14T22:13:20Z 两个时刻逐字段断言（年/月/日/时/分/秒/wday/yday），
参数写反时这些值全都不对。

## 4. EMF：为什么必须真做，以及"审计有效性"怎么测

### 4.1 假实现会让审计变成空断言

`RuntimeCampaignMenuUi.inl` 与 `RuntimeLoadingFrameStabilitySmoke.inl` 的写法是：

```cpp
HDC recording = CreateEnhMetaFileW(screen, nullptr, nullptr, nullptr);
drawCampaignMenu(state, recording, RECT{0, 0, size.x, size.y});
HENHMETAFILE frame = CloseEnhMetaFile(recording);
CampaignPaintAudit audit{size};
const bool recorded = frame && EnumEnhMetaFile(nullptr, frame, auditCampaignPaintRecord, &audit, nullptr);
...
if (!recorded || !audit.completeFrameOnly || audit.copies != 1) { /* 报错 */ }
```

这段代码存在的目的：**截屏看不出中间黑帧，指令流看得出**。它要抓的场景是
"重绘时先把窗口清黑、再贴最终帧"，那一瞬间的黑帧任何截图都拍不到。

如果 `EnumEnhMetaFile` 返回 TRUE 却不回调，`audit.copies` 是 0 → `copies != 1` 成立 →
**报错**。这个方向是安全的（假失败）。但如果记录下来的是空记录流同时还把 `copies`
预置成 1，就变成"永远通过"。所以这一层不能用桩。

### 4.2 实现

- `CreateEnhMetaFileW` 返回**录制型 DC**：`bitmap == nullptr`，`recording != nullptr`。
- `BitBlt` / `StretchBlt` 在录制型 DC 上不走像素路径，走 `emfRecordBlit`：
  把源位图连同 `BITMAPINFOHEADER` 一起**内嵌**进 `EMR_BITBLT` / `EMR_STRETCHBLT`。
  内嵌是必须的——EMF 是自包含指令流，回放时源位图早就被删了，照句柄回放等于读已释放内存。
- `CloseEnhMetaFile` 补 `ENHMETAHEADER`（108 字节）+ `EMR_EOF`（20 字节），
  回填 `nBytes` / `nRecords` / `rclBounds`，并**销毁录制 DC**（与 Windows 一致）。
- `EnumEnhMetaFile` 按 `nSize` 串下去回调；回调返回 0 则中止并整体返回 FALSE。

布局由 5 条 `static_assert` 钉住：`sizeof(ENHMETAHEADER)==108`、`sizeof(EMRBITBLT)==100`、
`sizeof(EMRSTRETCHBLT)==108`、`offsetof(EMRBITBLT,dwRop)==40`、`offsetof(EMRBITBLT,offBmiSrc)==84`。

> 顺带一提：最后两条我最初写成了 44 和 88（心算错），`static_assert` 当场否证。
> 这正是把布局写成断言而不是注释的价值——注释错了没人知道，断言错了编译不过。

### 4.3 自测的重点不是"能回放"

`CompatMetafileSemantics.cpp` 47 条断言，其中三条是这一层的真正验收标准：

1. **单帧** → 回放看到恰好 1 条 `EMR_BITBLT`，`completeFrameOnly` 成立，
   内嵌像素与源**逐字节**一致（`memcmp` 整幅 800×600×4）。
2. **人为多录一帧**（连做两次 BitBlt）→ 回放**必须**看到 2 条。
   这一条是"审计有效性"的证明：一个永远只报 1 条的记录器也能让第 1 条过。
3. **空录制** → 0 条拷贝，审计判**失败**而不是默认通过。

另外还断言了头部自洽：`nRecords == 3`、`nBytes == 108+100+40+800*600*4+20`。
这两个数一旦对不上，真实回放器读到一半就会断言失败——比"少一条记录"更难查。

## 5. 失败路径：宁可 FALSE，不要写一条回放时才暴露缺数据的记录

录制型 DC 只记录 `SRCCOPY` 位块传输。其余一律当场失败并在 stderr 说明：

| 调用 | 结果 | 理由 |
|---|---|---|
| `BitBlt(..., DSTINVERT)` | FALSE | DSTINVERT 要目标像素参与，录制型 DC 没有像素表面 |
| `StretchBlt` + `HALFTONE` | FALSE | `EMR_STRETCHBLT` 不带伸缩模式字段，放行等于静默降级成最近邻 |
| 源矩形部分越界 | FALSE | 目标尺寸不变而源变小，回放会拉伸错 |
| `CreateEnhMetaFileW(..., L"x.emf", ...)` | nullptr | 写文件未实现；假装写了会让"文件存在"类断言静默通过 |
| `EnumEnhMetaFile(..., const RECT*)` | FALSE | 缩放会让回调里的 cxDest/cyDest 与录制值不同，而所有审计都在比这两个值 |
| `PatBlt` / 像素级绘制 | FALSE（走"无位图"分支） | EMF 没有对应的记录类型；硬塞成 `EMR_RECTANGLE` 会改变语义（那条是描边+填充） |

这些在 Windows 上有的能成功，所以它们是**假失败**而不是假通过。方向是有意的。

## 6. CreateFileW 重载被移出 S9

原计划 14 个符号，实际做了 13 个。第 14 个是 S5a 为 `fs::path::c_str()` 自己加的
窄参 `CreateFileW(const char*, ...)` 重载——**只声明没实现，自造的债**。

查调用点后决定不还：

```
src/core/io/RuntimeAtomicFile.cpp:180        ← 生产路径：原子写文件
src/ui/input/diagnostics/...:224
src/audio/world/diagnostics/...:121,123
```

`RuntimeAtomicFile` 是"保存游戏"那条链路。而本层连宽版 `CreateFileW`、`ReadFile`、
`WriteFile`、`CloseHandle` 一个都没有。只补一个窄参重载，等于给这条链路留一个
**能编译、一调就崩**的入口——比留着链接错误更危险，因为链接错误会逼着人来看。

已拆成独立任务：文件与 HANDLE 族（含窄/宽两版 CreateFileW）。

## 8. 边界

1. **仍然没有可运行二进制。** 缺 267 个符号，所有结论上限是"编译干净 + 自测通过"。
2. **EMF 只被自己的自测跑过。** 产品的 `runCampaignMenuPaintSmoke` 需要
   `GetDC(nullptr)` 与 `CampaignDeviceBitmapWin32`，两者分别属 S3 与 P5-01，
   所以那条真实链路一次都没跑。
3. **EMF 记录不了文本。** `EMR_EXTTEXTOUTW` 未实现——`TextOutW` 本身还没实现（S4）。
   等 S4 落地后，录制型 DC 上的文本绘制要么补这条记录，要么显式失败。
4. **`mciGetErrorStringW` / `mciSendCommandW` 仍是"只声明"**，因为链接不引用它们。
   它们和 S5 那 16 个仅声明函数一样，属"声明了但没人调"的状态，不算完成。
5. **无 Windows 复核。** `MCIERR_*` 的数值取自 `mmsyscom.h` 的公开文档（`MCIERR_BASE + n`），
   `_putenv_s` / `_wgetenv_s` / `gmtime_s` 的语义取自 MSVC 文档与 C11 Annex K，
   都没有在真机上对拍过。
6. `timeBeginPeriod` 的 no-op 只对"单进程内精度"成立；跨进程精度影响在 macOS 上不存在，
   也没有代码依赖它。
