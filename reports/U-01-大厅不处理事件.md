# U-01 · 大厅点「開始遊戲」变彩虹圈

> 用户报告：从主菜单进入遭遇战大厅，点「開始遊戲」后鼠标变成彩色转圈，窗口画面不动。
> 结论：**不是点坏了，是整段大厅期间没有人处理 AppKit 事件**。已修，端到端验证通过。
> 提交：`a863d9e`

## 一、先取证，不猜

用户在现场卡着，进程还在（PID 59961），直接 `sample` 抓主线程：

```
main thread  1198 samples
  runRuntimeWindowSession
    runRuntimeSkirmishMenu +1292
      MsgWaitForMultipleObjectsEx  ← 1196/1198 样本
        std::this_thread::sleep_for → nanosleep → __semwait_signal
```

**不是死锁，也不是在加载**：主线程几乎全部时间停在"等消息"的睡眠里。
另外 2 个样本在 `IsWindow` —— 说明循环在正常转圈，只是每个 tick 都在睡。

## 二、根因：pumpEvents 只挂在 GetMessageW 上

compat 层有一条 Q-06 定下的约定：

```cpp
// GetMessageW 内
// Q-06：主循环是 compat 自己的 GetMessageW，不跑 NSRunLoop，
// 所以必须在这里主动排空 AppKit 事件——否则事件永远躺在 AppKit 队列里，
// 窗口看得见、点不动。pumpEvents 内部不阻塞。
concord_compat::apple::pumpEvents();
```

而遭遇战大厅的主循环**不经过 GetMessageW**：

```cpp
while (IsWindow(window)) {
    if (!PeekMessageW(&message, nullptr, 0, 0, PM_REMOVE)) {
        MsgWaitForMultipleObjectsEx(0, nullptr, 5, QS_ALLINPUT, MWMO_INPUTAVAILABLE);
        continue;      // ← 这里只是睡 5ms 再看队列，从不排空 AppKit
    }
    ...
}
```

于是从大厅打开那一刻起：**AppKit 事件队列没有人排空**。

| 表面现象 | 真实情况 |
|---|---|
| 大厅画面完整、中文标签正常 | 那是 `createShellSkirmishWindow + UpdateWindow` 画的第一帧，之后没再更新 |
| 鼠标悬停没有高亮、按钮点不动 | 点击事件躺在 AppKit 队列里，从未转成 WM_* 消息 |
| **点「開始遊戲」→ 彩虹圈** | 系统此时来查应用是否响应，发现 2 秒内没处理过事件 → 判定无响应 |

所以彩虹圈不是「点开始触发的」，而是**早就不响应了，点下去才被系统点亮**。

这也解释了为什么「主菜单」阶段一切正常：主菜单走 `GetMessageW`（会 pump）。

## 三、修法：把 pumpEvents 放进等待原语

改在 `MsgWaitForMultipleObjectsEx` 与 `WaitMessage` 的等待循环里（`compat/win32/src/RuntimeWin32CompatUser.cpp`）：

```cpp
for (;;) {
    concord_compat::apple::pumpEvents();   // 等待期间排空 AppKit
    { std::lock_guard<std::mutex> lock(userMutex());
      if (!messageQueue().empty()) return WAIT_OBJECT_0; }
    if (now >= deadline) return WAIT_TIMEOUT;
    std::this_thread::sleep_for(1ms);
}
```

选这个位置而不是各调用点，三条理由：

1. **语义正确**：Win32 的 `MsgWaitForMultipleObjects` 文档语义就是"等待期间处理消息"；
2. **不动共享代码**：`RuntimeWin32CompatUser.cpp` 是平台层文件（Windows 不编译），
   不需要在共享的菜单代码里加 `#ifdef __APPLE__`（多平台方案 §5.2 明确禁止）；
3. **一处修好全部调用点**：大厅就绪循环、世界循环、各类 smoke 的等待点都受益。

`pumpEvents` 自带 `gWindow == nil || gInputSink == nullptr` 前置判断，离屏 smoke 下立即返回，不影响既有离线路径。

## 四、顺带补一个可回归的入口

`CONCORD_SKIRMISH_AUTOSTART=<n>`：真实窗口的大厅里第 n 次循环后自动点一次「開始遊戲」，
走**与真人点击完全相同**的队列路径（`PostMessageW` 入队 → 本循环 `PeekMessageW/DispatchMessageW` 派发）。

没有它就无法在无人值守下回归"大厅 → 加载 → 世界"这条链路——而这条链路正是用户报障的那条。

## 五、验证

### 修复后采样（同一位置、同样方法）


892 个样本里 **314 落在 pumpEvents**，其余在派发与绘制。修复前该栈上是 **0**。

## 六、遗留

- **真人点击未复验**：本机没有辅助功能授权，无法合成真实鼠标事件。上述验证用的是
  `PostMessageW`，走的是同一条队列路径，但**"系统真的把点击送进来"这一步只有用户能确认**。
- 大厅里 `pumpEvents` 每轮最多占 2ms（其内部有界超时），最坏情况把 5ms 节流拉长到 ~8ms。
  60fps 不受影响（大厅本来就是低帧率脏刷新），但值得在 ON-2-06 的帧预算里记一笔。
- 若将来某个循环既不用 `GetMessageW` 也不用 `MsgWait*`（例如纯 `PeekMessage` 空转），
  它同样会拿不到输入——判定口径：**任何不调用这两个原语的等待循环都要自己 pump**。

## 七、后续（U-02）：进世界之后还是彩虹圈

U-01 修好大厅后，用户复测仍能看到彩虹圈。继续采样发现是**同一族的第二段**：

世界主循环既不调 `GetMessageW`，也不调 `MsgWaitForMultipleObjectsEx`：

```cpp
// RuntimeWindowHostWin32.cpp
bool drainMessages() { while (PeekMessageW(...)) { ... } }   // 纯 Peek
void sleepForIdleSlice() { std::this_thread::sleep_for(1ms); }  // 裸 sleep
```

进世界 9 秒后采样：1226 个样本中 **557 落在 `sleepForIdleSlice`**，`pumpEvents` 出现 **0 次**。
加载页同理：`pumpRuntimeLoadingWindow()` 每个 stage 只做
`InvalidateRect + UpdateWindow + PeekMessageW`，整段约 3 秒零 pump。

修法（`e142ccb`）：`PeekMessageW` 在队列为空时排空一次 AppKit 再重试出队，4ms 节流。
一处改动同时覆盖世界循环与加载页（后者每 stage 都会 Peek）。

验证：世界循环 `drainMessages → PeekMessageW → pumpEvents → nextEventMatchingMask`，
436 样本中 429 在 pumpEvents；加载阶段 219 样本在 pumpEvents 且 `loading complete` 正常。

**结论：彩虹圈不可能再长期挂着**——世界循环每 4ms 排空一次。若某个加载 stage 特别长，
系统可能短暂亮一下再自行消失，那属正常加载表现。
