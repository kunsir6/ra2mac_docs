# U-03 · 进了世界，点击没有任何效果

> 用户报告：调试过程中已经进到游戏世界（画面正常、FPS 56、侧边栏与单位都在），
> 但鼠标点击完全没反应，不报错、日志无异常。
> 结论：**输入被投给了已经退场的旧窗口**，另有两处 AppKit 默认行为让它更难察觉。
> 提交：`4b91741`（输入目标重绑）、`da1f8fa`（窗口输入属性）

## 一、主因：输入目标只绑一次

`compat/win32/src/RuntimeWin32CompatUser.cpp` 的 present 末尾：

```cpp
static HWND boundTarget = nullptr;
if (boundTarget == nullptr) {          // ← 只绑第一次
    boundTarget = toHwnd(w);
    setInputSink(&appleInputDispatch, boundTarget);
}
```

主菜单 → 大厅 → 加载页 → 世界，**每一跳都是新的 HWND**，而这个绑定从不更新。

于是：present 跟着新窗口走（所以画面完全正常、帧率正常），
而鼠标键盘全部 `PostMessageW` 到第一个窗口的句柄——那个窗口早已退场，消息被丢弃。
**不报错，因为投递本身是成功的；只是没人收。**

修法：一变化就重绑。修复后日志能直接看到三次切换：

```
[cocoa] input target -> 0x…aae0    （大厅 1024x640）
[cocoa] input target -> 0x…00e0    （加载页 800x600）
[cocoa] input target -> 0x…0700    （世界）
```

这一行日志本身就是补上的观测点：此前这类问题没有任何输出，只能靠"能看不能点"的体感。

## 二、次因一：鼠标位置永远不更新

开了 `acceptsMouseMovedEvents` 之前，AppKit 只在按键按住期间派发拖动，平时**没有
mouseMoved**。产品的 `WM_MOUSEMOVE` 因此永远不来，而世界里"点哪儿命中什么"依赖
`state.mouseClientPoint`——那个点只由 `WM_MOUSEMOVE` 更新。

结果不是"某一下丢了"，而是**每一下都用旧坐标判定**：看起来像"点击完全没效果"。

## 三、次因二：第一次点击被系统当激活动作吃掉

`NSView` 默认 `acceptsFirstMouse:` 返回 `NO`。窗口从非激活变激活时，系统把这次点击
当作"激活动作"处理，不派发给 view。表现是"第一下没反应，第二下才行"。

改用 `ConcordGameView` 子类返回 `YES`。

## 四、为什么既有 smoke 全绿却漏了这个

交互 smoke、大厅 flow smoke 都是**直接 `PostMessageW` 到自己手里的 HWND**，
完全绕过了"输入目标是谁"这一层。它们能证明窗口过程处理得对，但证明不了
"AppKit 的事件有没有送对地方"。

**口径：直接用 HWND 投消息的 smoke 覆盖不了输入绑定。** 要覆盖这一层，
必须让事件走 AppKit → 翻译 → sink → 队列 的完整路径。

## 五、验证

| 项 | 结果 |
|---|---|
| 输入目标切换 | 三次（大厅 / 加载页 / 世界），日志可见 |
| 大厅 → 加载 → 世界 | `loading complete`，世界 5–8 秒 170–280 帧，`EXIT=0` |
| 菜单 smoke | `rampPixels=1056,781,1428`（基线不变） |
| 遭遇战 smoke | `EXIT=0`，`maps=161 allPreviews=161` |
| 真机上屏自证 | 两帧 `match=yes` |

## 六、仍未验证

**真人鼠标点击**——本机没有辅助功能授权，无法合成系统级鼠标事件。
上述三条修复分别对应"送错窗口""坐标不更新""首点被吃"，都能从代码与日志确认，
但"点下去真的选中了单位"这一步需要用户手工确认。

排查工具（若仍不对）：`CONCORD_INPUT_TRACE=1` 会在每个翻译后的输入事件上打
`[input] kind=… x=… y=…`，可直接看出事件有没有到、坐标对不对。
