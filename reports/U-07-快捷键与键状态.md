# U-07 快捷键：Ctrl+数字编队不生效，根因是键状态表的两处缺陷

日期：2026-11-11 18:45

## 症状

用户实测：

> 我选中一个单位，按 T 是屏幕内相同单位全选。这个已经验证通过了。
> 但是我点 control+数字编队，没有生效。

即：不带修饰键的快捷键（T/P/M/N/Z/F/H/Q/W/E/R/K/L/O/A/B/C/J，以及纯数字选队）全部正常，
一旦叠加 Ctrl / Shift / Alt 就"按了没反应"。

## 排查顺序（为什么没能在绑定层发现）

绑定层是好的，而且是**一直被测试覆盖的**：

- `runtimePlayerCommandBindings()` 里 `TeamCreate_n = digit | runtimePlayerControlKey`（`RuntimePlayerCommands.h:45`）；
- `RuntimeTeamKeyController` 会比对 `input.code == host.binding("TeamCreate_1", '1'|Ctrl)`；
- `RuntimeTeamKeySmoke` / `KeyboardRouterContract` 等单测全绿。

问题在于这些测试都是**直接构造 `code`** 去比对，从不经过 `GetKeyState`。
真实链路是：

```
NSEvent(KeyDown/FlagsChanged)
  → appleInputDispatch            (compat/win32/src/RuntimeWin32CompatUser.cpp)
  → PostMessageW / DispatchMessageW
  → runtimeWindowProc(WM_KEYDOWN)
  → handleRuntimeKeyboardIngressKey
  → handleRuntimePlayerCommandKey
  → runtimePlayerCurrentKeyCode(WPARAM)        ← 在这里读修饰键
  → GetKeyState(VK_CONTROL) & 0x8000           ← 缺陷一 + 缺陷二
```

`runtimePlayerCurrentKeyCode` 是唯一把修饰键塞进 `code` 的地方（`RuntimePlayerCommandsUi.inl:3`），
它读 `GetKeyState`。所以只要这条路径断掉，绑定表再对也没用。

## 根因（两处，各自独立，都在 compat 层）

### 缺陷一：键状态表从来没人写

```cpp
SHORT GetKeyState(int nVirtKey) { return g_keyState[nVirtKey]; }   // 旧实现
```

`g_keyState[256]` 在 Windows 上由系统在输入排队/派发时维护。本层没有系统，
而唯一能写它的 `SetKeyboardState` **在整个产品里没有任何调用**（只有若干 smoke 用到）。
AppKit 桥接层 `emit()` 更直接：`FlagsChanged` 事件落在 `default: return;` 里被整体丢弃，
`out.keyCode` 只对 KeyDown/KeyUp 填充。所以这张表恒为零。

### 缺陷二：`GetKeyState` 的单位错了（更隐蔽）

就算有人把表写好，旧实现仍然不会生效：

- `GetKeyboardState` / `SetKeyboardState` 用的是**字节表**，按下 = 该字节 `0x80`（bit7）；
- `GetKeyState` 返回 `SHORT`，按 Win32 契约按下 = **bit15 (0x8000)**，bit0 才是锁存位。

旧实现 `static_cast<SHORT>(g_keyState[vk])` 把 `0x80` 留在 bit7，
于是产品里所有 `(GetKeyState(vk) & 0x8000) != 0` 的判据**恒假**。
实测有 20+ 处这样的判据（`RuntimePlayerCommandsUi.inl`、`RuntimeMapLeftPointerUi.inl`、
`RuntimeForceAttackHeldUi.inl`、`RuntimeCampaignMenu.cpp` 等）。

这一层是**先于**缺陷一的一层：只修"谁写表"仍然全红，而报错信息（"Ctrl+1 没建队"）
看起来完全一样，很容易被误判成绑定写错。

## 修法

1. `GetKeyState` 做位搬运（`compat/win32/src/RuntimeWin32CompatInput.cpp`）：

   ```cpp
   const unsigned char raw = g_keyState[nVirtKey];
   unsigned short value = 0;
   if ((raw & 0x80u) != 0) value |= 0x8000u;
   if ((raw & 0x01u) != 0) value |= 0x0001u;
   return static_cast<SHORT>(value);
   ```

2. 新增 `setVirtualKeyDown` / `clearModifierKeyDown` / `setModifierKeyState`，并让**每一条**输入路径都写表：
   - `appleInputDispatch`：KeyDown/KeyUp 先写表再 `PostMessageW`（顺序不能反，窗口过程在派发时就读）；
   - `DispatchMessageW`：`WM_KEYDOWN/SYSKEYDOWN/KEYUP/SYSKEYUP` 派发前写表 —— 合成消息因此与真键盘同语义；
   - `RuntimeAppleWindowSurface.mm` 的 `emit()`：**每个**事件先 `syncModifierState(event.modifierFlags)` 覆盖式同步
     （覆盖而非增量：处理"焦点从别的应用切回来"），`windowDidResignKey:` 清修饰键防止 Ctrl 卡住；
   - 鼠标消息 `wParam` 带上 `MK_SHIFT` / `MK_CONTROL`（Shift+点击加选、Ctrl+点击强制攻击依赖它）。

3. 顺手补上 F1–F12 的键码映射（见下节）。

### 为什么拆出一个新头文件

`.mm` 原本不碰 `windows.h`。第一次把 `RuntimeWin32CompatInternal.h` 引进去直接编译失败：
`Polygon` / `GetCurrentProcess` / `GetProcessInformation` 与 AppKit 的同名符号互撞
（`windows.h` 先声明，HIServices 的 `Processes.h` 再声明一份）。

改法是**收窄边界**而不是调换包含顺序：新增 `RuntimeWin32CompatKeyState.h`（不含 `windows.h`），
只暴露"抽象修饰位 + 虚拟键"两个概念，AppKit 常量 → `VK_*` 的映射留在 `.cpp` 里。
`Internal.h` 改为 include 这个小头，声明仍然只有一处。

## 附带发现：F1–F12 是死键

绑定表里 F 键是真被用到的，而且不小：

| 动作 | 键 | VK |
|---|---|---|
| `View1..View4` | F1–F4 | 112–115 |
| `SetView1..SetView4` | Ctrl+F1–F4 | 112–115 + Ctrl |
| `Taunt_1..Taunt_8` | F5–F12 | 116–123 |

而 `.mm` 的 `translateKeyCode` 只有 Esc/Enter/Tab/Backspace/Space/方向/Home/End/PgUp/PgDn/Delete。
F 键在 `characters` 分支里拿不到可打印字符，落到 `if (out.keyCode == 0) return;` 被丢弃——
**F 键完全没反应**。已按 macOS 硬件键码补齐 12 条映射。

这一条**没有端到端机器验证**（需要真键盘或辅助功能权限才能注入 NSEvent），
属于"映射已补、行为待真机确认"，与下面已验证的部分分开计。

## 验证

### 新增断言（`--interaction-smoke-test`，穿过消息循环）

在 `RuntimeShell.cpp` 的交互冒烟里、HUD 指针断言之后，新建一个 `WS_POPUP` 窗口（不上屏），
`PostMessageW → PeekMessageW → DispatchMessageW` 投递真实键消息：

1. 选 4 辆 HTNK；
2. 按 Ctrl 按下 → `1` 按下/抬起 → Ctrl 抬起；
3. 断言 `teams[0]` 恰好是这 4 辆（正向：修饰键生效）；
4. 清空选择 → 只按 `1` → 断言 `teams[0]` **没被改写**、且选择被找回（反向：Ctrl 没卡住）。

只测正向会漏掉"修饰键卡住"，那会让后续每次点选都变成建队。

修好前的输出（断言确实不是空转）：

```
HUD cursor: right=1016 top=8 frame=0 atlas=mouse
Interaction smoke test failed: Ctrl+1 did not create team 1 (GetKeyState probably reports no Ctrl).
```

修好后的输出：

```

Team keys: ctrl+1 create=4 units plain1 recall=1
```

（最后那行 `no owned structure for repair cursor` 是既有的 KNOWN-RED，见 EVO-10；

## 仍然缺的（诚实清单）

| 项目 | 状态 |
|---|---|
| 修饰键 → VK 映射（Shift/Ctrl/Alt/CapsLock） | 已修，机器验证 |
| 键状态表在每条输入路径写入 | 已修，机器验证（合成消息路径） |
| 鼠标 `wParam` 的 `MK_SHIFT`/`MK_CONTROL` | 已修，**未**单独断言（下游 Shift+点击加选仍靠既有 smoke） |
| F1–F12 键码 | 映射已补，**未**端到端验证（需真键盘） |
| `GetAsyncKeyState` | 仍恒返回 0；产品只有 GPU 输入追踪用到（Windows 分支），未修 |
| `MapVirtualKeyW` | 仍恒返回 0；键盘重绑定的"按键名显示"依赖它，未修 |
| 小键盘 / 标点键 | 绑定表未使用，未映射 |

结论：**"红警快捷键适配完全了吗"的答案是"没有"**——常用字母/数字/方向/编队/视角这一档现在是通的，
但 F 键刚补、`GetAsyncKeyState` 与 `MapVirtualKeyW` 仍是空实现。后者只影响键盘重绑定界面的显示，
不影响游戏内操作，优先级低于 EVO-08。
