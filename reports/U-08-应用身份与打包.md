# U-08 App 身份：图标显示空白、名字还是构建名

日期：2026-11-11 19:00

## 症状

用户：

> 红警的app图标，app名称，还没有同步到位

实际观测（不是猜测，下面每条都有命令与输出）：

- Finder 里这个 app 的名字是 `ConcordRTS-0.1.0-arm64.app` —— 版本号与架构一起进了显示名；
- Dock/Finder 的图标是**空白占位图**（浅蓝蓝图网格），不是尤里的复仇封面。

```bash
$ mdls -name kMDItemDisplayName "dist/ConcordRTS-0.1.0-arm64.app"
kMDItemDisplayName = "ConcordRTS-0.1.0-arm64.app"

# 用系统自己的解析器问"这个 app 现在长什么样"
$ osascript -l JavaScript -e 'ObjC.import("AppKit"); ... NSWorkspace.iconForFile(...)'
→ 1024×1024，内容是通用应用占位图（不是封面）
```

包里 `.icns` 文件确实存在（2 MB，`CFBundleIconFile` 也对得上）。**"文件在"不等于"系统认"**，
这是这件事最容易误判的地方。

## 根因（三条，各自独立）

### 一、图标是无 alpha 的方块图，IconServices 直接不采用

源图 `packaging/icon-source.png` 是 256×256、`space=RGB`、`hasAlpha=no` 的封面位图。
打包脚本当时是「sips 缩 10 个尺寸 → iconutil → .icns」。两个后果：

1. 十帧标准命名的 iconset，`iconutil` 直接判 **`Invalid Iconset`**（实测）；
2. 侥幸生成出来的 icns，IconServices 也不采信，回落成空白占位图。

macOS 的应用图标要求按它的网格来：**1024 画布、内容 824 居中、圆角半径约 185、四周透明**。
不是审美问题——Dock 里系统图标都按这个网格排，满幅方图在旁边一眼就偏大偏方。
而纯 RGB 图既没有透明边距，也不可能自带圆角。

### 二、显示名把版本号与架构带了进来

`CFBundleName` / `CFBundleDisplayName` 都被 `CONCORD_MACOS_APP_NAME` 填成了
`ConcordRTS-0.1.0-arm64`。那是**构建标识**（要用它区分 arm64/x86_64 两份产物），
不该是玩家看到的字符串。Finder 显示的是 `CFBundleDisplayName`，于是名字就是它。

### 三、同一个 bundle id 被登记了 18 次

```
org.concord.rts.arm64  ← ~/.Trash 里 7 份、build 目录 1 份、dist 两份（含 .stale）
org.concord.rts        ← AppTranslocation 2 份、build 三个目录的 ConcordRTS.app.stale
org.concord.rts.x86_64 ← 2 份
```

`lsregister -dump` 数出来的。LaunchServices 按 id 解析图标与显示名，命中哪一份是**不确定**的；
`.app.stale` 这种名字也会被当成应用登记（它只是文件名后缀，里面 Info.plist 一应俱全）。
所以即便新包的 icns 是对的，Finder 也可能拿旧记录回答。

## 修法

### 1. 图标生成器 `packaging/make-icon.py`（新）

- 用 Pillow 按 macOS 网格合成：1024 画布 → 824 内容 + 半径 185 圆角 → 透明边距 → 烘一层阴影
  （Big Sur 之后的图标阴影是图里带的，系统不再补）+ 1px 内高光；
- 等比铺满裁切，不拉伸；
- 再切 10 帧标准尺寸交给 `iconutil`；
- `--no-mask` 分支：源图自带 alpha/外形时只做等比缩放，不重复套壳。
  这样以后换图（任意尺寸 PNG）不需要改代码。

### 2. 打包脚本改用生成器，并补 plist 项

`packaging/make-app-bundle.sh` 的图标环节换成调用 `make-icon.py`，中间 iconset 放 `mktemp -d`
（不再往 `build/` 或 `dist/` 里留 10 张 PNG）。
`packaging/Info.plist.in` 增加 `LSApplicationCategoryType = public.app-category.strategy-games`
（"显示简介"里的类别）与 `CFBundleDevelopmentRegion = zh_CN`。

### 3. 交付打包脚本 `ra2mac_docs/scripts/pack-dist.sh`（新）

以前 dist 是手工 `cp` 二进制进 `.app` 再 `codesign`——只换了可执行文件，身份三件事（名字/图标/登记）一件没动。
现在一次到位：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| ① 归档 | 旧包 → `dist/.archive/<名字>-<时间戳>.app`，并 `lsregister -u` | 不留可双击的旧包在 dist 根，也不让它继续抢图标解析 |
| ② 清理历史登记 | 废纸篓、`build-product-*/app`、`*.app.stale` 逐个注销 | 同 id 18 份登记是"改了包还是老样子"的直接原因 |
| ③ 组装 | 调 `make-app-bundle.sh`（图标/plist/data-root/签名） | 单一入口，避免再手搓 |
| ④ 登记 | `lsregister -f` 新包 | — |
| ⑤ 验证身份 | 读回 plist 的 displayName / identifier / icon 引用并比对 | 防止拼错名字 |
| ⑥ 验证图标 | 现场造一个**没有图标**的空壳 bundle 作参照，分别向 IconServices 要图，比较平均像素差 | 「文件存在」不是判据；"和空白占位图不同"才是 |
| ⑦ 验证可运行 | 包内二进制跑 `--smoke-test` | 交付形态必须能跑 |

## 关于「一个应用、两个入口」

用户选择：名字用 `红色警戒2 尤里的复仇`，但《红色警戒 2》与《尤里的复仇》应当是**同一应用的两个可区分入口**。
按这个口径，外层只保留一个 app 名，区分放在应用内：

- `RuntimeCampaignMenu.cpp` 的 `campaignEditionSuffix()` 会给战役名加后缀
  「（红色警戒 2）」/「（尤里的复仇）」，选择器按 `source` 分组；
- 遭遇战/地图列表共用同一套数据树。

**但内容侧要如实说明**：当前战役库里**只有基础版 RA2**。实测：

```
$ ./concord_runtime --campaign-smoke-test | 按 id 前缀统计
ra2-gdi            44
ra2-nod            36
ra2-tutorial        4
（没有任何 yr-* 条目）
Campaign retail coverage gate: maps=40 objectives=27 events/actions/scripts/movies/sources/audio=FAIL
```

尤里复仇的战役数据在数据树里是有的（`local_data/resources/mix_exports/langmd/missionsmd.pkt`），
但战役数据库没有把它接进来。也就是说：**名字里写着"尤里的复仇"、外壳也是 YR，
但战役选择器今天只能选到红色警戒 2 的战役。** 这是内容缺口，不是打包问题，已单独立项（见队列 EVO-13）。

顺带一项事实：基础版规则其实齐了（`mix_exports/ra2/local/rules.ini`、`art.ini` 都在），
所以将来做"双入口"（两个 .app 各带一份 config）在数据上不是死路，只是需要先接 YR 战役、
并把规则文件选择做成可配置项。

## 没做的

- 图标源图只有 256×256（封面原画），放大到 1024 略软。换一张 1024 原图即可，
  重新跑 `pack-dist.sh` 就生效，不需要改代码。
- 封面右下角的 "Westwood STUDIO" 字样在原图里就被裁掉一半，图标里随之可见。
  这是原图内容，没有修图。
- LaunchServices 里仍有旧 id（`org.concord.rts*`）在废纸篓等位置的**历史登记残留**。
  它们和新 id（`org.concord.rts.yuri.arm64`）不同，抢不到新包的图标；彻底清需要
  `lsregister -kill -r` 重建整个数据库，会影响本机其它应用，本轮没做。
