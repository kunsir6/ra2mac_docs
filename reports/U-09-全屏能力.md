# U-09 全屏：绿灯是「+」，点下去是缩放不是全屏

日期：2026-11-11 20:45

## 症状

用户：

> 全屏能力还没有实现。左上角那个绿色的全屏按钮显示的是一个 + 号，不是全屏操作

观测到的两件事，其实是同一个原因的两面：

- 绿灯图标是「+」（AppKit 给**只能缩放**的窗口画的符号）；
- 系统全屏能力根本没开——窗口创建时 `collectionBehavior` 被设成
  `NSWindowCollectionBehaviorFullScreenNone`（ON-2-04 的定案）。

## 根因：ON-2-04 的结论本身是错的

ON-2-04 当时的记录是「系统全屏走不完：`windowWillEnterFullScreen` 触发了，
`windowDidEnterFullScreen` 永远不到，于是把这一位设成 FullScreenNone」。
那个现象是真的，但归因错了。

U-09 用四个一次性探针（`/tmp/fsprobe.m`、`/tmp/fsprobe2.m`）穷举了当时被怀疑的四个前提：

| 变量 | 取值 | 结果 |
|---|---|---|
| 是否 `[NSApp run]` | 不跑，手动 pump | willEnter → didEnter → willExit → didExit 走完 |
| 事件处理深度 | 只出队、不 `sendEvent` | 走完 |
| 激活策略 | `Accessory` | 走完 |
| run loop 切片 | 2ms `nextEventMatchingMask` | 走完 |

**四种组合全部走完，frame 变成屏幕尺寸。**所以「没有 `[NSApp run]`」不是障碍。

真实前提是时间线：ON-2-04 早于 U-01/U-02。那两轮修之前，主循环里有大段路径
**根本不 pumpEvents**（世界循环纯 `PeekMessageW` + 裸 `sleep_for`，大厅循环走
`MsgWaitForMultipleObjectsEx` 而不进 AppKit）。全屏切换是 AppKit 的动画状态机，
拿不到 run loop 时间就停在 `willEnter` 之后，看起来就像「didEnter 永远不来」。
U-01/U-02 把 `GetMessageW` / `PeekMessageW` / `MsgWaitForMultipleObjectsEx`
三处都接上 pump 之后，这个前提已经不存在了。

## 修法（五处）

### 一、`collectionBehavior = NSWindowCollectionBehaviorFullScreenPrimary`

只有这一档才是系统认可的「可全屏」形态：绿灯显示展开箭头、`Ctrl+Cmd+F` 可用。
条件也齐了——窗口本来就是 `Titled | Closable | Miniaturizable | Resizable`，
全屏要求的前置（可缩放）满足。

### 二、退回不能在通知栈里发

第一版在 `windowDidEnterFullScreen` 里直接再调一次 `toggleFullScreen:` 想退回。
实测被 AppKit 丢掉：日志停在 `entered`，之后既没有 `willExit` 也没有 `didExit`，
进程带着一个全屏窗口跑完了整个 smoke。改成置 `gFullScreenExitPending`，
由下一帧 `present()` 在**主循环栈**里发起——同一件事在主循环里做就没问题。

### 三、判据改写：hash 降级为诊断

原判据要求「全屏前后内容 hash 不变」，前提是「全屏期间游戏不重绘」。
但遭遇战界面一直在动（光标闪烁、背景动画），进出一段都报 `ok=0`，
而画面完全正常。改成三项：`contents` 还在、`CGImage` 尺寸仍等于呈现尺寸、
全屏期间确实又呈现过帧（证明呈现路径没断）。hash 仍打印，但不参与判定。

### 四、自测改走用户那条路：点绿灯

原来的自测直接调 `[window toggleFullScreen:nil]`。这只能证明「窗口能全屏」，
**证明不了「绿灯接在全屏上」**——而用户报障的正是后者。改成
`[[window standardWindowButton:NSWindowZoomButton] performClick:nil]`：
点的是那个按钮，走的是它的 action。若 8 帧内没有任何 `willEnter`，才退回
`toggleFullScreen:` 并**如实打印**是哪条路生效的。

实测：`request via green button` → `willEnter` → `entered`，全程按钮路径，
`viaButton=1`。这就是「绿灯现在是全屏按钮」的直接证据。

### 五、顺带修掉的：全屏后鼠标坐标会整体错位

这一条不是用户报的，是上一条修完必然踩到的。画面按
`contentsGravity = kCAGravityResize`（放大用 `kCAFilterNearest`）铺满整个 view，
而鼠标坐标原来是 view 坐标**直接**当客户区坐标交给游戏的：

```cpp
out.x = lround(local.x);
out.y = lround(gView.bounds.size.height - local.y);   // 只翻 y，不缩放
```

只有「view 尺寸恰好等于呈现表面」时才对。全屏之后 view 是 1512×949、
表面还是 800×600，点屏幕正中会报 (756,474)，游戏在 800×600 里命中，**永远打空**。
（ON-2-03 放开任意拉伸时这个错就已经在代码里了，只是默认窗口尺寸恰好等于表面，
没人踩到；全屏把它变成必现。）

抽出 `mapViewPointToSurface()`：按表面/view 比例反算并夹在 `[0, 表面-1]`。
view == 表面时比例是 1，行为与原来逐位一致，不影响既有路径。

## 没能验证的，和已知特性

- **绿灯图标的像素级验证没做成。** 想直接对比「+ 还是箭头」，但这台机器的
  Accessibility 未授权：`System Events` 查 AX 属性直接 `-10004 权限违例`，
  合成鼠标点击也进不去（点了绿灯窗口纹丝不动）。进程内读绿灯的 AX 子角色
  （`AXFullScreenButton` vs `AXZoomButton`，正是图标的判定源头）返回 nil——
  AX 元素是懒创建的，没有 AX 客户端连上来查不到。
  所以判据换成两层：①形态（`FullScreenPrimary` + 可缩放）；②**行为**
  （点绿灯真的进全屏）。第②层比图标本身更硬：只能缩放的窗口，点绿灯永远进不了全屏。
- **全屏是把 800×600 的呈现表面放大到整屏，不是按屏幕分辨率重绘。**
  放大用 `Nearest`，非整数倍比例下像素块会大小不均（横竖纹）。这是 ON-2-03
  「任意拉伸铺满、不做整数倍 letterbox」的直接后果，不是本轮引入的。
  要真正按显示器分辨率出图，得让渲染表面尺寸跟随窗口——那是另一件事，已记 EVO-14。
- **全屏尺寸随显示器变。**两次跑分别是 1800×1130 与 1512×949（显示器/空间状态不同），
  两次都 `ok=1`。自测断言的是「窗口尺寸 = 屏幕尺寸 + 内容没丢」，不是某个固定数值。
