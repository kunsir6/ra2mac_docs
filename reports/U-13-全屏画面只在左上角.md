# U-13 全屏后画面缩在左上角，右下全黑

日期：2026-11-12 00:10

> **更正（2026-11-12 00:35，见 U-14）**：本报告把目标定成"让 1024×640 的画面铺满全屏"，
> 那是**放大**，不是用户要的"更多显示空间"。用户随后澄清：全屏后单位仍是原来的像素
> 大小、一屏要能容下更多内容。正确的修法是把客户区尺寸交给游戏（`ResizeSink`），
> 由游戏按全屏尺寸重绘 1:1 的画面。本文保留的是**诊断过程**（为什么画面缩在左上角）
> 与"present 不得在全屏期间改窗口几何"这条结论；"拉伸铺满即正确"这一判断已被推翻。

## 症状

用户截图：进了全屏，但游戏画面只有 1024×640 那一块贴在屏幕左上角，右侧和下侧整片黑。
菜单阶段进全屏看起来是好的，所以问题只出现在"全屏 + 换了界面尺寸"的时候。

## 复现（把用户那条路走成可重复的）

用 `--skip-main-menu --skip-skirmish-menu` 直接进世界，让全屏在 **800×600 的加载画面**
上发生，然后世界以 1024×640 呈现：

```
[cocoa] NSWindow created 800x600 ...
[fullscreen] entered window=1800x1130 view=1800x1130 ... ok=1
[cocoa] NSWindow resized to 1024x640        <-- 病根
```

窗口是全屏的 1800×1130，view 被这句话改回 1024×640。

## 根因：present() 里"表面尺寸变了就改窗口几何"没有排除全屏

`RuntimeAppleWindowSurface.mm` 的 `present()`：

```cpp
} else if (surface.width != gPresentedWidth || surface.height != gPresentedHeight) {
    gPresentedWidth = surface.width;
    gPresentedHeight = surface.height;
    [gWindow setContentSize:contentRect.size];   // 全屏窗口被系统接管，这句要么被吞、
    gView.frame = contentRect;                   // 要么直接把窗口踢出全屏
}
```

这条分支本来是为"换界面"写的（遭遇战 800×600、主菜单 1024×640），前提是**窗口态**。
全屏时窗口尺寸由系统接管成屏幕大小，而这里按*表面*尺寸去设 view —— 窗口仍是
1800×1130，view 变成 1024×640 贴在左上角，右下全黑。

而 `contentsGravity=kCAGravityResize` 本来就会把 1024×640 的画面拉满整个全屏窗口，
**什么都不做才是对的**。所以 U-09 那轮"全屏能力"虽然判据都过了（它只看窗口尺寸、
内容还在、指针映射），却漏了"画面占没占满客户区"这一维——判据里根本没有它。

## 修复

1. `present()`：表面尺寸变化时先看窗口是不是全屏（`styleMask` 的 `FullScreen` 位，
   或 `gFullScreenEntered`）。全屏就**只更新 `gPresentedWidth/Height`，不动窗口/view**，
   并打 `surface changed to WxH while fullscreen: keep window geometry`。
2. 退出全屏（`windowDidExitFullScreen`）置一个 pending 标志，由下一帧 `present()`
   在主循环栈里把窗口恢复成当前表面尺寸——全屏期间表面尺寸可能已经变过（加载 800×600
   → 世界 1024×640），不补这一步退出后窗口会停在屏幕大小、画面被拉成非 4:3。
   （不在通知栈里改窗口状态，是 U-09 就踩过的坑。）
3. **判据补上**：`checkFullScreenState` 增加 `viewTracksWindow`——全屏时 view 必须和
   窗口一样大（全屏窗口没有标题栏，frame 就是内容尺寸）。原来的 `contents` / `size`
   两项在这个 bug 下都是"正常"的，只有这一条能抓出来。

## 新增调试开关（都是环境变量，生产零开销）

| 变量 | 作用 |
|---|---|
| `CONCORD_FULLSCREEN_SELFTEST=1` | 走真·绿灯点击进全屏（原有） |
| `CONCORD_FULLSCREEN_SELFTEST_DELAY=N` | 等 N 帧再点绿灯，用于"等世界画面起来之后才进全屏" |
| `CONCORD_FULLSCREEN_STAY=1` | 停在全屏不自动退回（抓图用） |
| `CONCORD_FULLSCREEN_STAY=N`（N>1） | 在全屏停 N 帧再退回（验退出路径） |
| `CONCORD_PRESENT_GEOM=1` | 每 60 帧打一次窗口/view/layer 几何 + gravity + 图片尺寸 |

`CONCORD_PRESENT_GEOM=1` 的输出就是这次定案的直接证据：

```
[geom] frame=900 win=1800x1130 fullscreen=1 view=1800x1130
       layer.bounds=1800x1130 layer.frame=1800x1130 gravity=resize scale=2.00 img=1024x640
```

窗口、view、layer 三者同尺寸且 gravity=resize ⇒ 1024×640 的图必须被拉伸铺满。

## 教训

- **判据要跟着症状走**。U-09 的判据是"窗口进没进全屏、内容还在不在、指针映射对不对"，
  用户报的是"画面占没占满"——三种都不是。现在 `viewTracksWindow` 把这一维钉住了。
- 负责"改窗口尺寸"的分支必须显式排除全屏：全屏期间窗口几何归系统，我们只能改表面尺寸
  和 layer 内容。
