# U-14 全屏 = 更大的视口，不是把画面放大

日期：2026-11-12 00:35

## 需求澄清（这一条推翻了我上一轮的做法）

用户原话：

> 全屏的目标不是把游戏画面放大。是有更多的显示空间，内部的单位还是显示那么大，
> 可以容下更多内容了。

也就是说，全屏后的正确形态是：

- **单位、建筑、侧边栏的像素大小不变**（还是原来那一个游戏像素 = 一个点）；
- **客户区变大**（1024×640 → 1800×1130），多出来的地方显示**更多地图**；
- 而不是把 1024×640 的画面拉伸到 1800×1130——那等于把整个游戏放大 1.76 倍，
  视野反而没变（U-13 的修复就是这种"放大"，方向错了）。

## 为什么"拉伸铺满"做不到

`contentsGravity = kCAGravityResize` 只能把**已经画好的那张图**拉伸到 view 大小。
游戏的世界视口是按 `GetClientRect` 算的（`runtimeMapViewport(clientRect)`），
后缓冲也是按客户区尺寸建/重建的（`ensureRuntimeBackBuffer(state->backBuffer,
paintDc, clientWidth, clientHeight)`）。只要兼容层的客户区还是 1024×640，
游戏就只会画 1024×640 的内容。

结论：**要让游戏自己知道"屏幕变大了"**，必须把兼容层的窗口矩形改成全屏尺寸，
让它按新客户区重排重绘。渲染器本身早就支持任意尺寸——`RuntimeFullscreenPerformanceSmoke`
就在 1280×720 / 1920×1080 / 2256×1504 / 2560×1440 / 3840×2160 上逐个跑过
paint 与缓存一致性，所以这不是新能力，只是**没人把全屏尺寸告诉游戏**。

## 修复

### 1. 新增跨界回调（`RuntimeAppleWindowSurface.h`）

```cpp
using ResizeSink = void (*)(int width, int height, void* context);
void setResizeSink(ResizeSink sink, void* context);
```

尺寸用**点**而不是 backing 像素：`layer.contentsScale` 已经负责 2x 放大，
游戏侧只认逻辑像素。

### 2. Cocoa 侧（`RuntimeAppleWindowSurface.mm`）

| 时机 | 动作 |
|---|---|
| `windowWillEnterFullScreen` | 记下进全屏前的内容区尺寸 `gWindowed*BeforeFullScreen`（此刻窗口还是窗口态，是唯一时机） |
| `windowDidEnterFullScreen` | `applyFullScreenViewport` → 回调 `gResizeSink(view.w, view.h)`；在 `if (!gFullScreenTest) return` **之前**，属于产品行为 |
| `windowDidExitFullScreen` | 回调 `gResizeSink(0, 0)`，语义 = "恢复进全屏前的尺寸" |

`present()` 的退出收口也改成按 `gWindowed*BeforeFullScreen` 恢复（全屏期间
`gPresented*` 已经是 1800×1130，照它恢复等于没退出）。

### 3. 兼容层（`RuntimeWin32CompatUser.cpp`）

- `ensureSurface`：**尺寸变化时重建客户区位图**。原来是"建好就一直 return true"，
  客户区被改成 1800×1130 之后 DIB 还是 1024×640，游戏画的与呈现的范围脱节。
  为此在 `CompatWindow` 上加了 `surfaceWidth/surfaceHeight` 记账。
- `appleResizeRequest`：改 `windowRect` 尺寸 → `PostMessageW(WM_SIZE)` → `InvalidateRect`，
  并记住"进全屏前的客户区尺寸"以便恢复。绑定点与输入接收方同一个（present 目标变化时）。

### 4. 镜头居中（`RuntimeShell.cpp`）

只 clamp 的话 `worldOffset` 不变，画面锚在左上角：多出来的 776×490 全在右下，
玩家的基地被挤到角落（第一版截图就是这样）。新增
`runtimeRecenterCameraForViewportChange`：客户区尺寸变化的那一帧把偏移按
`-(Δ/2)` 平移，**保持镜头中心的世界坐标不变**，再交给 `ensureRuntimeCameraForViewport`
做边界收敛。

只在尺寸变化那一帧动一次，之后的帧 `previous == current` 直接返回，
不与玩家滚动/跟随逻辑打架。

## 判据（这次的关键）

U-13 的判据（`contents` / `size` / `viewTracksWindow`）在"拉伸铺满"下**全都报 ok=1**——
它们只证明"窗口满了、图还在"，证明不了"图是不是被放大的"。补一条：

```objc
// 全屏期间出现过 surface 尺寸 == 内容区尺寸 的帧 ⇒ 1:1，没有缩放
[fullscreen] coverage: surface=1800x1130 == view=1800x1130 after 1 frame(s) — 1:1, no scaling
```

`checkFullScreenState("exited")` 把 `coverage` 计入判定；`entered` 阶段只打印
（此时还没重绘，必然为 0）。

## 教训

- **"全屏"要先问清语义**。我按"画面铺满"修了一轮，用户要的是"视野变大"——
  两者的判据完全不同：前者看 view 里有没有黑边，后者看 surface 与 view 是否 1:1。
- 拉伸一张小图永远不会让游戏看到更多内容；**尺寸必须回到产生画面的那一层**
  （客户区 → 后缓冲 → 视口），UI 层的 gravity 只能改"怎么显示"，不能改"显示什么"。
- 改了客户区尺寸就要同时处理**镜头锚点**，否则功能对了、观感像"被推到角落"。
