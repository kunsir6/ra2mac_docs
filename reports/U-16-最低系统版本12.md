# U-16 最低系统版本降到 macOS 12（Intel 机能启动）

## 诉求

> 我把游戏交到另外一台 intel 芯片的电脑了，但是提示系统版本太低了

追问后确认目标机是 **macOS 12 Monterey 或更高**。

## 症状

`.app` 拷到 Intel 机上，双击弹「系统版本太低」，没有任何更具体的信息，日志也指不到原因。

## 根因：声明与实际的"最低版本"是两件事

macOS 上"能不能启动"由两处**互不相干**的声明决定：

| 位置 | 键 | 谁看它 | 作用 |
|---|---|---|---|
| `Info.plist` | `LSMinimumSystemVersion` | Finder / LaunchServices | 只影响界面提示 |
| Mach-O | `LC_BUILD_VERSION.minos` | **dyld** | 真正决定加载还是拒绝 |

本机交付物当时的状态：

```
Info.plist  LSMinimumSystemVersion = 11.0     ← 声称支持 macOS 11
Mach-O      minos = 27.2                      ← 实际要求 macOS 27.2
```

`minos 27.2` 的来源是**没有设置** `CMAKE_OSX_DEPLOYMENT_TARGET`——CMake 默认跟着本机 SDK 走，于是二进制把构建机的系统版本写成了自己的下限。plist 里的 11.0 是打包脚本手写的常量，两者从来没有对账。

结果：Finder 按 plist 认为"可以打开"，dyld 按 minos 拒绝加载，用户看到的就是那句笼统的「系统版本太低」。

## 修复

### 1. 构建参数：把 minos 降到 12.0

两个架构都要重新配置（`CMAKE_OSX_DEPLOYMENT_TARGET` 只存在于 `CMakeCache.txt`，改它意味着全量重编）：

```
cmake -S ConcordRTS -B ConcordRTS/build-product-arm      -DCMAKE_OSX_DEPLOYMENT_TARGET=12.0
cmake -S ConcordRTS -B ConcordRTS/build-product-x86_64   -DCMAKE_OSX_DEPLOYMENT_TARGET=12.0
```

为什么不是 10.15 / 11.0：libc++ 直接拒绝——`The selected platform is no longer supported by libc++.` 12.0 是这套工具链能编的最低档，也正好覆盖用户那台机器。

### 2. 唯一的编译失败点：浮点 `std::from_chars` 需要 macOS 26

降目标后只有一处编不过：

```
src/data/maps/MapDatabase.cpp:167:14: error: 'from_chars' is unavailable: introduced in macOS 26.0
```

libc++ 把**浮点**版 `from_chars` 标了 `availability(macos 26.0)`（`__charconv/from_chars_floating_point.h`），整数版没有这个限制。原写法用它解析 ini 里的实数，等价于把整份二进制钉在 26。

改为 `std::strtod`，并显式保留原来 `from_chars` 的三条约束：

- 必须吃完整串（`parseEnd == value.c_str() + value.size()`）——原来靠 `result.ptr == end`；
- 溢出算失败（`errno == ERANGE`）；
- 非有限值算失败（`std::isfinite`）。

为什么 `strtod` 在这里安全：进程从不调用 `setlocale`，始终是 `"C"` 区域，小数点就是 `.`，与 `from_chars(general)` 的语义一致。整数解析（`parseIntValue`）继续用 `from_chars`，不受影响。

### 3. 遭遇战冒烟："换了 edition 拿到新对象"的判据不能用地址

降目标后 `skirmish` 从 PASS 变 RED-NEW，稳定复现：

```
Skirmish shell smoke failed: preload/reentry contract.
```

同一个数据目录、改动前的二进制（minos 27.2）跑却 PASS，所以是构建参数变化引入的。

根因:冒烟要证明"换 edition 之后是**新对象**而不是复用缓存",原来比的是裸指针地址。而 `prewarmedMenuState.reset()` 释放后，下一次同尺寸分配**极可能落在同一地址**——指针相等退化成"永远相同"，`editionFresh` 恒为假。minos 变化只是改变了分配顺序，把这个一直存在的脆弱判据暴露了出来。

修法：给 `MenuState` 加 `instanceSerial`（`std::atomic<std::uint64_t>` 自增），两处身份比较改用序号。序号不会被地址复用骗到。

### 4. 打包脚本：常量对齐 + 硬门禁

`pack-dist.sh` 的 `MIN_MACOS` 从 11.0（隐含）改为 **12.0**，并新增第 ⑦ 步校验：

1. plist 的 `LSMinimumSystemVersion` 必须等于脚本的 `MIN_MACOS`；
2. 二进制**每个架构切片**的 `minos` 必须等于 `MIN_MACOS`；
3. 不满足就 `exit 1`，并打印重新 configure 的完整命令。

为什么做成硬门禁而不是注释提醒：这个坑的形态就是"两个数字悄悄不一致"，人眼对不出来，只有机器能对。加了门禁之后，`pack-dist.sh` 不再可能产出一个声明与实现不配对的包。

实测门禁（把 `MIN_MACOS` 改成 27.2 跑一遍）：

```
pack-dist: x86_64 切片的 minos=12.0，与 MIN_MACOS=27.2 不一致。
  plist 声明的最低版本是 27.2，二进制实际要求 12.0。
  两者不等时，系统按 plist 放行、dyld 按 minos 拒绝，用户只会看到笼统的
  「需要更新 macOS」而拿不到真正原因。
  重新构建（两个架构都要）：
    cmake -S ".../ConcordRTS" -B <build-dir> -DCMAKE_OSX_DEPLOYMENT_TARGET=27.2
rc=1
```

## 验证

| 项 | 命令 | 结果 |
|---|---|---|
| 架构 | `lipo -archs dist/尤里红警.app/Contents/MacOS/concord_runtime` | `x86_64 arm64` |
| plist 声明 | `PlistBuddy -c "Print :LSMinimumSystemVersion"` | `12.0` |
| arm64 实际 | `vtool -arch arm64 -show-build` | `minos 12.0` |
| x86_64 实际 | `vtool -arch x86_64 -show-build` | `minos 12.0` |
| x86_64 切片能跑 | `arch -x86_64 … --smoke-test`（Rosetta） | rc=0，`World loaded: yes`，地形 16218 格 / 建筑 10 个 |
| 包内冒烟 | `pack-dist.sh` 第 ⑧ 步 | `rc=0` |
| 全量回归 | `regress.sh` | **PASS=5 KNOWN-RED=6 RED-NEW=0** |
| minos 一致性门禁 | 故意把 `MIN_MACOS` 改成 27.2 | `rc=1`，提示准确 |

x86_64 切片单独跑一次是必要的：交叉编译能链接成功不代表那个切片能执行，而 `pack-dist.sh` 的冒烟只会跑**本机原生**架构，x86_64 那一半一直在盲区里。

### 拷到另一台机器的数据根

`Contents/Resources/data-root` 里写的是**构建机上的绝对路径**。目标机上它必然失效，但探测器会继续往下走（`runtimeLocateDataRoot` 的 ⓪→①→②→③→④），所以：

- **推荐**：把 `ConcordRTS-GameData` 放在 `.app` 的**同级目录**，什么都不用改；
- 或者设 `CONCORD_DATA_ROOT=/path/to/ConcordRTS-GameData`；
- 或者手工把 `Resources/data-root` 改成新路径，然后 `codesign -s - --force "尤里红警.app"` 重签。

实测（把 `.app` 拷到 `/tmp/xfer/`，把 `data-root` 改成不存在的路径，数据目录做邻居）：

```
[config] data root /private/tmp/xfer/ConcordRTS-GameData (source=sibling)
World loaded:     yes
```

数据目录缺失时的诊断是完整的，会告诉用户要求什么样的目录布局：

```
[config] data root NOT found: game assets will not resolve at startup.
[config]   rule: a data root must contain BOTH local_data/ and RedAlert2/
[config]     current dir    : /private/tmp/xfer
[config]     executable dir : /private/tmp/xfer/尤里红警.app/Contents/MacOS
[config]   no near-miss: no candidate had local_data/ or RedAlert2/ at all
```

## 遗留

- **`CMAKE_OSX_DEPLOYMENT_TARGET` 没有写进 `CMakeLists.txt`。** 它只活在两个 `CMakeCache.txt` 里，新建构建目录会退回本机 SDK 版本（即 minos 27.2）。没有顺手全局 pin 的原因是：全项目 321 个测试可执行文件都得跟着重编，其中若有用到 macOS 26 符号的（同类 `from_chars` 浮点问题），会让 `ninja all` 编不过。当前 1444 个对象只重建了 `concord_runtime` 那条链。要彻底收口需要单独一轮：全局 pin + 全量构建 + 逐个修。
- 那 321 个测试二进制现在还是 11-11 14:02 的旧产物（minos 27.2），所以**回归跑的是 12.0 的 `concord_runtime`，但部分 smoke 可执行文件仍是 27.2**——这不影响交付物，但意味着"开发工具链仍绑在高版本"。
- `CONCORD_MACOS_MIN_VERSION`（cmake 里，默认 11.0）与 `pack-dist.sh` 的 `MIN_MACOS` 仍是两个独立真值源。当前交付走 `pack-dist.sh`，cmake 那条 bundle 路径没人用，暂时无冲突。

## 教训

1. **"最低系统版本"有三处，必须同时真**：构建参数（minos）、plist 声明、以及不用高版本才有的符号。改一处等于没改。
2. **声明与实现要机器对账**。人眼对不出 `11.0` 与 `27.2` 的差别，但一行 `vtool` 可以。凡"两个数字必须相等"的地方，都该有断言。
3. **降部署目标会暴露一直存在的脆弱判据**。`skirmish` 的地址比较不是这次改坏的，是这次被照出来的——顺手修掉比回滚好。
4. **交叉编译的切片要单独执行一次**。链接成功 ≠ 能跑，`pack-dist.sh` 的冒烟只覆盖原生架构。
