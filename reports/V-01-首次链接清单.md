# V-01：第一次链接与 280 个未定义符号

**一句话结论：编译图已经干净了——14/14 个编译步骤全部成功，`ld` 第一次给出了权威清单：280 个未定义符号。
其中 180 个是兼容层该兑现的 Win32/CRT 接口，100 个是 Apple 构建图整片裁掉的 Windows 专属实现层。
这个比例说明剩下的活不是"补 API"，而是"逐个文件判断该放回还是该重写"。**

本轮同时完成 P2-04 第二轮（`xapobase.h` / `ks.h` / `ksmedia.h`），
过程中静态断言抓出两处**真实的布局错误**——它们都不会让编译失败，只会让功能静默失效。

---

## 1. 这一轮到底发生了什么

前四轮的收尾结论一直是"只剩一个编译失败 TU"。把 `RuntimeVoiceAudio.cpp` 的三份依赖头补齐之后：

```
[1/14] … [13/14] Building CXX object … RuntimeShell.cpp.o
[14/14] Linking CXX executable concord_runtime
ld: symbol(s) not found for architecture x86_64
```

`exit=1` 是**预期**的。链接失败本身就是交付物：在此之前，所有"还缺什么"的判断都建立在
编译错误上，而编译错误只反映头层；`ld` 反映的是**实现层**。

280 个数字比"5 个失败 TU"有用得多，因为它可以分区、可以排期、可以对账。

不是换 API 名）。它属于"让它不被引用"，而不是"实现它"。

## 3. 本轮真正的技术发现：两处不会报错的布局错误

这一轮写的是三份"声明层"头文件，但价值不在补声明，而在 `static_assert` 抓出来的两件事。

### 3.1 `WAVEFORMATEX` 少了 `pack(1)`

Windows SDK 的 `mmreg.h` 用 `pshpack1.h` 包住 `WAVEFORMATEX`，所以它是 **18 字节、无尾部填充**。
我们的 shim 是自然对齐，于是 **20 字节**。

字段偏移**碰巧完全相同**（`cbSize` 都在 16），所以"读字段"永远是对的。错的是三件事：

1. `sizeof(WAVEFORMATEX)` 对不上；
2. `cbSize == 22` 这条 `WAVEFORMATEXTENSIBLE` 判据算不平（18 + 22 = 40）；
3. `reinterpret_cast<const WAVEFORMATEXTENSIBLE*>(format)` 时 `Samples` 落到 **20** 而不是 **18**。

第 3 条是静默错值：`RuntimeAudioPeakLimiter::validFormat()` 会拿到错位的
`wValidBitsPerSample`，把合法格式判成不合法，于是**限幅器永远不生效**——
音频不削顶、不报错、不打印，什么都看不出来。

修法：`#pragma pack(push, 1)` + 钉住 `sizeof(WAVEFORMATEX) == 18` 与 `offsetof(cbSize) == 16`。

### 3.2 `KSIDENTIFIER` 写成了扁平结构体

真实 `ks.h` 用 **union** 让 `{Id, Flags}` 与 `GUID` 的前 8 字节重叠，整体 **16 字节**。
我按"GUID + Id + Flags"写成扁平结构体，得到 **24 字节**。

没有代码读 `Id`/`Flags`，所以这不影响行为；但它说明一件事：**照着字段列表抄结构体是错的**，
必须先确认它是 union 还是 struct。修法：只留 `GUID Set`，另给 `id()` / `flags()` 访问器
（`flags() = Data2 | Data3<<16`，即小端下真实 union 的解释），布局回到 16 字节。

### 3.3 `XAPO_REGISTRATION_PROPERTIES` 的 56/64

我算成 56（漏数了一个 `UINT32`：它是 7 个标量不是 6 个），断言当场纠正为 64。
这条没什么深意，但它演示了这类断言的正确用法：**先写下你相信的数字，让编译器去否证**。

## 4. `CXAPOBase`：可实例化的基类，不是纯虚壳

`RuntimeAudioPeakLimiter` 是项目里**真实的 DSP**（116 行峰值限幅器，纯数学），
它 `final : public CXAPOBase`，且**不重写 `Release`**。所以：

- `Release()` 的销毁责任只能落在基类；
- 基类要正确销毁派生对象就**必须**有虚析构；
- 真实的 COM `IUnknown` 没有虚析构（删除必须由叶子类的 `Release` 完成）。

这是一个刻意的取舍：**牺牲"逐字节 vtable 对齐"，换取"引用计数正确"**。
理由是本层 vtable 不跨二进制边界，没有第三方按真实布局读它；而引用计数错了就是每次建引擎泄漏一个限幅器。

这条决定用 ASAN 的 UAF 探测证明了，而不是靠推理：

```
AddressSanitizer: heap-use-after-free on address 0x6040000003d0
freed by thread T0 here:
    #1 RuntimeAudioPeakLimiter::~RuntimeAudioPeakLimiter() RuntimeAudioPeakLimiter.h:10
    #2 CXAPOBase::Release() xapobase.h:162
0x6040000003d0 is located 0 bytes inside of 40-byte region
```

释放栈里出现的是**派生类析构**——虚析构真的生效了，`Release()` 到 0 真的把对象还给了堆。
（`detect_leaks` 在 macOS 的 ASAN 上不支持，所以用 UAF 反证，而不是等泄漏报告。）

## 5. 验证输出（单一入口）

```
$ scripts/verify-win32-compat.sh

1/4 头层声明自测（仅编译）
  ok    395 个函数声明与全部常量可编译
2/4 头层内联语义自测（编译并运行）
  ok    compat header selftest (inline): 67 checks, 0 failures
3/4 GDI 实现语义自测（CMake 目标 + 运行）
  ok    80 checks, 0 failures
4/4 XAPO / CXAPOBase 语义自测（项目真实限幅器）
  ok      25 checks, 0 failures

全部通过
```

新增的第 4 步（`concord_win32_compat_xapo_selftest`，25 checks）覆盖的不是"能编译"，而是：

- 32-bit float 立体声被接受；mono / int16 PCM / 低于 `XAPO_MIN_FRAMERATE` 被拒；
- `WAVEFORMATEXTENSIBLE` 的 `IEEE_FLOAT` 子格式被接受，`PCM` 子格式被拒
  （这条直接依赖 3.1 的修法——`cbSize == 22` 与 `SubFormat` 的位置都必须对）；
- 1.5 峰值被限到 ≤ 1.0，且**两声道同增益**（不是逐声道压缩 pumping）；
- `XAPO_BUFFER_SILENT` 输出零；`enabled=FALSE` 直通；
- 引用计数 `1 → 2 → 1 → 0` 且归零即销毁；`QueryInterface` 只认 `IUnknown`。

## 6. 边界：这一轮没有证明的东西

1. **没有可运行的二进制**。链接失败，所有结论的上限是"编译干净 + 符号清单准确"。
   没有任何一行代码在 macOS 上被执行过（除了三个自测 TU）。
2. **架构是 x86_64**。CMake 探测 `CPU ISA=x86_64`，`ld` 也报 `architecture x86_64`。
   如果目标机是 Apple Silicon，这个产物只能靠 Rosetta 跑。是否要出 arm64 是独立决定，
   已写进 `rules.arch_note`——不能默认。
3. **构建配置目前把三条呈现路径都关了**：`sdl3-window=OFF sdl3-audio=OFF metal-present=OFF
   software-present=ON`。也就是说 S7 的"用 SDL3 做窗口后端"这个前提现在**不成立**，
   而 brew 又因 macOS 版本号 26.7.1 崩过。S7 的第一步应该是选型，不是写代码。
4. `XAPOBASE_DEFAULT_FLAG` 的数值（`INPLACE_SUPPORTED|INPLACE_REQUIRED`）本机无法核对 SDK；
   它是惰性的（本层不读 Flags），但接了真实 XAudio2 后就必须复核。
5. 字体度量、文本排版、EMF 回放——这三块**一个字节都没验证**，而且它们压在 30 个符号下面。
