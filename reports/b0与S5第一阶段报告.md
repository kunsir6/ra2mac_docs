## 1. b0：146 条级联错误，根因是一行漏掉的 include

### 现象

上一轮把 `compat/win32/include` 接进 include 路径后，`RuntimeShell.cpp` 报 **146 条**
`no member named 'X' in namespace 'std::__1'`。此类错误看起来像 shim 破坏了 libc++。

### 定位

`RuntimeShell.cpp` 第 **243** 行开了一个 anonymous namespace，而第 **21848–21849** 行的
mid-file include 落在它**内部**（花括号深度实测 = 1）：

```
#include "ui/selection/RuntimeSelectedPathBatch.h"
#include "ui/selection/RuntimeSelectedPathRaster.h"   →  #include <list>
```

于是 libc++ 的 `<list>` 在 `namespace { ... }` 里展开，`_LIBCPP_BEGIN_NAMESPACE_STD`
开出的 `std` 落在匿名命名空间内 → `std::list` 全部失效。

把这两个头单独放到文件作用域编译是**零错误**，因此问题不在 shim。

### 决定性实验

不猜，直接验证：

```
c++ ... -include list RuntimeShell.cpp
```

**146 条级联错误全部消失**，降到 385 条真实的声明缺失。假设成立。

### 根因

第 204–238 行的标准库 include 按字母序排列：

```
#include <limits>      ← 222
#include <map>         ← 223   ← 这里本该有 <list>
#include <memory>      ← 224
```

**`<list>` 从一开始就漏了。** Windows 上它被其它头（真实 `windows.h` 的连带面比 shim 大得多）
提前引入过，include guard 让 21848 行那次 include 成为空操作，所以这个缺陷在 Windows 上永远不会显形。
shim 的连带面更小，缺陷就暴露了。

### 修法

一行，插在字母序正确的位置：

```cpp
#include <limits>
#include <list>
#include <map>
```

**为什么这不算"给 macOS 打补丁"**：补一个漏掉的标准头，在任何平台上都是正确且零行为变化的改动；
它让 macOS 的编译单元与 Windows 的**实际**编译单元一致，而不是新增平台分支。

## 3. 顺带修掉三个真实缺陷

### 3.1 `ICM_QUERY` / `ICM_OFF` 的值是反的（S1 遗留 bug）

S1 写的是 `ICM_OFF 1` / `ICM_QUERY 3`。windwingdi.h 的真实值是 **`ICM_QUERY=1` / `ICM_OFF=3`**。

后果很隐蔽：`RuntimeTerrainViewportFill` 与 `RuntimeRadarPixelStore` 都用
`SetICMMode(dc, ICM_QUERY) != ICM_OFF` 断言"没有色彩管理介入"，两个常量互换后这个断言
**仍然碰巧成立**（1 != 3 与 3 != 1 都为真），但语义已经错了。已按 Win32 校正。

### 3.2 `LONG_MIN / LONG_MAX` 的取值域

`RuntimeStructureSpriteGeometry.inl:104`：

```cpp
const RECT viewport{LONG_MIN / 2, LONG_MIN / 2, LONG_MAX / 2, LONG_MAX / 2};
```

shim 把 `LONG` 定为 `int32_t`（必须如此，否则 `RECT` 会从 16 字节变 32 字节），
但 `<climits>` 的 `LONG_MIN` 在 macOS 上来自 64 位的 `long` → `LONG_MIN/2 = -4.6e18`，放不进 `LONG`。
Windows 上 `LONG_MIN` 就是 `INT_MIN`，`/2` 后是 `-1.07e9`。

处理：在 `windows.h` 末尾按 Win32 语义覆写 `LONG_MIN`/`LONG_MAX`/`ULONG_MAX`，
并在文件头部先 `#include <climits>`，使后续任何 `<climits>` 变成空操作、不会重定义。
已用 `static_assert(LONG_MIN == -2147483647L - 1)` 与 `sizeof(RECT)==16`、`sizeof(BITMAPINFOHEADER)==40` 钉住。

### 3.3 GDI+ 只是一个 PNG 出口

`RuntimeMapRenderer.cpp` 里 `#include <gdiplus.h>` 是 fatal error。普查后确认全仓库只有 **3 处**
引用 GDI+，且**全部只为把像素写成 PNG 诊断图**（muzzles-N.png、调色板审计图）——
渲染结果本身不经过 GDI+。

因此新增 `compat/win32/include/gdiplus.h`（约 130 行，仅声明）：
`GdiplusStartup`、`GdiplusShutdown`、`GetImageEncodersSize`、`GetImageEncoders`、
`ImageCodecInfo`、`Bitmap`。`Bitmap::Save` 同时提供 `const wchar_t*` 与 `const char*` 两个重载，
理由与 `CreateFileW` 相同——`fs::path::c_str()` 在 POSIX 上是窄字符。

`PixelFormat32bppRGB` 取 **0x00262008**。这个值写错不会编译报错，只会让导出 PNG 的通道次序错，
所以按 GDI+ 的编码规则（通道数 | 位深<<8 | 标志位）核算后固定下来。

## 4. T-01 的两类形态，处理方式完全不同

### 形态一：`std::max(1L, LONG运算)`

macOS 上 `LONG= int`、`1L = long` → 模板推导冲突。**不能把 shim 的 `LONG` 改成 `long`**：
macOS 的 `long` 是 64 位，`RECT`/`BITMAPINFOHEADER` 会从 16/40 字节变成 32/72 字节，位图格式彻底不兼容；
更糟的是结算数学会在 64 位下不再按 32 位回绕，属于**静默的模拟结果差异**。

只在调用点收敛：`std::max<LONG>(1L, x)`。Windows 上 `LONG` 就是 `long`，
`std::max<LONG>` 与默认推导是**同一个实例化**，行为逐位相同。

已处理 10 处（`RuntimeShell.cpp` 6、`RuntimeDiplomacyPage.inl` 1、`RuntimeDiplomacyPageSmoke.inl` 1、
`RuntimePlayerHotkeysUi.inl` 2），另有 1 处 `std::min` 在 `RuntimePlayerDefeatNoticeSmoke.inl`。

### 形态二：`fs::path::c_str()` 的窄宽差异

POSIX 上返回 `const char*`，Windows 上返回 `const wchar_t*`。`CreateFileW(path.c_str(), ...)`
在 Windows 天然匹配、在 POSIX 完全不匹配。

处理：在 shim 里给 `CreateFileW` 补一个 `const char*` 重载（放在 `extern "C"` 之外——
C 语言链接同一个名字只允许一个函数）。调用点一行不改，也不需要 `#ifdef` 分叉。

### 形态三：多声明符 `auto`

```cpp
const auto count = u32(p + 4), start = p + 8;   // macOS: uint64_t vs size_t → 推导冲突
```

`size_t` 在 LP64 上是 `unsigned long`，`uint64_t` 是 `unsigned long long`——宽度相同但**类型不同**；
Windows 的 LLP64 上二者同为 `unsigned long long`，所以恰好一致。拆成两条声明，语义不变。

## 5. `wchar_t` 宽度：一处真转码，一处必须跳过

这是 S1 报告里点名的高风险项，本轮第一次真正撞上。

### 5.1 真转码（`RuntimePlayerHotkeysUi.inl`）

```cpp
std::u16string runtimeChatTextDraftFromWide(std::wstring_view text) {
    static_assert(sizeof(wchar_t) == sizeof(char16_t));   // macOS 上必挂
    for (wchar_t unit : text) result.push_back(static_cast<char16_t>(unit));
```

只删断言会**静默截断** BMP 外的码点（`U+1F600` → 两个非法码元）。
已改为 `#if defined(_WIN32)` 保留原逐单元路径，`#else` 走真正的 UTF-32 → UTF-16 转码（含代理对拆分），
反向同理（含孤立代理项替换为 `U+FFFD`）。Windows 分支逐字节未变。

### 5.2 必须跳过（`RuntimeChatTextSmoke.inl`）

这个 722 行的探针以**冻结的 Windows oracle** 为基准：断言 `wchar_t` 是原生 UTF-16、
用真实 HWND 回放 `WM_CHAR`/`WM_KEYDOWN`、并逐字节比对 `oldWin32ChatUtf8` 的输出语料。
POSIX 上 `wchar_t` 是 32 位，断言、语料、预期行为三者都不成立，硬跑只会得到**假失败**。

已整体 `#if defined(_WIN32)` 包住，非 Windows 侧返回一个显式打印
`skipped (frozen Windows oracle requires native UTF-16 wchar_t)` 的桩。
**不伪造通过**——这条要能在日志里被看见。

## 8. 一个方法上的教训

上一轮我写"b0 要先精确定位那个跨 2 万行的命名空间闭合点"——**判断错了**。
正确做法是先做一次**决定性实验**（`-include list`）直接验证因果，再决定要不要动那个
89k 行的文件。实验成本 2 分钟，定位成本估算是数小时。

同理，"这批诊断代码必须退出构建图"这个上一轮的结论也有一半是错的：
`GR_GDIOBJECTS` 根本不该排除，它对应的是可实现的 `GetGuiResources`。
**先量后定**这条要一直执行到数据推翻自己的结论为止。
