`AdrianLuo` 的提交基本是**阶段快照**：`32ab245 非 Windows 核心实际运行，平台边界验收通过`

`kun_sir` 是**改动单元**：中位 2 文件 64 行，最大的两条也是「一个主题一整块」
（`6ff9b0d9 S2-S10 兼容层实现` 9,990 行 / 18 文件），仍能按 commit 回滚。

### 2. 可复核性（提交正文是否给得出证据）

这是差距最大的一项。

| 指标 | kun_sir | AdrianLuo |

| 正文带可复核证据（数字/读数/缺口/断言计数） | **97 / 117 = 82%** | **0 / 22 = 0%** |
| 非空正文比例 | 82% | 86% |

两边都写了正文，但性质完全不同：

- `kun_sir` 给的是**读数**，例如
  `pending=0 power=650 aboard=5 —— 5 人全部真实进入，生物反应堆段转绿`、
  `缺口 280→109`、`混音 52/40 断言全绿`。任何人事后都能重跑复现。
- `AdrianLuo` 给的是**结论性概括**，例如
  `完善 GPU 资源重建、后端配置及异常恢复…验证数据寿命、任务同步和稳定绘制顺序，记录性能结果`。
  他 22 条提交全部是这个句式——有「验收通过」，但没有任何可执行的复核路径。

## 二、结论

| 维度 | kun_sir | AdrianLuo | 判 |
|---|---|---|---|
| 原子性 | 中位 2 文件 / 64 行 | 中位 38 文件 / 4381 行 | kun_sir 明显优 |
| 可复核性 | 82% 带读数 | 0% | kun_sir 明显优 |
| 可追踪性 | 50% 挂队列编号 | 无编号体系 | kun_sir 优 |
| 文档随提交 | 不做 | 19/22 次同步改 README/API | AdrianLuo 优 |
| 测试定位能力 | test 独立成条 | src+tests 混装 | kun_sir 优 |

**整体：`kun_sir` 的质量管控强一个量级，`AdrianLuo` 是「快照式提交」。**
但两者面对的问题不同——`AdrianLuo` 做的是 1,415 文件规模的首轮移植，把上游整块搬进来
本来就不可能拆成 64 行的单元；`kun_sir` 做的是已落地代码上的缺口填补，天然适合小步。

## 三、各自的管控漏洞（不能只看谁分高）

**kun_sir 的风险：自我确认。**
82% 的证据是他自己打的读数，37% 的相邻提交在同一个文件上来回改。
一旦读数打印的位置本身错了（本项目踩过：`GetKeyState` 位布局、呈现层缓存 CGImage、
绑定层全绿而输入链路不通），整条链路会一路绿灯。
所以这套流程的真实管控力不在提交记录，而在外部门禁：
`ra2mac_docs/scripts/regress.sh` 11 条 smoke + `known-red.tsv` 登记 + `pack-dist.sh` 硬门禁。
**提交记录本身证明不了质量，它只证明了每一步都留下了可复核的痕迹。**

**AdrianLuo 的风险：不可定位。**
63% 的提交 ≥3000 行。他 2026-10-29 出现了 `GPU 资源恢复…` 的重复提交，
说明连他自己都需要重放历史来修——这正是不原子带来的成本。
一旦后面发现某个后端配置有回归，回滚范围是 986 个文件。

## 四、可直接借鉴的一条

`AdrianLuo` 每提交同步刷 README/API 这件事，`kun_sir` 这边是空白。
本轮 117 条提交的知识全部散在 commit message 和 `reports/` 里，
README 里读不到「当前支持到什么程度」。建议在里程碑收口时补一次，
而不是每条都刷（会稀释提交原子性）。
