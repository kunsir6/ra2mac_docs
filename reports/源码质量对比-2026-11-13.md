# 源码质量对比（不是提交元数据，是代码本身）

仓库：`ConcordRTS` @ main
统计时间：2026-11-13
口径：`git blame --line-porcelain` 逐行归属，覆盖全部 `.cpp/.h/.inl`（`src/` `compat/` `tests/`）。
函数边界用括号配平解析（先剥离注释与字符串），一个函数归属给正文行数占比 >70% 的作者。

**归属结果**：全库 C/C++ 825,400 行，其中
`kun_sir@126.com` **30,669 行（3.7%）**、`AdrianLuo-XH` **792,726 行（96.3%）**。
下面的每个比值都是各自内部比例，不受体量差影响。

---

## 一、一句话

`kun_sir` 写的是**小函数 + 高注释 + 零重复**的代码；
`AdrianLuo` 写的是**能跑、可读性低、重复度高、但有极少数巨型函数**的移植代码。
结构债几乎全部来自 `AdrianLuo`，且集中在 `RuntimeShell.cpp` 一个文件里。

## 三、结构级问题（比任何单段代码都严重）

全库最大的三个编译单元：

| 行数 | 文件 | include 数 | 主要作者 |
|---|---|---|---|
| **90,459** | `src/runtime/host/RuntimeShell.cpp` | **886** | AdrianLuo（S 也有 38 次提交，但主要是补 compat 挂钩） |
| 42,668 | `src/render/core/RuntimeMapRenderer.cpp` | 249 | AdrianLuo |
| 30,792 | `src/runtime/session/RuntimeSessionWorld.cpp` | — | AdrianLuo |

`RuntimeShell.cpp` 里有一个函数：

```
int runRuntimeCommandSmokeTest(const RuntimeConfig& config) {   // 第 60,278 行
    ...
}                                                              // 第 74,546 行  → 14,269 行
```

这段代码 98.8% 的行归属 `AdrianLuo`（14,234 / 14,269），`kun_sir` 只碰了 35 行。
它一个函数就是全库最大的函数，同时也是全库最大文件的 1/6。

**>1000 行函数共 43 个，合计 83,415 行 = 全库代码的 10%。全部来自 `AdrianLuo`，`kun_sir` 一个都没有。**

`.inl` 文件 1,073 个，`.cpp` 只有 600 个——64% 的实现单元是头文件式碎片（957 个仅由 `AdrianLuo` 触碰）。
这直接导致 886 include 的 TU 存在：改一行内部实现，全库重编。

`AdrianLuo` 的代码分布：核心 63%、`diagnostics/` **23%**、测试 13%。
即「生产代码里每 4 行就有 1 行是诊断/追踪代码」，这些和业务逻辑混在同一个 TU 里。

## 四、哪些差异是职责造成的，不能算他的锅

诚实地说，四项里有两项对 `AdrianLuo` 不公平：

- **`reinterpret_cast` 10 倍差**：`kun_sir` 的 68% 代码在 `compat/win32/`，把 Win32
  `HANDLE/HWND/HDC`（本质是 `void*`/整数令牌）搬到 macOS 对象上，`reinterpret_cast`
  就是那层的语言。`AdrianLuo` 主要写平台无关的模拟/渲染，没有这个需求。
- **`printf` 直出 2 倍差**：`kun_sir` 的方法论就是「先打读数再改代码」，全库 `CONCORD_*_TRACE`
  开关都是他加的。这些输出有闸门（默认静默），属于可接受的调试设施。
- **魔数他反而更少**：因为他习惯把常量抽成 `runtimeVxlLightSpaceToken()` 这类具名函数，
  而不是散在表达式里。
- **重复 10% 有相当比例是刻意的内联快路径**（如 `runtimeVxlPaletteLookupEnabled` /
  `runtimeVxlSofteningEnabled` 这一族 getter，逐字段复制是为了避免间接调用）。

真正站得住的批评是三条：

1. **单函数 14,269 行**。这不是风格，这是无法评审、无法单测、编译一次要重解析 886 个头的实体。
2. **重复 368 组里有一类是纯复制粘贴**：`toLower` 在 `ModCompatibilityScanner.cpp`、
   `ObjectReferenceValidator.cpp`、`AiTriggerSandbox.cpp` 里各写一遍，第 4 处写成 `toUpper`。
3. **23% 的诊断代码混在生产 TU 里**，加上 90% 的提交把 src 和 tests 混装，导致
   「这段逻辑到底是游戏行为还是观测手段」在代码层面已经分不开。

## 五、代码风格对照

`kun_sir` 的文件开头（`compat/win32/src/RuntimeWin32CompatProcess.cpp`，28 行注释先讲
「哪些符号必须说谎、哪些必须诚实」，再进代码）：

```cpp
// 这一批符号的难点不在"实现"，而在"哪些必须说谎、哪些必须诚实"：
//   必须诚实（返回失败）：
//     GetModuleHandleW(具名) / GetProcAddress —— macOS 上没有 DLL 与导出表。
//       ...若返回一个"看起来有效"的假地址，崩得更晚、更难查。
//   必须等价（返回成功）：
//     GetCurrentProcess / GetTickCount64 ... 只有"用哪个内核接口"的差别。
```

`AdrianLuo` 的代表性片段（`RuntimeMapRenderer.cpp`，零注释，靠命名自解释）：

```cpp
std::string runtimeVxlLightSpaceToken() {
    const char* rawValue = runtimeRendererEnvironmentValue("CONCORD_VXL_LIGHT_SPACE");

    }
    const std::string value = toLowerAscii(rawValue);
    if (value == "camera" || value == "viewer" || value == "view") {
        return "camera";
    }
    ...
```

单看这段，`AdrianLuo` 的代码是干净的——函数小、早返回、命名清楚。
问题不在微观写法，在**他把这个写法复制了一万五千次之后，又造出几个万行函数**。

## 六、值得抄回来的两点

`kun_sir` 的 30,669 行里没有一条 `TODO`，也没有一个超 300 行的函数——但这是因为他只写了
3.7% 的新代码（compat 层），**没经历过 `AdrianLuo` 那种「把整套引擎塞进一个 TU」的压力**。
如果哪天 compat 层扩到几万行，这套「小函数 + 高注释」还能不能守住，目前没有证据。

`AdrianLuo` 值得抄的有两点：

1. **命名即文档**。`runtimeVxlSofteningEnabled` / `materializeRuntimeLoadStateFromIni`
   这类名字，不比注释信息量低，而且不会过期。
2. **常量具名化**。他的魔数密度比 `kun_sir` 低 34%，这是抽函数抽出来的，不是靠注释解释出来的。

---

## 七、如果要动手，按性价比排序

1. **把 `runRuntimeCommandSmokeTest` 拆掉**。14,269 行单函数，拆成按命令类型分派的若干
   子函数，风险最低、收益最大（一个函数的可读性 ≈ 全库 1.7% 的代码）。
2. **抽出 `toLower/toUpper` 到一处**。368 组重复里最容易消的一类。
3. **诊断代码分文件**。`diagnostics/` 已经占 23%，把它们从生产 TU 里挪出去（不是删），
   才能让 886 include 降下来。
4. **不要给 `kun_sir` 加「注释率」类门禁**。他的注释率已经 22%，再压只会产出废话注释；
   他的真实短板在上一份报告里——证据是自己打的读数，需要外部回归门禁兜底，不是代码风格。
