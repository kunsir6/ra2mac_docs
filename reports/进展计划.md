# ConcordRTS 持续推进计划

> 目标：在**不破坏 Windows 构建**的前提下，让项目原生跑在 macOS 上。
> 执行方式：每小时自动推进一个工作单元，结果写回 `progress/`。
> 起点：P0 已完成（内核 170/170 编译、10/10 测试通过、产品构建 12 个 TU 失败）。

---

## 一、三条不可违背的约束

这三条决定了所有技术选择，任何一轮推进都不能破：

**1. 只增不改 Windows 分支**
所有平台差异都通过「在既有 `if(WIN32)` 之后追加 `elseif(APPLE)`」表达。Windows 分支内部一个字符都不动。自证方式：`git diff` 只有新增行。

**2. 不删除文件**
一律「临时文件 + 原子替换」。既能避开沙箱的批量删除拦截，也让中途失败不留半成品。

**3. 按族收口自动提交，绝不 push**
定时任务不再「永不提交」，改为「族收口时自动 commit」。族 = 任务 ID 去掉尾部 `-数字` 的前缀（`S3`、`P1`、`P5`、`T`），某族全部任务 `done/superseded` 即提交一次；partial / diagnose-only / 半成品态不提交。提交用统一文案（见「提交颗粒度与文案」），但**绝不 push / reset / force**——push、远程同步与存量归位仍由人做。

---

## 二、每小时的执行协议

自动化按这个顺序跑，每轮只做一件事：

| 步骤 | 动作 |
|---|---|
| 1 | 读 `progress/queue.json`，取第一个 `status=pending` 的任务 |
| 2 | 置为 `in_progress`，按 `detail` 执行 |
| 3 | 跑 `verify` 里的命令，贴真实输出 |
| 4 | 通过 → `done`；不通过 → 保留 `in_progress` 并写清卡在哪 |
| 5 | 追加一条 `progress/RUNLOG.md` |
| 6 | 判定本轮所属「族」是否收口；收口则 `git commit`（统一文案，绝不 push） |
| 7 | 停止，等下一个小时 |

**熔断规则**：如果上一轮仍是 `in_progress`，或连续两轮没有实质进展，本轮只做诊断、不改代码，把结论写进 RUNLOG 供人判断。

**阻塞规则**：任务缺前置条件（比如需要 Windows 机器）就标 `blocked` 并写原因，立刻跳到下一个 `pending`。不空转。

---

## 提交颗粒度与文案

| 项 | 规则 |
|---|---|
| **锚点** | 族收口。族 = 任务 ID 去掉尾部 `-数字` 的前缀（`S3`、`P1`、`P5`、`T`）；某族全部任务 `done/superseded` 即提交一次 |
| **禁止** | partial / diagnose-only / 半成品态（只编译不链接）不提交 |
| **范围** | 该族 `touches` 仓库内文件 + 该族新增源文件 + 相关 cmake（报告 md 与 `progress/` 在仓库外，不纳入） |
| **文案** | 单行 subject ≤60 字：`<族ID> <成果一句话>（<关键对账数字>）`，无数字则省略括号；对账数字优先取「链接缺口 N→M > 编译 TU X/Y > 测试/断言数」 |
| **绝不** | push / reset / force / amend——远程同步与存量归位由人做 |

示例：`S3 GDI 区域与图元：42 符号清零（缺口 236→225）`、`P1 平台轴接入：多平台骨架成立（Windows 分支零改动）`。

## 三、阶段与顺序

顺序不是按「好做」排的，是按「解锁价值」排的。

| 阶段 | 内容 | 为什么在这个位置 |
|---|---|---|
| **P1** | 平台轴接入 → 多平台骨架成立 | 只加分支不改语义，风险最低；做完后「Windows 与 macOS 并存」在构建系统层面就成立了 |
| **P2** | 消除 12 个失败 TU | 从「缺一个头文件」这种 20 分钟的事开始，逐步啃到 `RuntimeShell` |
| **P3** | SDL3 窗口 + 软件呈现 | 第一次能看到画面 |
| **P4** | SDL3 音频 | 从「静音可玩」到「有声可玩」 |
| **Q** | 资源美术派生 | 任何一轮被阻塞时插队执行，纯数据不碰源码 |

## 五、唯一需要你出手的事

**B-01** 卡在物理条件上：证明「P1 改动对 Windows 零回归」需要一份 Windows 侧基线。在 Windows 机器上跑：

```bash
cmake -S . -B build-core-win -G Ninja -DCONCORD_PORTABLE_CORE=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-core-win
./scripts/capture-core-baseline.sh ConcordRTS/build-core-win baseline/core-windows-x64.json
```

把 `baseline/core-windows-x64.json` 拷回来放进 `baseline/` 即可。这一项不影响后续推进——P1 的改动在 Windows 上根本不进入编译，只是「缺一份事后对账的凭据」。

## 六、怎么暂停或调整

- **暂停**：删掉或暂停这条定时任务即可，进度都在 `progress/queue.json` 里，随时能续。
- **换优先级**：改 `queue.json` 里任务的 `status`。把某项置为 `pending` 就会优先被取到（取的是数组顺序里的第一个）。
- **插队**：把 `Q-01` 的 `status` 改成 `pending` 并移到数组靠前位置。
- **重来**：`queue.json` 是纯文本，随时可以手改。

## 八、一个会改变节奏的发现：验证天花板

P2-03 之后，剩余失败 TU 的修复**只能做到「编译通过」，做不到「链接通过」**。

原因：`concord_runtime` 是一个整体可执行文件。在 `RuntimeShell.cpp`（P2-08）解决之前，任何单项修复都拿不到端到端验证。

**这意味着原来 P2-04 → P2-07 的顺序是错的。** 按那个顺序做，会在工作区累积 5–6 个「只编译不链接」的改动，把风险后置到 P2-08 一次性引爆——届时无法定位是哪一项引入的问题。

**已调整：P2-08 提前到 P2-04 之前。** 先建立「能链接」这个门槛，之后每项修复才有真验证。

这也正是 `queue.json` 里那条 `rules.verification_ceiling` 的作用——让后续每一轮都记得这条约束，而不是重新踩一遍。
